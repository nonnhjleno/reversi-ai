# Phase 5 サーバー提出時の時間予算と安全応答の検討

検討日: 2026-11-07。基準: `main`の`110c1e7841d32f51e6b7b5419bff8df761becfb7`（Phase 4統合済み）。検討ブランチ: `docs/ai-phase5-server-time-budget`。

本書はPhase 5以降の実装で参照する引き継ぎ方針である。7秒を起点とする安全応答、0.1秒刻みの実機調整、提出ZIPの保存・復旧を各工程へ反映する。6.0秒・6.5秒などの内部値は初期案であり、実装済み・安全確認済みの設定ではない。今回の変更は本書だけとし、文書をcommit・push・mergeする。プログラム実装・サーバー提出・ローカルテストは行わない。

## 1. 現時点の推奨

**最初は「genmoveの受付から応答までを7.0秒に収める設計」とし、成功した設定から0.1秒ずつ増量して実機で確かめる。サーバー自身の実経過時間による中断と、既知の正常ZIPへ戻せる運用を組み合わせる。成功した最大設定と、普段使う設定は分ける。**

7秒自体が安全を保証するわけではない。探索の止め方が不十分なら7秒設定でも10秒を超え得る。逆に、サーバー自身の時計を見ながら止まれるなら、CPUが遅いことは主に「同じ時間で読める量が減る」形で現れる。ローカルで7秒かかる固定深度を、そのままサーバーでも実行する方法とは区別する。

最初に改善すべきなのは、7秒を7.5秒に近づけることよりも、途中で確実に戻れる探索と、戻った後に応答を送り切る時間の確保である。共有CPUの混雑などでプロセス自体が長く実行されなければ、通常のPythonプログラムだけで10秒以内を絶対保証することはできない。

## 2. 確認できた前提と未確認事項

### 利用者から確認できたこと

- サーバーの10秒制限は、`genmove`の受信から応答までである。Pythonプロセスの起動からの10秒ではない。
- サーバーのCPUは手元の環境より弱いと見込まれる。具体的な性能比は未測定。
- 着手ごとの時間やタイムアウト理由は、おそらく確認できない。取得できない前提で計画するが、取得不能と確定したわけではない。
- 複数ファイルはZIPで提出する予定。新しいアップロードで旧ファイルは消える。
- 何回も再アップロードして確かめられる。利用者は成功した設定から0.1秒ずつ増量する運用を希望している。

### まだ分からないこと

サーバーのOS、Python版、CPU割当、同時対局数、メモリ制限、ZIP展開先と起動ファイル名、エラー表示の詳しさは未確認。10秒の厳密な端点が「親の送信開始」「子が1行を受領」「親が改行まで読了」のどれに対応するかも未確認である。これは起動から計測するかという確認とは別の、短い受渡し区間の問題である。

本書ではサーバーがLinuxやDockerを使っているとは決めつけない。負荷試験でLinuxコンテナを使う場合も、サーバーを再現したとの保証にはしない。

### プロジェクトで確認できたこと

[授業仕様の処理時間](プログラム開発方法.md)は通常コマンド1秒、`genmove`10秒。[詳細計画のPhase 5](リバーシAI段階開発・評価設計書.md)は反復深化・安全応答・`search_v1`の独立固定を対象とし、測定した全応答8秒以内を暫定安全目標にしている。7秒案はその内側の提出用候補であり、10秒の仕様や既存の暫定目標を書き換えるものではない。

現在の`ai_engine.py`は既定深度2、公開探索の最大深度4で、時間による中断は未実装。`search_trace.py`も実AIの対応予算をdepth1〜4に限定し、timeを拒否する。ハーネスにtime設定があることと、実AIが時間制限を守れることは別である。[Phase 4の設計](phase4_design.md)・[実装報告](reports/20261107_phase4_implementation.md)も参照する。

手元の`web.py`はHTTP要求ごとにプロセスを起動し、盤面を再生する。これはサーバーの実装を示す資料ではなく、HTTP全体の時間をそのままサーバーのgenmove時間へ読み替えない。

## 3. 弱いCPUで何が起こるか

| 方法 | CPUが遅くなったとき | 提出時の位置付け |
|---|---|---|
| 固定深度だけで最後まで探索 | 同じ木でも時間が延び、10秒を超え得る | 正しさ・同条件比較用。単独の安全対策にはしない |
| 固定ノード数だけで探索 | ノード当たりの時間差で応答が延びる | 比較の再現性には有用だが、応答期限も別に必要 |
| 自分の実経過時間を見て中断 | 遅い環境では少ないノード・浅い完了深度で終了 | 提出用の第一候補 |
| CPU使用時間だけで中断 | CPUを割り当てられない待ち時間を見落とす | 外部10秒制限の主時計にはしない |

Pythonの`perf_counter_ns()`は待ち時間を含む経過時間を測る単調時計として使える。一方、`process_time_ns()`はプロセスが消費したCPU時間を測り、待っている時間を含まない。期限には前者を使い、後者は負荷の診断が必要な場合の補助にとどめる。ローカルとサーバーの時計の絶対値を比較せず、そのプロセス内の差だけを使う。[Python time公式資料](https://docs.python.org/3.13/library/time.html#time.perf_counter_ns)

例えば「7秒のCPU時間を使う」という条件では、CPUを平均半分しか割り当てられなければ経過時間が14秒程度になる場合がある。これは説明用の単純化で、性能比の測定値ではない。「7秒の経過時間で止める」条件なら、待っている間も期限は近づく。ただし再開後に停止確認へ到達するまでは戻れない。

## 4. 7秒と7.5秒の比較

| 応答までの目標予算 | 10秒までの名目余裕 | 7秒案との違い |
|---|---:|---|
| 5.0秒 | 5.0秒 | 未知環境での初回確認に使う保守的候補 |
| 7.0秒 | 3.0秒 | 通常提出の第一候補 |
| 7.5秒 | 2.5秒 | 目標予算は約7.14%増、名目余裕は約16.67%減 |

この表の秒数は探索だけでなく応答までの予算である。名目余裕は観測した安全余裕ではない。タイムアウトの確率が表の比率で増えるという意味でもない。

0.5秒増やしても、次の深さの探索が完了しなければ返す手が変わらない場合がある。7秒から7.5秒への変更を、そのまま棋力7.14%向上と解釈できない。Phase 4では最大深度4もあるため、その上限に早く達する局面では時間を増やしても探索量さえ増えない。

失敗率が小さくても複数着手では積み重なる。独立で一定の着手当たり超過率を仮に0.1%、自分の着手数を30回と置くと、少なくとも一度超過する確率は`1 - 0.999^30 ≒ 2.96%`。これは実測値ではなく、余裕を削る損失を考えるための例である。実際の混雑や同一対局内の着手は独立とは限らない。

**再提出できる条件を使い、7.0→7.1→7.2秒と小さく進める方針を採る。7.5秒もその延長の候補にできる。** 0.1秒は試行の刻み幅であり、安全余裕の測定値ではない。完走した設定を記録しても、将来の混雑時まで保証したとは扱わない。

## 5. 時間を三つの層に分ける

次の数値は設計を相談するための初期例であり、実測済みの設定ではない。上限近くまで毎回待つ必要もない。

| 層 | 初期例 | 役割 |
|---|---:|---|
| サーバーの外部期限 | 10.0秒 | 利用者が確認した失効条件 |
| 自プログラムの応答目標 | 7.0秒 | 受付から盤面確定・出力までを含める |
| 探索途中での停止確認期限 | 6.5秒 | 戻り処理・検証・盤面確定・flush用に0.5秒を残す |
| 新しい深さを始めない目安 | 6.0秒 | 完了済み結果があれば無理に次へ進まない |

6.0秒と6.5秒は、ともにコマンド受付を原点とする。探索開始から6.5秒を追加で数える設計にはしない。rootの合法手列挙・設定確認などに時間がかかった分も消費済みとして扱う。探索処理そのものに許す長さは、その時点の残り時間から決まる。全反復で期限を共有し、深度を上げるたびに7秒の起点を取り直さない。

式では、子がコマンドを受け取った時刻を`t0`、応答目標を`B`、後処理の予約分を`R`とし、途中停止の期限候補を`D = t0 + B - R`とする。`R=0.5秒`で十分かは未検証であり、弱いCPU・混雑・trace有無の測定で決め直す。パイプ待ちや子が実行される前の遅延もあり、子の7秒と親が観測する7秒は完全には一致しない。

後処理には、再帰からの戻り、選択手の検証、実Boardへの一度の適用、必要な計測記録、1行のstdoutとflushまでを含む。正式測定では現行producerがstdoutの前にtraceを書き込む点も計上する。サーバーへは大量のログを出さず、stdoutには課題の応答だけを出す。

「hard deadline」と呼んでも、協調的な時計確認でOSの実行停止まで制御できるわけではない。次の分解を測る。

`親が観測する時間 = 受渡し・実行待ち + 準備 + 探索 + 停止確認の遅れ + 戻り・確定 + 記録・出力・読了`

探索中の待ちがすでに探索時間へ入っている場合は二重計上しない。この分解は、未計測の区間を見落とさないための整理である。

## 6. 第一実装は反復深化と協調的中断

### 完了結果を一段ずつ確保する

1. `genmove`受付直後に`t0`を取得する。rootの合法手を列挙し、通常着手では決定的な合法候補を先に一つ確保する。
2. 合法手なしはパス／終局として速やかに仕様どおり応答する。7秒を使い切るための探索はしない。
3. 深度1からAlpha-Betaを進める。root全体の探索が完了した時だけ、返却候補と完了深度を更新する。
4. 次の深さを始める前には開始停止の目安を確認し、探索途中でも停止確認期限を確認する。
5. 時間による中断は専用の制御として上位へ戻し、最後に完了した深度の候補を採る。深度1も未完了なら、最初に確保した合法候補を使う。未完了の候補に厳密なroot評価値を付けない。
6. 本体で実盤面へ一度だけ適用し、1回だけ応答する。中断したrootの途中評価や未完了の最善手らしい候補を、厳密な完了結果として採用しない。

Phase 3のMinimaxと評価関数は変更せず、Phase 4の同点規則・placement ply・パスで深度を減らさない契約を維持する。初期版ではroot順を固定し、前回結果によるroot並べ替えなどの追加判断を急がない。通常のルール例外や設定違反まで一括で捕まえ、合法フォールバックの成功に変えない。

### 時計を確認する位置

最初は再帰呼出しの冒頭に加え、合法手生成・評価・仮着手など、ひとまとまりの処理の前後でも確認する。root手の間や深度の間だけの確認では、一つの大きな部分木の終了を待って超過し得る。

時計の確認を一定ノードごとに間引くのは、まず安全性と確認コストを測ってからにする。ノード当たりの時間は局面とCPUで変わるため、C++エンジンの数百ノード単位の確認間隔をPythonへそのまま移さない。Pythonの時計確認にも費用はあるが、Phase 5では先に停止可能性を確保する。

Stockfishは反復深化と時間上限の確認を行い、リバーシのEdaxも次の反復を継続する判定と途中のtimeout判定を分けている。前者の最適時間・最大時間、後者の複数時間境界は、考え方の参考になる。ただし、持ち時間制の配分式やC++用の係数は今回の一手10秒制へ移植しない。[Stockfish探索](https://github.com/official-stockfish/Stockfish/blob/master/src/search.cpp)、[時間管理](https://github.com/official-stockfish/Stockfish/blob/master/src/timeman.cpp)、[Edax探索](https://github.com/abulmo/edax-reversi/blob/master/src/search.c)

### 最大深度4をどう扱うか

現行の最大4を残せば、早く深度4を完了した後は追加時間を使わない。これは安全性の第一確認には使えるが、7秒と7.5秒の探索品質差を測る前に明示する必要がある。

候補は、参照Minimaxの0〜4を維持し、時間対応の探索にだけ別の深度上限を設ける方法である。上限・入力検査・計数の契約を先に決め、深さを上げる場合も途中停止を必須にする。専用の終盤完全読みやTT・bitboardへ拡張する理由にはしない。具体的な上限値はPhase 5設計時の未確定事項とする。

## 7. 他の方法をどう評価するか

| 方法 | 評価と採否 |
|---|---|
| ローカルとサーバーの速度比から固定深度・nodesを減らす | 補助的な較正には使えるが、局面・割当・混雑で比率が変わる。時計による期限の代用にはしない |
| 次の反復時間を予測して始めるか判断する | 安全な中断を実装した後の改善候補。前回の時間・増加率を使っても外れるので、途中停止期限は残す |
| ノード予算と時間期限の併用 | 再現性・資源上限の補助候補。Phase 5は既存depth比較を維持すればよく、nodes対応の追加を必須にしない |
| Pythonの別threadとTimerで時間切れにする | threadは安全に強制停止できず、Timerの起動時刻も厳密ではない。共有盤面の競合や停止待ちを増やすため第一案にしない |
| Futureの`result(timeout=...)`で包む | 待つ側のtimeoutだけでは実行中処理は止まらない。executor終了で待ち続ける場合もあり、単独対策にはならない |
| SIGALRMなどOS signal | Unix依存で、Pythonのhandler実行が遅れる場合もある。Windowsの手元環境と共通の主対策にしない |
| 親プロセスが探索子を監視し、期限前に回収する | 将来の補強候補。親が合法候補とstdoutを所有し、子は実Boardを触らない設計が必要。起動費用・子の残存・許可・終了待ちを検証するまで導入しない |
| 専用CPUやサーバー設定を変更する | 利用者側で可能とは分からず、今回の前提にしない |

thread、Future、signalの制約はPython公式資料で確認できる。外部プロセスのtimeoutにも起動や終了回収の費用があり、監視プロセス自身が実行されなければ絶対的な保証にはならない。[threading](https://docs.python.org/3.13/library/threading.html)、[concurrent.futures](https://docs.python.org/3.13/library/concurrent.futures.html)、[signal](https://docs.python.org/3.13/library/signal.html)、[subprocess](https://docs.python.org/3.13/library/subprocess.html)

## 8. 手元で行う検証の案

### 正しさと中断のテスト

時計を差し替える単体テストで、予算切れを狙った場所に発生させる。通常着手の探索前、深度1の途中、深度1完了直後、次のroot候補の途中、パス直後、終局、残り時間がほぼゼロの各条件を含める。完了した候補だけが残ること、入力・RNG・実盤面が不変であること、確定着手と出力が一度であることを検証する。

これとは別に実時計と子プロセスで測る。偽時計で通った結果を、そのまま原traceの時刻や正式計測に使わない。

### 弱い環境と混雑の試験

- 代表局面を序盤・中盤・終盤・合法手多数・角・パス・終局に分け、Phase 0のdevelopment側と既知局面を固定して使う。held_outは時間設定の調整にも使わない。
- 平常時だけでなく、CPU割当が小さい条件、競合負荷がある条件、処理の途中に実行待ちが生じる条件を分ける。CPU上の計算を増やす遅延と、`sleep`で待つ遅延は別物として記録する。
- Linuxコンテナが利用できる場合、CPU quotaを0.5、0.25などに制限する試験は候補になる。`--cpus`による割当制限は「その割合のクロック周波数のCPU」を再現するものではなく、周期的な実行待ちも生じる。実施条件と未再現部分を残す。
- Windowsでコア数や優先度を下げる試験は補助になるが、それだけでサーバーと同じ速さとは言わない。遅いCPUや別OSの実機が使えるなら追加する。

Linuxの`cpu.max`は期間当たりのCPU帯域を制限し、`cpu.stat`にはthrottlingの統計がある。DockerのCPU quotaもこの種の制約で、サーバーが同じ方式を採るとの情報ではない。[Linux公式資料](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu)、[Docker公式資料](https://docs.docker.com/engine/containers/resource_constraints/#cpu)

### 測定値と初期の件数案

応答時間の平均だけでなく最大、p95・p99、超過件数を保存する。分位点の計算法、各条件の件数、色、局面集合、seed、同時実行数を残す。探索だけの時間と、親が観測する受付からの全応答を分ける。長い応答の裾を見るという考え方は有用だが、大規模サービスの論文から、このゼミサーバーの遅延値を推定することはできない。[Dean・Barrosoの原著紹介](https://research.google/pubs/the-tail-at-scale/)

実装中は0.1秒・0.5秒・1秒などの短い予算で中断を繰り返し確認する。その後に、提出候補の5秒・7秒を同じ条件で測る。初期の実用試験案は通常着手100件以上を各負荷条件で測り、加えて固定2相手への各2局smokeと各100局の先後交換対局を行う方法である。件数は相談用で、成功済み件数や十分性の保証ではない。

初期の判断案は、外部10秒超過・不正手・異常終了0件、弱い条件を含む測定で全応答8秒以内、という既存Phase 5の安全目標を維持すること。応答目標7秒の超過も別に数え、8秒以内なら無条件で良いとはせず、予約分と停止遅れを見直す。10秒を超えた試行を測定から取り除かない。

## 9. サーバーでログが見えない場合

この条件では、7.5秒の採用判断に必要な「最大応答が何秒か」「余裕が何秒か」を直接確認できない。対局が完走したことは、その試行で外部期限に抵触しなかった証拠にはなり得るが、7.5秒でも安全という証拠にはならない。負けた理由が時間切れなのか、棋力なのかも区別できない場合がある。

実行時間が見えない間は、まず5秒または検証済みの7秒ZIPを使い、先後を替えて複数局・異なる時間帯・可能なら異なる相手で様子を見る。完走と勝敗は分けて記録する。失敗理由が不明なら「原因不明」とし、時間を増やして確認する方法は採らない。stderrやファイルのログが回収できると判明した場合だけ、提出規則に従い必要最小限の計測を追加する案を検討する。

反復深化なら、同じ時間内でそのサーバーが読める深さに自動的に下がる。モデルや時間設定を頻繁に上げ直す必要を減らせる。ただしサーバーに他の人のモデルと対局させること自体を、同条件の正式棋力比較と呼ばない。相手の更新や割当条件が分からない場合の順位・勝率には限界がある。

### 完走件数と「失敗ゼロ」の読み方

説明のため、各試行が独立で超過確率`p`が一定と仮定する。`n`回とも超過0のとき、二項分布から求める片側95%の上限は`1 - 0.05^(1/n)`になる。[NISTの二項分布](https://www.itl.nist.gov/div898/handbook/eda/section3/eda366i.htm)

| 独立試行数n | 失敗0でも残る上限の例 |
|---:|---:|
| 30 | 約9.50% |
| 100 | 約2.95% |
| 300 | 約0.99% |
| 1000 | 約0.30% |

これはこのサーバーに適用した正式CIではない。同じ対局内の着手や同じ混雑時間帯の試行には相関があり、結果が見えない試行を含む可能性もある。数局成功しただけで余裕が確保できたと解釈しないための参考計算である。

## 10. 0.1秒ずつ増量する運用

1. 7.0秒を起点に、コード・評価関数・依存を変えず、応答目標だけを0.1秒増やした完全なZIPを用意する。正常だった旧ZIPも手元に残す。
2. 各設定の完走・勝敗・異常表示・相手・先後・実施時刻を記録する。先後を替えた複数局を基本とし、一局だけの成功は初期確認として扱う。候補を絞った後は異なる時間帯でも繰り返す。
3. 問題が出たら増量を止め、既知の正常ZIP全体へ戻す。原因が分からなければ「原因不明」と記録し、時間切れや棋力の問題と決めつけない。
4. まず7.5秒を見直し地点にし、追加時間で手や対局結果に改善が見えるかを検討する。さらに上げるなら、既存の全応答8秒以内という暫定目標との関係を改めて整理する。増量自体を目的にしない。
5. 成功した最大設定と常用設定を分ける。例えば7.8秒まで通った場合に7.3〜7.5秒へ戻して運用する方法がある。この0.3〜0.5秒は相談用の例で、安全を保証する幅ではない。

混雑によって、同じ設定でも後で失敗する場合がある。成功した最大値を固定的な安全上限と呼ばず、ログなしという限界を残したまま実用上の設定を探す。

増量時も探索後の予約分を保つ。応答目標7.0秒・途中停止6.5秒という案なら、7.1秒では途中停止6.6秒、7.5秒では7.0秒となる。受付からの経過時間であり、探索だけに7.5秒使ってから出力する設計にはしない。これらは未実装の設定例である。

期限管理を実装してから実機調整へ進む。時間設定を増やした直後に勝っても、相手や先後が違えば、その勝利を0.1秒の効果とは判断しない。

## 11. 旧ファイルが消えることへの対策

**アップロードを差分更新として扱わず、毎回それだけで動く提出ZIPとして扱う。旧版はサーバーから取り戻す前提にしない。**

提出前に、同じコード・全依存ファイル・時間設定・Python想定版をひとまとまりでローカルへ保存する。ZIP全体と展開後の各資産のSHA-256、Git commit、未コミット差分の有無、時間設定、検証結果を対応させる。これはサーバーのファイル消去への復旧手段であり、Gitだけでは未追跡資産や提出したZIPそのものを復元できない場合がある。

想定される構成の例は、起動対象の`reversi.py`と、その直接実行時に必要な`ai_engine.py`・`search_trace.py`、将来導入する提出用設定である。現在の実装に学習モデルはなく、モデル重みの提出はPhase 5の必須作業にしない。ZIP内の階層と起動名はサーバー指定に合わせる。名前の大文字・小文字、解凍後の相対参照、作業ディレクトリが変わる場合も確認する。

開発用のharness・pytest・venv・ローカル環境変数や、サーバーに残っているはずの旧ファイルへ依存させない。Pythonはスクリプトのあるディレクトリをimport探索に使うが、設定ファイルの単なる相対パスは実行時の作業ディレクトリに依存する。必要に応じて`__file__`基準で解決する設計を検討し、実物を別の空ディレクトリへ展開して起動する。[Pythonのmodule探索](https://docs.python.org/3.13/library/sys_path_init.html)

ZIPのCRC検査だけでは動作・依存の欠落は分からない。破損確認に加え、展開物だけで`name`、通常コマンド、通常着手、パス、終局、連続対局を検証する。検証したZIPのbytesをそのままアップロードし、提出直前に別のZIPを作り直してすり替えない。[Python zipfile](https://docs.python.org/3.13/library/zipfile.html#zipfile.ZipFile.testzip)

提出時は既知の正常版ZIPを手元に残し、新版の完走確認前に消さない。失敗時には正常版ZIP全体を再提出する。再アップロードもできない期間や提出回数制限があるなら、本番枠での時間増量実験は控える。今回はZIP作成もアップロードも実施しない。

### 計測契約で先に詰める点

現行ハーネスのtime予算は`search_only`を測る。7秒の全応答目標を、そのまま`limit_ns=7秒`と同一視しない。コマンド全体の残り時間と、探索そのものの上限が両方ある場合の優先順位・実効設定を定義する。`REVERSI_EVAL_CONFIG`がない提出経路でも、安全な既定設定が働く設計が必要である。

現行のtime検証は実測探索時間が`limit_ns`を超えれば失敗とする。上限に達してから止め始める設計では戻り処理の分だけ超過し得るため、探索内の停止用余裕も先に確保する。探索開始を`S`、探索上限を`L`、探索内の停止・戻り用余裕を`R_stop`とし、停止開始の候補を`min(t0 + B - R, S + L - R_stop)`とする。余裕の具体値は未確定で、超過した記録は失敗のまま残す。上限や原traceを後から修復して成功にしない。

ノードは反復や中断した探索も含む実際の呼出しを数える。完了深度はroot全体が完了した最大のplacement深度、開始深度は実際に開始した最大深度とし、途中の値を完了扱いしない。具体的な停止理由と計数定義は契約へ先に記す。

探索時間切れに備える合法候補と、モデル障害時のfallbackは意味が異なる。現行traceの`fallback`はモデル関連の検証に使われ、trueなら正式資格を失う。探索中断を表すために機械的にtrueへ流用したり、正式validatorを緩めたりしない。`completed_depth=0`を含む安全応答の扱いを、既存契約と照合して決める。

時間制御は環境の速度で完了深度が変わり得る。固定depth条件での決定性・棋力比較と、time条件の`deployment`としての実用評価を分ける。提出時の応答目標を7秒から7.5秒へ変えても、学習用の固定相手`search_v1`の設定は勝手に更新しない。比較相手と提出版に同じ探索実装を使っても、用途と資産IDは識別する。

TT・bitboard・学習・専用終盤solver・大幅な高速化・投機的な相手番探索は本検討のPhase 5第一実装へ加えない。途中停止が安全にできることを先に完成させる。
