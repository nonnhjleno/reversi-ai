# Phase 9-B 最大探索深度の検証

2026年11月25日に、Phase 9-Aの `ec2863a` を基準として、最大深度4・5・6を同一時間で比較した。手作業評価の深度5は深度4に75.0%、Zero-TDの深度5は同じモデルの深度4に3 seed平均68.1%だった。手作業評価の深度6は深度4に58.3%で、序盤ペアによる95%参考区間は50%を含んだ。既定の最大深度は4、置換表は無効のまま運用する。

## 先行実験との対応

2026年11月14日の540局では、応答設定に深度4・5を指定したが、評価ハーネスの `unknown` と空の探索設定によって両者が実際には固定深度2で動作していた。この条件の棋譜は深度差の推定に使わない。11月18日に通常起動で追試したところ、手作業評価の深度5は直接対局5ペアで5勝4敗1分、勝ち点率55%。固定 `search_v1` 戦は1序盤で1勝1敗だった。通常負荷でも深度5が中断する例があり、提出採用は保留された。今回の比較は、明示した時間設定と深度をtrace4で全局照合し、同じ開発12序盤を全候補に使う。 [先行実験](20261114_depth5_experiment.md)・[追試と旧経路の調査](20261118_depth5_budget_stability.md)

## 実装と独立検証

通常起動の `REVERSI_MAX_DEPTH` と時間評価設定の `search.max_depth` で、最大深度5・6を指定できる。両設定を同時に与えると起動時に拒否する。固定深度の実AI設定は1〜4を受け付ける。反復開始と探索停止の時刻、合法な代替手、パスの深度、根の順序と同点規則を引き継いだ。最後に完了した反復の値と着手を保持し、期限を超えた反復には完了値を付けない。ハーネスのスキーマと正式資格の判定は維持した。 [設計・再現手順](../phase9b_depth_design.md)

専用テスト34件では、独立refereeと全幅Minimaxに対して手作業評価・n-tupleの値と着手を確認した。黒白、パス、終局、全滅と、深度5・6の開始拒否・途中中断を扱った。初回16件の失敗はテスト側が既存Minimax APIの深度4上限を経由したことが原因だった。独立オラクルを直接呼ぶように修正し、34件すべて再検証した。

## 中断、復旧と有効ペア

最初のZero-TD 701の残り22局では、genmoveの約72秒・697秒・810秒の異常と、Windowsのスリープ・復帰時刻が対応した。3ペアの両先後を再取得対象にし、元の8ペア16局は既存検証器で棋譜・通信・予算を照合した。再取得中にバッテリーによるスリープが入り、再取得試行の2ペア4局を保存済みの証拠から再検証した。703の最初のバッチは終了記録を残さず停止した。原因は未確認であり、途中スナップショットの完了脚7件のうち両先後が検証済みだった3ペア6局を用いた。残る701の1ペアと703の8ペアはAC接続を確認してから再取得し、別の終了記録で確定した。

失敗の元報告、途中スナップショット、Windowsのイベント、対象を選んだ事前登録はそれぞれ保持した。集計では同一序盤の両先後を一組として扱い、未確定の片側や重複する脚は算入しない。Windowsの自動スリープを実行中だけ抑える一時リクエストは処理終了時に解除した。画面のタイマーや電源プランの設定は書き換えていない。 [Windowsの電源管理API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)

## 採否と今後

同一時間の開発評価では手作業D5とZero-TD D5を有望候補とする。手作業D6は完了率が低く、深度4との勝ち点率の参考区間にも50%が入ったため優先度を下げる。D5の候補を凍結して独立評価へ進める。大学サーバーでの応答・資源条件、独立序盤での優位性を確認するまで、提出用パッケージと既定深度4を維持する。

次に試す技術は着手順の改善である。TTは無効にし、同じ評価・同じ時間で着手順だけを変えて、最悪局面と深度5・6の完了率を比較する。今回着手順の実装は変更していない。
