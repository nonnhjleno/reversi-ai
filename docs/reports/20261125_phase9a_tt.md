# Phase 9-A 上限付き置換表の実装と評価

2026年11月25日。比較元はPhase 8終了時の `354b522e08210242c9d75f8f1a32f8ef5c2267fe`。手作業評価とZero-TD 100,000局の双方で置換表を切り替えて比較した。

**置換表は実験機能として既定無効で保留する。** 4,096枠で深度4の対応時間比は手作業0.947、Zero-TD seed 701で0.934だった。いずれも短縮を観測したが、事前の10%短縮目標を満たした容量はなかった。同一時間の試走では各評価1勝1敗で、先後を交換しても同色の着手列が一致した。提出版は維持する。

## 実装と正しさ

`ai_engine.py` に上限付き直接配置の表、`timed_search.py` に1コマンドの反復間での共有、`search_trace.py` に明示設定と診断、`reversi.py` に通常起動での明示切り替えを加えた。盤面の行tupleと手番を完全照合し、同じ残り深さの根視点の値だけを使う。EXACTを返し、LOWERとUPPERは照会時の窓で枝刈りできる場合に使う。探索を中断したノードの未確定値は保存しない。既存の根の着手順、最大深度4、内部上限6.5秒、応答目標7秒を使う。[設計・再現コマンド](../phase9a_tt_design.md)

独立refereeとFractionによる全幅Minimaxを使い、10局面・黒白・深度1〜4で根の値と同点時の選択を確認した。n-tupleでは独立した黒視点オラクルを使い、パスと白番を含めて符号と着手を照合した。境界値、強制衝突、同一状態の優先保持、同点、期限中断、コマンド間の表の分離、実プロセスとGUI接続を専用テストで確認した。初回の専用テストでは実プロセス試験のAPI呼び出しを誤り、46件成功、1件失敗だった。既存の `Player.command()` に修正し、失敗したテストを再実行して成功した。原記録は `targeted-first.xml` と `proc-first.xml` に保存した。

固定局面では両評価40条件×非ゼロ3容量×3反復で720比較、Zero-TD seed 702・703と4,096枠で80比較を照合した。すべて探索値・選択手が一致した。Phase 8の検証済み実コードを別プロセスで動かした80条件についても、現行TTなしの値・着手・ノード数・葉数・パス数・枝刈り数と一致した。初期盤面から `(3,2) → (2,2) → (2,3)` と `(2,3) → (2,2) → (3,2)` の2経路が同一盤面・同じ白番へ合流することを独立refereeで確認した。座標は0始まりの `(x,y)` である。

## 同一時間の参考対局

Phase 8の開発用序盤、評価seed 20261119、最大深度4、内部6.5秒、起動・通常・genmoveの外部上限5・1・10秒を使用した。双方で同じ評価とモデルを使用し、直列で先後を交換した。置換表は候補側だけ4,096枠とした。

| 手作業 | 1／2 | 1・1・0 | 0／1 | 50% | 0 | TTなし52、あり52 |

各ペアは手作業で白の42石差、Zero-TD 701で白の15石差の同じ棋譜を先後交換で再現した。全4局の予算・通信を照合し、不正手、timeout、fallback、モデル・プロセス異常は0件だった。試行時間は手作業33.7秒、Zero-TD 701は28.9秒。通常着手の平均訪問ノードは手作業1,086→1,076、Zero-TD 701は987→980。最大応答は上の表に記録した。試走で観測した1ペアだけから独立した序盤への優劣は判断できない。時間短縮基準に届かなかったため、手作業の追加11ペアと、n-tupleの残り35ペアは実行しなかった。
