## 実行・復旧の契約

- 新しいプロファイルは `zero-500k`。学習率0.0000625、ε=0.20、γ=1、黒視点の半勾配TD(0)を継続する。並列数は1〜3。正式な評価節目は150,000、200,000、300,000、400,000、500,000局で、途中は1,000局ごとに局境界で保存する。
- 3系列が同じ節目へ着いた時点で、凍結モデルを `positional_v1`、深度2の `search_v1`、同じseedの100,000局モデルと比較する。開発序盤12組の先後交換と評価seed 20261119を固定する。学習と評価は同時実行しない。勝ち点率は試行ごとに記録し、3 seedの等重み平均を示す。
- 読み手は削除共有を許可して状態を読み、表示ファイルの置換はWindowsエラー5・32・33だけを最大約1.53秒の待機で再試行する。子プロセスは更新を保留した場合にログを残して学習を続ける。モデル・棋譜・stateの保存失敗は上位へ通知する。
- 新しい子プロセスが作られる前の既知の共有競合は、同じ確定入力を再検証した後に最大2回再試行する。原因不明の異常終了や、不正な確定状態を使った再学習を避ける。停止要求で局境界の保存を待ち、管理プロセスが異常終了した場合は排他ロックとプロセスの作成時刻を照合して手動で再開する。
- 評価プロセスが起動後に失敗した場合は、モデル、予算、序盤、先後、seed、生の対局記録と再集計値を照合する。異常が最初の `name` の応答待ちに限られている試行は、最大2回まで、同じ条件で新しい出力先にやり直す。対局開始後の異常や、契約・ハッシュに合わない結果は自動再試行の対象外。正常終了済みの比較を再実行せず、確定結果は比較ごとに1件だけ集計する。
- 正常な確定保存点が欠けた場合や分岐している場合は再開を拒否する。過去の未確定区間を正常な区間が覆う場合は復旧済みとして記録する。現状の不整合は `verify` の終了コードに反映する。

最初の短時間実行 `s-1-011101` は、既存トレーナーの累積上限100,000局による `invalid_td_game_limit` で停止した。そこで、保存点を必須とする長期モードの上限だけを500,000局に広げた。旧トレーナーとの互換は既知2版のSHA-256に限る。

検証用の `s-1-011427` は外側の観測スクリプトが180秒に達して管理プロセスが終了した。再開後に全3系列が100,040局へ到達した。評価の `name` 応答待ちが失敗し、その後の3並列試行 `s-3-012808` でも9比較中1比較で同じ異常が発生した。異常時と同じ凍結モデルを直接起動した検査では0.741秒で応答し、起動異常を常時再現できなかった。起動タイムアウトに限定した再試行を追加し、後者の評価の生データで正常8件と再試行対象1件を区別できることを確認した。予算とタイムアウトはPhase 7.1の条件を維持した。

その後の停止・再開試験 `s-restart-013909` では、運転中の `status.json` の置換でもWinError 5を記録した。運転中の集計済み進捗の書き換えを延期できるようにし、発生回数を記録する。起動確認と終了時の状態は、上限付きの再試行後に公開を確認する。正式なcheckpointの検証条件は同じ。

### 保存点と評価の実証

1・2・3並列の連続試験と、停止後に再開して `status.json` を別プロセスで保持した試験を照合した。4試行の各seedで100,000局の起点から100,020局までの確定連鎖をたどり、最終モデルの実bytes、model ID、乱数状態、累積回数、追加20局の棋譜が一致した。連続試験と再開試験のソース差は運転中の表示更新を扱う `tools/phase7_longrun.py` のみで、トレーナーと評価のソースは一致した。保存時刻や区間境界は試行ごとの記録に残す。根拠は `checkpoint-comparison-e5b3cf7.json`。

連続試験は各9比較を照合し、各試行の集計を生成した。表示ファイルを保持した `s-restart-015815` では、置換の延期を2回記録して3系列の学習を完了した。その後、701対 `positional_v1` の `name` タイムアウト2試行を記録し、3試行目を採用した。702対 `search_v1` では先後2局に `quit` と `name` のタイムアウトが分かれて発生した。探索深度の検証も欠けたため自動再試行対象に含めず、保存済みの3モデルを残して停止した。

Full終了後に最終コードの `s-restart-033811` で停止・再開を再確認した。701が100,010局、702・703が100,000局の確定保存点で停止し、`verify` は0。3並列で再開して別プロセスから `status.json` を保持したところ、置換の延期1回を記録して運転を継続した。全3系列が100,020局に達し、9比較と集計が完了して最終 `verify` も0だった。モデル実bytes、model ID、乱数状態、累積回数、棋譜は連続試行3件と一致した。根拠は `smoke-results-033811.json` と `commands-033811.jsonl`。
