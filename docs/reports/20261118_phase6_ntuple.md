# Ranger Phase 6 実装・検証報告

## 設計と実装

`ntuple.py` は盤面と手番を検証し、黒視点のlogit・tanh価値と、重みIDごとの出現回数を返す。`ntuple_io.py` はversion 1のモデルJSONを検証・保存する。`phase6_player.py` は明示指定したモデルで一手選択し、既存Boardへ着手を渡す。GUIは指定を受けて子プロセスを切り替える。学習用APIから推論と同じ特徴量を利用できる。[数式・データ形式・実行契約](../phase6_design.md)

2-tuple 32代表、3-tuple 24代表。各代表の8対称像を手番別LUTで共有する。計112 LUT、1,872重み、1局面448参照。出現回数を重みの係数とする。黒は黒視点の値を最大化し、白は最小化する。確定勝敗の選択スコアはtanhの飽和域の外に置き、同じ結果内では石差を比較する。引き分けの選択スコアは0。

単一JSONは定義・重み・来歴を一緒に保存できる。今回の資産は約9.6 KB、ローカル読込中央値は約1.5 ms。固定長のbinary64バイナリを別ファイルとして管理する案も検討し、今回のサイズ・時間と標準ライブラリでの実行互換性からJSONを採用した。ファイル実bytesのSHA-256、payloadのSHA-256、定義・重みで決まるモデルIDを個別に検証した。保存は同一ファイルシステムのhard linkで先着を保持する。

## 独立検証と実行経路

専用pytest 125件、失敗・error・skipは各0。独立オラクルは全端点対から直線を選び、座標ラベルを載せた行列の転置と反転、3進パターンの全列挙表で参照を求める。候補の配置・変換・エンコード・参照・加算は期待値計算に呼ばない。全36パターンと64マス×8操作、合成・逆変換・回転・反転、合法着手との可換性を照合した。固定seedの8合法棋譜から480以上の状態を照合し、空き0から60、強制パス、終局、対称盤面を通過した。

手計算fixtureでは初期盤面の隅の縦2マスと斜め2マスを使った。黒番で0.25と−0.125を各8回加えてlogit 1、白番では−0.5を8回加えてlogit −4。別の状態で単一代表に重複のない8参照を確認した。大きい正負重みの相殺、tanhの飽和、有限差分で重複回数を含む勾配を照合した。入力・重み・乱数の不変性、双方合法手なし、片側だけ合法手なし、空きを残す終局、引き分けを検証した。

I/Oは重みのbinary64ビット、保存の再現性、定義と来歴の独立性を照合した。重複キー、旧版と互換性のない定義、欠落、切断、非有限値、改変hash、過大ファイル、読書き障害、同名への競合保存を再現した。子プロセスの全7コマンド、EOF、範囲外座標・不正色、別cwd、package起動、起動時に一度だけ読込、欠落・破損時の終了2を確認した。HTTPは既存HTML、初期状態、着手、パス、終局、指定なしの通常経路、欠落・破損時の500と次要求での再読込を確認した。

最初の関連回帰では巨大なpytest IDがWindowsの環境変数上限を超え、別の異常系では親子の標準エラーの文字コードが食い違った。テストのIDと文字コード指定を直した。最初の参考2局では、ハーネスが割り当てる非計測のunknown予算を子が拒否した。その失敗を保存し、同設定を受け入れる回帰を加えた。明示された探索予算は拒否し、実験用経路のモデルロード失敗はstderrと終了2で報告する。

## Phase 6.5とPhase 7への引き継ぎ

盤面・手番から `NtupleModel.features` の `(weight_id, count)` を取り、`logit` と `value` を同じモデルで呼ぶ。教師ラベルは黒勝ち+1、白勝ち−1、引き分け0。白番でも符号は同じ。これは観測結果であり、完全読みでの局面価値とは区別する。教師あり学習の初期候補は二乗損失 `(V−y)²/2`。学習側で目的関数と更新を管理し、勾配には `(1−V²) × count` を使う。Phase 7の最初の実装では、パスを含む後続状態・終局報酬とTD(0)の目標を定め、少数重みの更新を手計算・有限差分と照合する。モデル保存は同じ互換定義を使い、学習時の来歴を別項目に書く。

配布ZIP内のpickleと展開済みpickleの実bytesは一致する。形式見本は黒白交互の座標、パス `(-1,-1)`、黒視点の最終石差を記述する。実件数・生成元・対局者の棋力・ラベル・偏り・ライセンスは未確認。Phase 6.5の最初に原本と出所を監査し、安全に解釈した棋譜を独立refereeで再生して終局石差まで確認する。同一対局、重複、D4同値を同じ群へ入れてから対局ID単位で分割する。近似序盤・対局者・生成元・ラベル比率を照合し、train／validation／test間の漏洩を検査する。Phase 0のheld-outを学習・調整には使わない。

## 品質・保全と証拠

初回Fullは、READMEと開発計画に報告書へのリンクを先に置いたため、リンク先の存在検査で失敗した。初回runを保全し、本文とリンクをそろえた。リンク単体回帰の成功後にFullを再実行し、終了0・必須11工程PASS、pytest 1,770成功・独立smoke 1成功、失敗・error・skip各0を確認した。strictは22ファイル。pytest工程は1,184.27秒。57対象の開始・終了・現在SHA-256と原証拠publicationを照合した。

WindowsのCPython 3.7.9、3.8.10、3.9.13、3.10.11、3.11.9、3.13.5の6版で、直接起動、packageからのfixture読込、推論logit、再保存bytesを比較した。通常Rangerは元の作業ツリーと専用worktreeで同じseed・同じ相手の着手を使い、黒番・白番各1局の全着手、盤面、結果が一致した。独立refereeと共通の固定資産18ファイル、元の提出資産10ファイルのSHA-256を開始時と終了時で照合した。提出ZIPは `34dd1283b844928f12862d8791a1a4cccf1f67864a7a87c8da8d1f2d1869f050`。元のmanifestとZIPの全5メンバーの実bytesを照合した。
