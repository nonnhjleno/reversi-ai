## 2. 探索方式と高速化

Minimaxは自分と相手の最善応手を交互に選ぶ。Negamaxは同じ二人零和探索を手番視点の符号反転で表す。同じ深さ、葉評価、パス・終局規則であれば、正しいAlpha-Betaと全幅Minimaxは同じ根のminimax値を求める。違いは枝刈りによる探索量で、同点時の着手は別途規定する。反復深化は完了した浅い探索を次の着手順や期限時の応答に使う。PVS／NegaScoutは有望な最初の手を通常窓で、後続を狭い窓で調べ、必要なときだけ再探索する方式である。最初の手の順序が悪いと再探索費用が増える。連続値では整数用の `alpha+1` を流用せず、比較可能な値域と境界を先に定義する。

[Egaroucidの技術解説](https://www.egaroucid.nyanyan.dev/ja/technology/explanation/)は、作者の実験を踏まえたminimax系統の選択、Alpha-Beta系のNegaScout、着手順、置換表、ビットボードと終盤の完全探索を説明する。実装や比較条件の異なるRangerに、そこでの速度や方式の優劣を外挿しない。Rangerは現行Alpha-Betaを主力として、次を一項目ずつ比較する。

### 置換表とキャッシュ

| 仕組み | 入力 | 保存内容と寿命 |
|---|---|---|
| ハッシュ | 盤面と手番などの状態 | 検索用の番号を計算する。衝突はあり得る |
| 置換表（TT） | 状態・探索条件 | 探索した深さ、値の境界、最善手候補、世代。探索中に上限内で置換する |
| 評価キャッシュ | 状態とモデル・設定ID | 静的な葉評価だけを保存。モデル変更で無効化 |
| Opening Book | 局面全体と手番 | 事前に計算した着手候補と根拠。独立した版を保存 |
| ライン表 | 符号化した1ライン・手番・必要なら着手位置 | ルールや特徴量の局所計算済み結果。対局過程には依存しない |

最初のTTは1手の反復深化で共有する小さな固定上限の表とする。キーに色付き盤面と手番を含め、ハッシュで添字を求めた後、盤面・手番の一致でヒットを確認する。パス時は手番を切り替え、直前パスが終局判定に必要な表現ではその情報もキーへ入れる。局面IDにはZobrist方式（石色・マス・手番の乱数値をXORし、着手・反転・パスで差分更新）を候補とする。差分の値は毎回再計算した値と照合する。[Zobristの原論文](https://journals.sagepub.com/doi/10.3233/ICG-1990-13203)・[Egaroucidのハッシュ用コード](https://github.com/Nyanyan/Egaroucid/blob/main/src/engine/hash.hpp)

EXACTはその探索条件で確定した値、LOWERは真値の下界、UPPERは上界。探索開始時の有効な窓で登録種別を決める。検索では深さ・終局解法の種類・採点規約・モデルID・探索設定を照合する。初版の固定深度同値検査では同じ残り深さに限定し、条件が違う場合は合法と確認した候補手だけを順序付けに使える。より深い近似値の流用は固定深度探索の意味を変え得るため、別実験とする。未完了探索は登録しない。完全解と近似を混在させない。置換は空き、古い世代、浅い項目を優先して検討する。例えば4,096枠×32 Bなら生配列128 KiBで、完全キーを含むレイアウトやPythonオブジェクトのRSSは別途測る。衝突をわざと発生させ、モデル交換、同一盤面の逆手番、上下界の誤用、パス、早期終局を回帰させる。

| Move Ordering候補 | 初期の比較と費用 |
|---|---|
| 直前の反復深化の最善手、TTの候補手 | まず個別に試す。候補手の合法性を照合し、TTの値を使う効果と順序だけの効果を分ける |
| 隅、位置重み | 着手位置の参照だけで既存順序に追加できる。順位付けと同点規則を固定する |
| 相手の合法手数、潜在的合法手数 | 子局面の合法手生成や隣接空きの計算が必要。順序計算込みの時間を測る |
| 軽量の順序専用評価 | 葉評価を共通にし、追加評価の費用に見合う枝刈りがあるか測る |
| 終盤の空き領域の偶奇 | 局所的な着手順の目安。領域計算費用と終盤に限定した効果を測る |

Phase 9-Cでは直前の完了反復の主変化から内部の合法手を優先する方式を単独で試した。701の固定D5では訪問ノード数が71,031から69,593になった。固定D5の対応時間の中央値は2.3%増加した。対局への進行条件は未達だった。未達項目は「701の固定D5で対応時間の中央値を10%以上短縮」。事前登録に従い、開発用の先後交換smokeと24局対局は開始していない。固定局面の実プロセス試験は完了した。次の優先候補は盤面処理の高速化の計測。次は現行実装で合法手生成・反転・盤面コピーの時間を測る。負担が確認できた処理について、同じ探索値と合法手を保つ盤面表現を独立比較する。[Phase 9-C実行報告](reports/20261127_phase9c_ordering.md)

### MCTSの比較条件

MCTSは訪問と価値の統計を使って次に調べる手を選ぶ探索方式。最初はUCTで、平均価値と訪問の少ない手への加点を使う。末端をロールアウトで終局まで指す方式と、同じ凍結n-tupleで葉を評価する方式を分ける。policy/value版では方策が探索の事前確率、価値が葉の見積もりを与え、PUCTで事前確率と訪問数から探索を配分する。別の方策モデルは後段とし、葉評価を手番側に直した上で合法手後の値からsoftmaxを作る案も比較する。局面や結果の手番視点を固定し、パスを含む辺の符号、訪問数での最終選択と同点規則、終局の確定値、最低1合法手の確保と打切りを検査する。[UCT原論文](https://link.springer.com/chapter/10.1007/11871842_29)・[AlphaZero原論文](https://doi.org/10.1126/science.aar6404)

先生の「探索する場所を人が決める」という案は、隅などによる初期順位、訪問とともに弱まるProgressive Bias、候補を段階的に増やすProgressive Wideningとして試せる。合法手の少ない盤面では後者の効果が小さい可能性がある。証明のない手の恒久除外には、唯一の勝ち手を落とす危険がある。既定は全合法手を対象とし、優先順位のみを変える。100・1,000シミュレーション程度で時間とRSSを測り、木はノード上限で制限する。同じデータ・重み・序盤・実行環境・外部期限のAlpha-Betaと比較し、シミュレーション数とAlpha-Beta訪問数は別指標とする。Policy/Valueを別学習した場合はモデル容量・生成費用も報告する。単一実験の結果は評価した構成に限定する。[Progressive Bias](https://cris.maastrichtuniversity.nl/en/publications/progressive-strategies-for-monte-carlo-tree-search/)・[Progressive Wideningの公開論文](https://www.remi-coulom.fr/Amsterdam2007/icgaj.pdf)

## 3. 盤面・ライン表、Opening Book、終盤

### 盤面表現とライン表

縦・横・斜めの最大8マスを、空き `00`、黒 `01`、白 `10`、短いラインの盤外 `11` として符号化する。8マス16bitの添字空間は65,536状態。例えば盤外は短いラインの端の詰め物なので、全組み合わせが有効になるわけではない。盤外を長さで管理する3進数表なら、長さ8で6,561状態。走査方向と上位ビットの対応、短い対角線の位置、辺越えの禁止を固定する。

| 65,536エントリの単表 | 生データ |
|---|---:|
| 1 B/entry | 64 KiB |
| 2 B/entry | 128 KiB |
| 8 B/entry | 512 KiB |

例えば両手番×8着手位置×1 Bの反転マスクを別に持つと、同じ表の単純な密配置で1 MiB。方向別に状態表を複製するか、盤面への対応だけを別管理するかで容量が変わる。普通のPythonのlist・int、テーブルの生成中の領域、対応表、プロセス起動時の読込も実測する。bytes、array、memoryviewも候補にし、状態数をバイト数と読み替えない。

入力を符号化したライン、手番、着手位置とし、空き位置の合法マスク、着手時の反転マスク、石数や特徴量、差分更新情報を必要な表に分ける。4軸それぞれの両方向を盤面座標へ戻して統合する。1ラインだけで全合法手や全反転を求めない。比較は現行Board、2つの64bit論理マスクによるbitboard、ライン表、両者の併用。Python整数の実メモリは2×8 Bのデータ表現とは別に測る。D4、8方向、隅・辺・短い対角、パス・連続パス、全滅、早期終局、合法な生成局面、着手／取り消しと対局結果を独立refereeで照合する。Perftはパスを深さに数えるかを明記し、同じ規約で既存実装・独立オラクルと一致させる。盤面単体の速度差を探索・実対局でも検証する。[EgaroucidのビットボードとPerft](https://www.egaroucid.nyanyan.dev/ja/technology/explanation/)

Phase 9-Dの計測で701の固定D5に占める盤面処理は44.2%、Bitboardによる固定D5の短縮は51.6%だった。次の優先候補はBitboardからn-tupleの葉評価を直接計算する方式。行変換を含む全体の速度を比較し、評価の意味とLUT参照順序を保つ。[Phase 9-D実行報告](reports/20261127_phase9d_bitboard.md)

### Opening Book

初期4石からの石を置いた回数で8・9手を数え、パスを数えない。着手後の石数はそれぞれ12・13。Bookの最初の候補は局面全体と手番をキーにし、候補手、評価の視点・単位、生成エンジン・深さ／期限、出典、版とSHA-256を持つ。対称形を統合する場合は着手座標を逆変換し、必ず合法性を確認する。未登録、破損、候補が不正な場合は通常探索へ戻す。登録済み候補だけで決める方式と、探索順を優先するだけの方式は別の比較にする。

候補の出所はRangerの事前探索、強いAIの固定探索や対局棋譜、利用条件を確認した公開Book・定石。外部Bookのライセンスは学習データやコードのライセンスと別に確認する。まずオフラインで少数局面を作り、Bookなし・8手・9手・複数候補を一要素ずつ比較する。目安として10,000局面×32 Bなら単純な索引部分は約313 KiBで、候補や根拠、ロード現物は別に積算する。先後交換により登録内外の両方で勝ち点、命中率、検索・起動時間、Book外での通常探索と時間を測る。8～9手の事前計算は時間を節約し得るが、この深さではその後の逆転を排除できない。EgaroucidのBookでは、事前評価に加え計算レベルなども保持する。[Egaroucid Book詳説](https://www.egaroucid.nyanyan.dev/ja/usage/book/)

### 終盤完全探索

空き6・8を独立列挙で合わせる初期候補とし、次に10・12を計測候補にする。採用空き数は提出環境の難局面で、外部応答の安全余裕を含めて決める。終局の採点は授業仕様の最終石差を先に固定し、勝敗だけを解く場合は別の目的にする。片側に着手がなければパス、両側が打てなければ空きがあっても終局。厳密なAlpha-Betaを基本にし、TT、終盤の着手順、偶奇、確定石で得る証明済み境界、専用合法手生成は別々に追加する。中断時は直前の完了探索か合法な安全手を返し、厳密な完了と分けて記録する。空き数別の正答、最善手集合、解けた割合、p95・最大時間、メモリを測り、Bookの効果とは別に判断する。

## 4. 評価の意味と次世代モデル

評価関数は局面から数値を返し、MinimaxやMCTSはその値などを使う探索方式。勝率を出すことは必須ではない。現行Rangerのn-tupleは黒視点の `V(s)=tanh(f(s))` で、勝ち・引き分け・負けを +1・0・−1 と置く。これは原則として勝敗期待値（勝率−敗率）の尺度で、+0.6を勝率60%とは読まない。tanhの出力は有界な推定値であり、終局の確定結果より優先しない。

| 目標 | 利点と注意 |
|---|---|
| 黒視点の勝敗期待値／手番側の勝敗期待値 | 既存TDと揃う黒視点をPhase 8で保持。手番側に変換する場合は黒なら同符号、白なら反転。引き分け込みの勝敗期待値と勝率を区別 |
| 黒視点の最終石差／手番側の最終石差 | 大差と小差を区別でき、対応する教師を使える。範囲、空きのある終局の集計、手番を固定。石差を単に64で割っても勝敗期待値にはならない |
| 任意の形勢スコア | 手作業の特徴量を比較しやすい。絶対的な勝率や石差と解釈しない |
| 勝率と石差の2出力 | 別々の教師を扱える。引き分け、損失比、探索でどちらを優先するか、較正を事前登録する |

Negamaxは葉評価の入口で黒視点を手番側へ一度変換し、親子の手番交替で探索値を反転する。黒視点のTD更新にはNegamaxの反転を持ち込まない。MCTSは木で一つの視点規約を定め、手番側の値ならパスも含めて親へ戻す際に反転する。手番別LUTは色交換だけで反対称とは限らない。有限な非終局値の尺度と終局勝敗・石差の優先規則を境界で揃え、欠損・非有限値、最大振幅、パス、白番を試験する。教師が手番側の値だけを提供する場合、絶対色の手番が復元できなければ、黒視点への変換は行えない。

### 最初の教師ありNN

先生の「3層・128次元」の厳密な意味は未確認。Rangerの最初の実験では隠れ層を3つと定義し、全結合MLPを `128 → 128 → 128 → 128 → 1` とする。これは[先生の助言](先生からのメモ/20261120.md)を出発点にした候補であり、この規模が最適かは比較で確かめる。

- 入力の前半64次元は手番側、後半64次元は相手側の石の有無を、双方ともa1からh8の行優先順で表す。空きマスは両方0。パスで手番が移れば2平面を交換する。回転・反転を使うD4拡張では2平面に同じ変換をかけ、教師値は保持する。拡張は分割を固定した後、学習用に適用する。
- 各隠れ層の初期候補はReLU。線形出力1値で手番側の予想石差を回帰する。教師は第5節Cの値とその由来を保持し、範囲と採点規約を照合してから、必要なら64で割る。正規化の有無はモデルに保存し、評価時に元の単位へ戻せるようにする。学習はAdamとMSEを初期候補とする。
- 探索が推定した石差と自己対戦で観測した石差は、来歴を保持して別々に誤差を報告する。石差の回帰出力を既存n-tupleの勝敗期待値や勝率に読み替えない。Rangerの黒視点に渡す境界では黒番なら同符号、白番なら反転する。Negamaxの葉が手番側の値を直接受け取る場合は変換を重ねない。終局では正確な勝敗と石差を優先する。
- この構造は重みとバイアスで49,665パラメータ、float32の生データは198,660 bytes（約194 KiB）。密な葉評価1回は49,280積和とバイアス・活性化を含む。入力変換も含めたCPU実測で葉評価の時間、探索ノード数・深度と提出環境での応答を測る。学習基盤にはPyTorchなどを検討し、実戦推論で必要なライブラリとCPUの互換性は別に検証する。差分更新を使うNNUEは独立候補とする。

### 配布102,400局の追加監査

「左上に偏る」は未検証。対局IDに沿って元棋譜を再生し、着手座標と黒石・白石の出現頻度を、色・手番・盤上石数・進行段階別に集計する。元の座標と各D4群の代表座標の両方で集計し、対称変換による見かけの偏りと、序盤の手順・戦略的な局面の偏りを区別する。接頭手順の種類と頻度、対局者・生成元の棋力と来歴、勝敗・石差分布、隅や可動性などの局面の特徴も比較する。生の重複とD4同値の重複を数え、同一対局由来の局面とtrain／validation／test間の漏洩を調べる。

CとDに共通する公式データ規約は自身の活動での利用を認め、再配布を禁じる。出典表記や連絡は作者の希望で、実験では取得日、配布URL、版、ハッシュを記録する。原データや元の行を復元できる派生物はGitへ入れない。派生物や学習済みモデルの提出・公開条件は事前に確認する。Egaroucidのコードに掲示されるGPLと、公開データの規約は別に確認する。[学習データ利用規約](https://www.egaroucid.nyanyan.dev/ja/technology/train-data/)・[公式リポジトリ](https://github.com/Nyanyan/Egaroucid)

新しい学習データは対局単位で分割し、由来の分かる同一棋譜やD4同値棋譜は同じ群に置く。対局IDのないCは確認できる由来単位と、手番相対のD4局面群で分ける。対局をまたぐ漏洩の有無を追えない場合は限界を報告し、独立性が必要な最終比較は別のデータで行う。実ファイルを監査するときは構文と採点、石数別の件数、D4正規化と重複率、元データ間の重なりを確認する。Phase 0のheld-outとPhase 6.5の凍結testは学習・最適化・モデル選択・Book作成に使わず、新研究の最終評価集合も開発開始前に固定する。許可済みの少数サンプルから読込・RAM・I/Oを見積もる。

Phase 7.1と7.2では学習局数に応じた一貫した棋力改善を確認できなかった。大型パターン、段階別評価、Adam、教師あり事前学習、TDに共通して、複数seed、途中checkpointと評価間隔、開発評価での選択規則、最終独立評価を事前登録する。学習終了時点を自動選択しない。事前学習による初期差、同一指標への到達時間、同じTD量での系列差を分けて記録する。

### Phase 7.2から残る学習仮説

Phase 7.2ではTD誤差と重みが変化したが、開発評価の棋力は一貫して上がらなかった。同じ1,872重み・オンライン半勾配TD(0)・α=0.0000625・ε=0.20・γ=1・1手選択のまま100万局以上へ延長することは既定計画から外す。次に自己対戦を行うなら、下表の仮説を検証するGoalを個別に作る。[段階開発・評価設計書のPhase 7.2](リバーシAI段階開発・評価設計書.md#phase-72zero-tdの50万局追加学習と節目評価)

| 未検証の仮説 | 比較する条件と見る指標 |
|---|---|
| 2・3-tupleの表現力が足りない | 同じ教師と分割で、大型パターンまたはNNとの段階別誤差、棋力、推論費用を比較 |
| 固定学習率で重みの変動が続く | 学習率の減衰だけを変え、重みの区間変化、TD誤差、飽和率、複数seedの棋力を比較 |
| 1手ε-greedyの局面分布や相手・初期局面が偏る | 探索付き自己対戦、過去モデルなどとの混合、初期局面の多様化を別々に試す。局面群の被覆と固定相手・独立評価への効果を測る |
| 勝敗報酬の情報が少ない | 採点を検証した終局石差の教師、強い教師による事前学習、TD(λ)をそれぞれ比較。出力尺度と終局優先の契約を明記 |
| 黒番・白番で分離した重みの学習特性が違う | 手番別の更新回数・誤差・重みの変化と先後別対局成績を測る。Phase 7.2の白番側の負け越しだけで原因を決めない |

## 6. 独立実験の開始条件と採否

実験は原則一要因。まず独立オラクルと共通品質ゲート、次に固定局面・開発序盤で費用と効果、最後に凍結候補を独立評価へ進める。初期例は開発用12ペアから開始し、ばらつき・予算に応じて拡張する。評価相手、先後、固定序盤の集合とseed、外部応答期限、機器、モデル・ソース・実行設定、算出する差・不確実性、停止条件を先に登録する。既存の正式条件は[ハーネス契約](harness_contracts.md)に従う。

| ID／段階 | 開始条件と最小変更 | 検証・評価と続行条件 | 中止・保留 |
|---|---|---|---|
| Search A／9 | Phase 8の比較元を凍結し、小容量のTTだけ追加 | 無効時と同じ深さの値、衝突・境界・パスを確認。代表局面でヒット率・時間と深さを測り、固定相手で効果を確認 | 不一致、メモリ超過、探索時間の改善なし |
| Search B／9 | 比較元とTTの状態を固定し、順序だけを一項目変更 | 最善手集合と同点規則、ノード・順序付け費用・同時間の到達深さを比較。効果が残る手法を選ぶ | 合法性・値の回帰、追加計算で相殺 |
| Search C／9 | 合法手・反転・評価の計測で盤面処理が支配的と確認 | Board／bitboard／ライン表／併用を単体で照合。Perft、実ノード時間と同時間対局に進める費用で比較 | oracle不一致、RSS・起動・移植の費用超過 |
| Search D／9 | 安定した通常探索とBookの出所・作成手順を固定 | 8手から開始。Book外と障害時に通常探索へ戻ることを確認し、9手・複数候補の増分を別計測 | 不正着手、期限超過、登録外や同時間の棋力悪化 |
| Search E／9 | 小空きの厳密オラクルと期限時の代替手がある | 完全解を全件照合し、空き数別に正答・完了率・最大応答を比較。採用は実機の安全余裕がある範囲 | 厳密値の不一致、最悪局面で超過 |
| Evaluation A／10 | Aモデルと既存splitを固定 | SGDとAdamの再開再現、同予算での誤差・時間・同時間棋力を比較。主要指標改善を別seedで確認 | 非有限値、再現不能、費用に見合う改善なし |
| Evaluation B／10 | 既存n-tupleとNNの対照条件、教師データの被覆と容量を見積もれる | 小数の大型パターンを追加し、共通教師で誤差・葉の時間・同時間の棋力を比較 | 誤差が下がっても同時間棋力が悪化 |
| Evaluation C／10 | パターンを固定し、各段階の教師が足りる | 段階なし、8、16、60を順に比較。空段階、境界、過学習、容量を測る | 段階追加で改善なし、ラベル不足 |
| Evaluation D／11 | 出典・規約・ラベル・重複を監査できる教師がある | 同量でデータ源だけ、同源でデータ量だけを変える。段階別の誤差と独立した棋力を比較 | 規約・由来・ラベル不明、漏洩、費用超過 |
| Evaluation E／11 | 教師ありモデルの初期性能と探索統合後の性能を確認 | 学習率・方策・教師信号を個別に変え、複数seedで初期差・到達時間・途中checkpointを比較 | 初期差しか説明できない、独立対局で利点なし |
| Evaluation F／12候補 | 優先候補で残る課題と比較費用を説明できる | 差分更新型NNUE、KPP型、分類／回帰木を各々同じデータ・時間で比較 | Python実機での負荷超過、棋力改善なし |
| Search F／12候補 | αβ比較元と既存モデル、木の予算を固定 | UCT／凍結値／事前方策を個別に比較し、安全応答と同時間のペア勝ち点を検証 | 予算・RSS・応答安全性が不適合、優位不明 |

### NN-A〜Eの開始・続行条件

新規自己対戦を最初の教師あり学習の開始条件にしない。各段階で対象局面数、学習seed、設定・資源予算、停止条件、checkpoint選択規則を事前登録する。前の小規模なデータ集合を含む決定的な部分集合を用いる場合は、全規模で同じ分割と監査手順を保つ。

| 段階 | 開始条件と作業 | 続行・保留の判断 |
|---|---|---|
| NN-A 約100,000局面 | 利用条件、ラベル、重複と分割を監査。読込、手番側2平面、D4、パス、学習と推論の一致、保存・読込と学習再開を検証 | 独立した手計算局面と再開で一致を確認し、条件と必要費用を保存。教師の意味や漏洩が不明なら保留 |
| NN-B 約1,000,000局面 | NN-Aを通過後、同じ設定の複数seedでAdam。validationでcheckpointを選び、誤差・決定的な1手選択の棋力・単一局面のCPU推論速度を既存n-tupleと比較 | 予測誤差、棋力、速度を別々に評価。荒い予測精度だけで規模を増やさない |
| NN-C 10,000,000局面から全体へ | NN-Bで有望な場合に限り、局面数を増やして誤差・棋力・計算費用、段階と教師由来ごとの差を測る | 10,000,000局面の結果を確認してから全体利用を決める。費用に見合う改善がなければ止める |
| NN-D Alpha-Betaの葉評価 | 有望な教師ありモデルを凍結し、Phase 8で定めた評価と安全応答の契約に接続 | 手作り・n-tuple・NNを同一時間で比較。固定深度で値を検証し、同時間では棋力、探索ノードと深度、葉のCPU時間、起動・メモリ・依存関係を測る。独立評価で採用を判定 |
| NN-E 自己対戦による追加強化 | 教師ありモデルの性能を確認後、学習率、探索方策、教師信号を一つずつ変える対照を設計 | 事前学習時点と追加学習後を同じ相手で比較。複数seedと途中checkpointを確認し、従来のTD(0)をそのまま長期移植することを前提にしない |

### 教師データとモデル構造の比較

| モデル構造 | 教師データ | 比較の役割 |
|---|---|---|
| 既存n-tuple | Phase 6.5の配布102,400局 | 既存勝敗モデルは履歴上の対照。データ源だけを比べる実験では、終局盤を再生して整合する石差規約を登録できる場合に同じ回帰課題で作る |
| 既存n-tuple | Egaroucidの評価値付き局面 | 石差回帰の共通対照。上の行と比べる際は、実測終局ラベル層、局面数・段階・手番の分布を揃える |
| 大型n-tuple | Egaroucidの評価値付き局面 | 同じ教師、分割、局面数で配置とサイズの効果を測る |
| 3隠れ層×128 NN | Egaroucidの評価値付き局面 | 同じ条件で表現力と速度を比較。必要なら配布棋譜で学ぶNNを追加の対照にできる |

公開データで絶対色を復元できない行では、現在の黒視点・手番別checkpointを石差回帰に流用しない。既存と同じ配置を持つ手番相対の比較モデルを別設定で定義し、二つのデータ源でその設定を揃える。同じラベル、split、サンプル数、seed、最適化の予算、対戦条件を揃えられる範囲を事前に示す。実測石差と探索評価の差、勝敗期待値と石差の出力差、葉の推論速度と探索の効果は別々に報告する。統制できなかった比較から教師と構造の寄与を断定しない。

### 測る項目と停止基準

勝ち点率と同じ相手への対応差、先後別結果、ペア単位の不確実性、学習seed間の分布を報告する。タイムアウト、不正手、通信・プロトコル異常、ロード失敗と代替動作を個別に数える。時間は起動、全通常応答、全genmove、内部探索、葉評価1回を区別し、p95・最大と外部期限を併記する。メモリは配列の計算値、モデル／Bookファイル容量、ピークRSSを分ける。探索深度は完了した深さ、ノード数は既存の計数定義に従い、NPSの分母は測った内部探索秒とする。Bookの命中率は検索対象着手に対する合法な採用候補の有無、TTは照合済みヒットと枝刈りに使えた件数を別に、完全探索は試行局面に対する期限内の厳密解の割合を報告する。

事前に事実上の最小改善幅、試行費用上限、メモリ・最大応答の上限、異常を見たときの停止条件を定める。誤判定や不正・期限超過は修正するまで次に進めない。NPSやMSE／MAEの改善は次の試行を検討する材料であり、提出採用は同じ外部条件での棋力・実運用の適合・品質の証拠で判断する。時間と安定性への余裕を失う候補や、必要な効果が確認できない候補は基準版を残して保留する。

## 7. Raspberry Pi 4の試験基盤

PiではLinux／ARMの動作確認、小規模な固定相手評価、定期テスト、証拠の保存・参照、進捗ダッシュボードから始める。長期自己対戦はWindowsとの小さな共通計測で局/秒・温度とスロットリング・ピークRSS・消費電力・ディスク容量を確認してから計画する。Caddy、PM2、Tailscaleとポート、CPU、メモリ、ストレージを共用する場合は既存サービス優先で負荷上限を設ける。大規模な教師あり学習、重いモデル学習、コード開発は当面Windowsを中心とし、提出環境に近い評価は対象機器・契約を別に確認する。Piの性能や提出環境への適合は未計測。
