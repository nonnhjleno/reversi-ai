## 1. 基本設計と変更する場所

固定した序盤母集合からケースを選び、その序盤からA黒/B白、A白/B黒の2局を実行する。この2局を1ペアとし、ケースID、ペアID、乱数シード、探索予算を双方の対局と比較JSONに持たせる。統計もこのペアを単位にする。重複除去した局面を、未知の序盤分布からの独立同分布標本と決めつけない。

「同じ実験条件か」「正常な対局か」「予算を守ったか」「統計的に何を推定できるか」を別々に検査し、最後に採用条件として組み合わせる。動作確認、正式な強さ評価、時間制限下の実用評価は区別する。

既存の通信・ルール照合を再利用し、課題の標準入出力コマンドは維持する。

| 対象 | 追加する責務 |
| --- | --- |
| `harness/openings.py`（新規） | 固定序盤母集合の生成、保存、検証、対称重複の判定、非復元抽出 |
| `harness/search_budget.py`（新規） | 探索設定の検証・正規化、AIへの設定伝達、テレメトリの検査 |
| `harness/statistics.py`（新規） | 完全なペアの検査、有限母集合の平均に対する区間、前後差の計算 |
| `harness/evaluate.py` | 序盤の同期、手番の引継ぎ、ID付与、v2 JSON、厳密な比較条件 |
| `harness/protocol.py` | 必要な評価用環境変数の受渡し。既存の期限とstdout検査を保つ |
| `tests/test_harness.py` | 既存の再現性・比較・異常テストを拡張。固定fixtureも追加 |

設定伝達は環境変数を使うので、現在の `seeded_player.py` が対象スクリプトの引数をリセットする構成でも使える。AIがその設定を利用する処理は、今後の探索AI側に実装する。環境変数を渡すだけで、既存AIへ探索上限を強制できると考えない。

### 1.1 実験ケースの識別規則

| 識別子 | ハッシュに含める意味上の内容 | 用途 |
| --- | --- | --- |
| `orbit_id` | 最終盤面の回転・鏡映正規化キーと手番 | 対称重複の除去。対戦ケースの一致判定には使わない |
| `case_id` | 初期盤面、実際の座標と色による序盤全履歴、パス、到達盤面、次の手番、ルール版 | 履歴と向きまで含む実際の開始条件 |
| `pair_id` | `case_id`、A/Bの各seed、先後交換方式の版 | 先後二局と変更前後の対応付け |
| `experiment_id` | 選択ケース集合、両AIのコード・モデル・正規化設定、予算、対戦処理版、実行環境 | 実験条件全体。候補AIを変えれば別ID |
| `run_id` | 実行ごとに発行する固有値 | 同一実験の再実行、失敗した試行の識別 |

`orbit_id` が同じでも、履歴や向きが違えば `case_id` は異なる。同じ盤面へ別の履歴で到達すると、乱数消費やキャッシュに影響する可能性があるためである。Aは候補、Bは固定相手という役割で、黒白の色名ではない。`pair_id` にはAIのコード・モデルhashを含めず、比較条件は別に照合する。二局は `leg=0` と `leg=1` で区別し、記録の主キーは `(run_id, pair_id, leg)` とする。

意味上の識別子は、既定値を明示した正規化JSONのSHA-256から生成する。正規化の版、UTF-8、キー順、数値表現、配列順を固定し、不正な数値を拒否する。日時、絶対パス、ログ保存先は意味上のハッシュへ含めない。コード・モデル・依存資産は内容hashで識別し、パスは所在情報として別に保存する。

### 1.2 再現性と変更前後の一致条件

プレイヤーのseedは、マスター評価seed・`case_id`・A/Bの役割・seed導出方式の版から生成する。同一ペアでA自身とB自身のseedを先後交換後もそれぞれ維持し、ケースの実行順や選択数から導出しない。序盤生成、ケース抽出、AI、探索的bootstrapの乱数系列は独立させる。Python以外の乱数源を使うAIは、そのseed設定方式も記録する。

変更前後を厳密比較するには、母集合hash、抽出ケース、履歴・向き・手番、seed、先後交換方式、固定相手Bのコード・モデル・設定、Aの予算と計測定義、対戦・判定処理版、必要な実行環境が一致することを要求する。CPU/OS/Python・依存パッケージ・スレッド数・同時実行数等を記録し、比較プロファイルごとの必須一致項目を固定する。OS負荷まで同じと保証しない。

Aのコード・モデル・探索設定の差は、意図した変更として一覧にする。Aの予算も変わった場合は同一予算比較を拒否し、明示的な記述的比較で「構成全体の比較」とする。`pair_id` の一致だけで比較可能としない。

対戦・同期・計測・判定の `evaluation_fingerprint` と、統計方法・信頼水準・解析コードの `analysis_fingerprint` を分離する。候補の実体は対象hashとして別管理する。初版の全harnessファイルhashの一括一致は、第8節の修正で責務別の一致判定に置き換える。解析だけが変わった場合は、必要な生データのある保存済みJSONから再計算できるようにする。

## 2. 固定した複数の序盤局面

### 2.1 8配置の母集合と評価用の抽出集合

初版の規模案は **初期盤面から合法に8個の石を置いたユニーク局面1,000個を母集合として固定し、200ケースを抽出して400局を評価する**。母集合サイズNと抽出ペア数nは別の設定として保存する。数値は初期実験案であり、400局で採用条件を満たす保証ではない。生成上限内で必要数を得られなければ、重複で埋めずに止める。

8回の配置と、パスも含む手番数を区別する。途中のパスは履歴に保存するが、8配置には数えない。生成中に終局した履歴は採用しない。

生成は `harness/referee.py` と専用の `random.Random(seed)` で行い、候補AIを呼ばない。合法手からの一様選択を繰り返すため、全ての到達局面から一様に選ぶ方式ではない。この生成分布をセットの説明に残す。

8配置に統一するのは、短い序盤で必要なユニーク数を得にくい場合があることと、序盤の長さが異なる結果を初版で混ぜないためである。後から4配置・12配置などを追加する場合は別母集合として評価し、必要なら別途層別の推定方法を定める。

### 2.2 保存形式

固定序盤JSONのformat_versionは1とし、次を保存する。

| 項目 | 内容 |
| --- | --- |
| `generator` | アルゴリズム版、Python版、生成seed、8配置という条件、試行上限、生成コードのSHA-256 |
| `purpose` | `development` または `held_out`。調整用と最終判定用を分離 |
| `rules_version` / `identity_version` | ルールと識別子の定義版 |
| `entries[].orbit_id` | 対称性正規化キーから作るSHA-256。重複除去専用 |
| `entries[].case_id` | 初期盤面・全履歴・実際の盤面・手番・ルール版から作るSHA-256 |
| `entries[].moves` | 色と座標の履歴。パスの座標はnull |
| `entries[].board` | 初期盤面から履歴を再生した結果の8行 |
| `entries[].to_move` | 最後の操作の次に来る色。合法手がなくても、その色を記録する |
| `population_hash` / `population_size` | 固定母集合の意味上の内容hashとケース数 |

読み込み時には保存盤面を信用せず、初期盤面から全履歴を再生して合法性、パス、盤面、手番、IDを検査する。パスは、その色に合法手がなく相手には合法手がある場合だけ受け入れる。両色とも手がない終局局面は、対局開始用の序盤として受け入れない。これは子プロセスを起動する前に行う。

生成ファイルを再現可能にするため、エントリ順序、合法手の列挙順、JSONの整形と改行を固定する。生成日時のような毎回変わる情報は再現用の内容へ入れない。同じコード・Python・seed・条件なら同じファイルを生成する。生成回数に上限を置き、必要なユニーク数が得られなければエラーで止める。

抽出manifestは母集合と別に保存し、母集合hash・N・抽出方式と版・抽出seed・n・選択した `case_id` と実行順を持つ。母集合の内容と選択内容は、対局結果を見た後に変更しない。

### 2.3 重複を除く

最終盤面に8種類の回転・反転を適用し、盤面の64文字と手番を連結したキーの辞書順最小値を使う。色交換は行わない。同じ盤面でも手番が違えば別状態。同じ状態に到達する別の履歴は重複として除く。

調整用と最終判定用でseedを変えるだけでは、局面の重複を防げない。セット間でも正規化キーを照合し、最終判定用の生成時に調整用のキーを除外する。手作業で選んだセットは、その選び方も記録する。

生成CLIには `--exclude-openings FILE` を追加し、調整用等の複数セットを指定できるようにする。入力セットを検証してから除外キーを読み、使用した除外セットのhashも生成条件へ保存する。

### 2.4 対局ループへの組込み

予定する追加引数は `--openings FILE` と `--selection-seed INT`。前者は固定母集合を指定する。正式評価では後者を必須とし、専用乱数系列で一様な非復元抽出を行う。選択ケースが同じなら、実行順が違ってもIDで対応付ける。

1. ケース一覧を確定する。指定がなければ、現在と同じ初期盤面からの評価を続ける。
2. 序盤1個につき必ず先後2局を割り当て、`case_id`、`pair_id`、役割番号0/1を付与する。
3. 各局でA/Bを独立して起動し、初期盤面を確認する。
4. 序盤の各着手を **両プロセスにplayで送る**。序盤はAI自身のgenmoveでは生成していないため、通常対局の「相手だけにplay」と処理を分ける。
5. パスでは盤面更新コマンドを送らず、独立判定と手番交代だけ行う。各配置後には双方の盤面を独立判定と照合する。
6. `to_move` から現在の対局ループを開始する。黒番から始まると決めつけない。
7. 序盤履歴とAIが選んだ着手を別項目に保存し、強制序盤の処理時間をAIの思考時間に含めない。

同じペアでは序盤、A/Bそれぞれのseed、探索設定を維持し、担当する黒白だけを交換する。各局は新規プロセスで開始し、前局のキャッシュを引き継がない。序盤同期中に探索・着手予測を行わない。パス時に盤面が変わらないことも照合する。

`--games` は2以上の偶数という制約を保つ。固定序盤モードで省略した場合は全母集合の2倍、指定した場合は `games / 2` 個を一様に非復元抽出する。正式評価では予定nを事前に固定するため `--games` も明示する。母集合を超える指定はエラーとし、同じ序盤を自動再利用しない。先頭n個を正式な無作為標本として扱わない。初期盤面モードの省略時は既存の2局を保ち、初期盤面だけの反復には正式な序盤区間を付けない。

### 2.5 完了条件とテスト

- 同じseedで同じファイル、重複・対称な重複なし、セット間の重複なし。
- 不正着手、偽のパス、手番違い、盤面改ざん、終局開始、ID改ざんを起動前に拒否する。
- 既知の合法履歴で再生盤面を確認する。期待盤面は候補AIから生成しない。
- 両AIが同じ開始盤面になり、パスを含む履歴でも開始手番を引き継ぐ。
- 同じ序盤の2局で役割が交換され、双方のseed・設定は一致する。
- 対称な盤面は同じorbit IDとなる一方、向きや履歴の違うケースは同じcase IDにならない。
- 同じ母集合・抽出版・seed・nで同じケースが選ばれ、重複なくN以下になる。
- ケースの並べ替えや選択数の変更でも、同じケースのプレイヤーseedが変わらない。
- 従来の引数なし評価は現在の動作を維持する。

## 3. AI内部の探索予算の記録

### 3.1 設定値・実効値・実測値を分ける

JSONには次の3つを分けて保存する。

| 区分 | 例 | 検査の意味 |
| --- | --- | --- |
| 要求設定 | ハーネスが渡した100ms上限 | 何を要求したか |
| 実効設定 | AIが読み込んで探索に使う設定 | 要求が受理されたか |
| 実測値 | search時間、ノード数、完了深さ、応答RTT | 今回の探索がどう動いたか |

自己申告と実測は、設定が必ず守られるという一般的な保証ではない。設定の受理、上限チェックの実装テスト、各着手の観測を組み合わせる。コード・設定・モデルのhashも残す。

予定する追加引数は `--a-config FILE` と `--b-config FILE`。初版の予算kindは `time`、`nodes`、`depth`、`none`。不明・未対応は `unknown` として記録し、noneと混同しない。不要な数値や未知のkind、非正値を拒否する。

設定例（AIは環境変数 `REVERSI_EVAL_CONFIG` を読み、traceを `REVERSI_EVAL_TRACE` へJSONLで出力する）:

```json
{
  "format_version": 1,
  "budget": {"kind": "time", "limit_ms": 100},
  "search": {"algorithm": "alphabeta", "iterative_deepening": true}
}
```

depthを上限にする場合はパスを除く配置数とし、試行した最大深さと完了深さを分ける。nodesなら根・葉・再訪・トランスポジション表参照を数えるか等を明文化し、`counting_definition_id` を持たせる。αβの探索ノード数とMCTSのシミュレーション回数を同じ単位として比較しない。同じ数値上限でも計算費用は等しいと保証しない。異なる探索方式の実用比較には時間予算を共通軸にするが、正式な区間の適用可否は別に検査する。

### 3.2 設定の伝達と記録経路

`Player` が子プロセスへ、絶対パスの `REVERSI_EVAL_CONFIG` と、対局ごと・プレイヤーごとに異なる `REVERSI_EVAL_TRACE` を渡す。探索AI側は設定を読み、対戦時だけ有効な開発用記録をJSONLへ出す。標準出力へ追加情報を流さず、web.pyの通常起動では既定設定で動く。

記録先はローカルの `evaluation_results/` 以下に用意し、既存ファイルと混ざらないよう実行単位のディレクトリを作る。最初に実効設定を記録し、genmoveごとに次を記録する。

- 当該プロセスの全genmove連番、要求phase、色、着手前の盤面hash、返した座標またはNG。
- `search_elapsed_ns`、`nodes`、試行最大深さ、`completed_depth`、停止理由。
- 初回モデルロード時間、モデル識別子、フォールバックの有無。

子プロセスはイベントをflushしてから標準出力へ応答する。ハーネスは同じ連番・色・盤面・座標のイベントを照合する。単にstderr末尾の数行を読む方式では、途中の記録欠落や誤対応を検出できないため採用しない。traceは終了時にまとめて精査し、必要項目を評価JSONへ統合する。

通常着手、パス応答、終局後のNG確認をすべて連番照合の対象にする。終局確認は `game.moves` にないため、その件数だけを期待ログ件数に使わず、Playerが実際に送った要求一覧と照合する。探索時間は単調時計で計測し、時計の種類・分解能・計測範囲の版も記録する。負値・非有限値を拒否する。

要求と実効設定が違う、イベントが欠ける・重複する、盤面や座標が違う場合は予算検証を不成功にし、原因を記録する。次局の実行や参考の勝敗記録は続けられるが、厳密な予算比較と採用判定は不可とする。モデルのフォールバックも、予定した学習モデルの採用試験を無効にする。

記録のない既存AIはunknownとして動作・対局評価を続けられる。現在のランダム版を探索なしの基準として使う場合は、コードhashと確認根拠を残し、事前に宣言した `baseline-asymmetric` の範囲でのみ予算適用除外とする。未知のAIを自動的にnoneや適用除外へ変換しない。対応していない既存AIにtime設定を付けて、実効100msと見せかけない。

### 3.3 時間計測と上限

探索時間には根の合法手列挙、盤面複製、探索内の価値推論、最終着手選択と代替手選択を含める。非同期推論は結果確定まで含め、計算をplay中やバックグラウンドへ移して予算から外さない。モデルロードは別項目だが、genmove中に行えば応答RTTには含まれる。traceの書込み・通信もRTTに含める。

外部応答時間は、送信直前から必要な全応答の受信までとする。起動・準備完了の確認は独立した期限と計測値を持たせ、起動確認後に通常のnameも測る。通常コマンド1秒・genmove10秒の監視を維持し、タイムアウト時には子プロセスツリーを終了する。GUIでは要求ごとの起動も別途評価する。

早期終了は許すが、内部時間予算Tに一律10msの超過を許さない。記録された探索時間がTを超えたら予算違反とし、AI側が安全余裕を持って停止する。nodesは消費数が上限以下、depthは試行最大深さが上限以下であることを検査する。内部予算を守っても外部期限に違反すればプロトコル失敗とする。

決定的な探索上限による評価では、時間経過を使って着手や探索量を変更せず、外部期限に達したら正常な代替手で成功扱いせずタイムアウトとする。全乱数源、並列実行、推論処理にも決定性が必要である。固定seedだけで決定性を保証しない。再実行一致テストは決定的fixtureに限定し、時間予算のAIには合法性・同期・期限・記録の一致を要求する。

思考時間は通常着手、パス応答、終局確認を分けて集計する。平均・最大値の対象は完了した応答と明示する。タイムアウトは通常の実測値として平均へ混ぜず、件数、期限、観測した待機時間を別に残す。

### 3.4 JSON比較で確認する条件

新しい比較には `equal-time` と `equal-work` の区分を持たせる。後者は「同じ計数上限」を意味し、同じCPU命令数や推論費用の保証ではない。

予定する `--budget-policy` は `descriptive`（既定）、`equal-time`、`equal-work`、`baseline-asymmetric`。前後で同じpolicyを要求する。equal-time/equal-workを明示した実験では、同一対局のA/Bの予算も一致させる。古いAIをそのまま対戦させる実験はdescriptiveで残し、同予算の証明として使わない。

- 変更前Aと変更後Aの要求予算・実効予算・検証方式が同じこと。Aの重みやアルゴリズムが違うことは許す。
- 固定相手Bのコード、モデル、設定、予算が同じこと。
- equal-timeでは時間上限が同じこと。equal-workではkindとカウンター定義も同じこと。
- 同じ対局内のA/Bも同じ予算なら、その事実を記録する。ランダム版と探索版などの非対称な比較は `baseline_asymmetric` と明示する。

同予算でもCPUの命令数や推論費用が等しいわけではない。学習の寄与を切り分ける実験では探索方式・設定も固定し、別の探索方式を比べる実験では同時間の結果を使う。

評価プロファイルは `smoke`、`descriptive`、`confirmatory`、`deployment` を予定する。smokeは少数局の動作確認、descriptiveは参考集計、confirmatoryは固定されたケース得点を前提にした正式な推定、deploymentは時間予算下の成績と期限・安定性の検査とする。confirmatoryは決定的な上限・動作を要求し、timeで探索量を変えるAIや決定性未確認のAIは正式区間の対象にしない。noneの基準AIは、固定seedでの決定性と明示的な適用除外が確認された場合だけ許す。

予算policyと評価プロファイルは別項目とし、未対応の組合せを起動前に拒否する。equal-timeはdeployment/descriptiveで用い、confirmatoryではequal-workまたは宣言済みbaseline-asymmetricを用いる。descriptive policyの予算未確認比較をconfirmatoryへ昇格させない。将来、非決定的結果に対する反復・推定モデルを定めるまでは、deploymentの成績に同じ正式区間を付けない。

`--compare` の既存の条件照合へこれらを加える。unknownを含む場合は、通常集計を表示できても `budget_comparable: false` とする。最終評価用には `--require-budget-verification` を追加し、未確認があれば成功終了しない設計とする。

### 3.5 完了条件とテスト

- A/Bで異なる設定が正しいプロセスへ渡り、元のシードとcwdを保つ。
- 設定の無視・既定値への置換、記録欠落・重複・応答との不一致を検出する。
- ダミーの探索AIで、異なる時間・ノード上限が実際の停止条件へ反映することを確認する。
- モデルロード、探索、通信を別項目にし、早期終了を違反扱いしない。
- 上限超過やフォールバックを検出し、厳密な採用判定を止める。
- 通常着手・パス・終局確認の全要求を照合し、思考時間の集計対象を分離する。
- 決定的な上限と時間予算のfixtureを分け、後者の棋譜差だけを再現性の失敗としない。
- 古いAIは予算未確認として動く。通常stdoutとGUI接続を維持する。

## 4. 先後交換ペア単位の信頼区間

### 4.1 まず得点とペアを厳密に定義する

各局のAの得点は勝ち1、引き分け0.5、負け0。同じ序盤の先後2局の平均をペア得点とする。

`pair_score = (score_A_black + score_A_white) / 2`

値は0、0.25、0.5、0.75、1のいずれか。例として1勝1敗なら0.5、1勝1分なら0.75。全ペアが正常ならペア平均は現在の勝ち点率と一致する。

ペアを作るときはindexの偶奇だけに頼らず、pair_id、case_id、seed、役割、予算を照合する。2局が揃い、A/Bの先後が一回ずつであることを検査する。欠けた局、同じ役割2局、重複ID、異常終了した局を捨てて、残りだけで有利な信頼区間を出さない。第5節の正式評価資格をすべて満たす二局だけが適格なペアとなる。

初版は母集合の1ケースにつき1ペアに限定する。初期盤面モードの反復や、同じケースの再実行を標本数へ加算しない。将来同じ序盤を複数seedで繰り返す場合は、ケース内反復とケース抽出を分けた推定モデルを定めてから拡張する。

### 4.2 推定対象と正式な区間

推定対象は「固定母集合の全ケースを、指定AI・設定・各ケースの固定seedで先後交換対戦させた場合の平均勝ち点率」とする。母集合の各ケースの得点が固定され、母集合を固定した後にnケースを一様に非復元抽出することが前提である。全合法局面、人間の実戦、未知の全相手への強さは推定対象ではない。

正式な初版は、有限母集合の非復元抽出に対応する保守的な境界を使う。n>=1、n<=N、点数範囲[0,1]、有意水準alphaについて、両側区間の半幅hを次とする。

```text
rho = 1 - (n - 1) / N                 if n <= N / 2
rho = (1 - n / N) * (1 + 1 / n)       if n > N / 2
h = sqrt(rho * log(2 / alpha) / (2 * n))
interval = [max(0, sample_mean - h), min(1, sample_mean + h)]
```

95%区間ではalpha=0.05なのでlog(40)を使う。対称重複の除去や生成の偏りは固定母集合の内容を決めるが、その母集合からの一様な非復元抽出という条件と混同しない。信頼水準は抽出手続きに対する保証であり、母集合平均が実行後に確率的に動くという意味ではない。

原典は Bardenet and Maillard, *Concentration inequalities for sampling without replacement*（2015）, Bernoulli 21(3), 1361–1385, DOI [10.3150/14-BEJ605](https://doi.org/10.3150/14-BEJ605)、[原論文のCorollary 2.5](https://arxiv.org/pdf/1309.4029)。片側境界を両側へ適用した式であり、本プロジェクトの母集合・得点・予算・採用規則そのものが論文に示されているわけではない。

全点数が同じでも、n<Nなら半幅は0にせず、点数範囲による上記境界を使う。n=Nなら母集合の全数評価であり、その集合の平均は既知となる。`population_census` として点数範囲内の一点を返すが、未知の局面や非決定的な再実行への不確かさが0という意味ではない。旧案の30ペア境界と `degenerate_sample` による一律nullは採用しない。小標本は幅の広い区間として扱うが、smokeには正式区間を付けない。

例としてN=1,000、n=200では半幅は約0.08595。点推定55%の区間は約46.4～63.6%となり、下限50%超を満たさない。保守的であることを明示し、標本数や判定方式は結果を見てから都合よく変更しない。

ペア欠損、予算違反・不明、非決定的動作、一様抽出の未確認、初期盤面のみの反復等では理由付きnullとする。選択済みの全nペアが適格でなければ、成功したペアだけを用いた正式区間を算出しない。

通常のペアpercentile bootstrapは、必要になった場合の探索的解析候補に留める。正式境界とは別のmethod・用途として保存し、採用条件を満たす方だけを選ばない。実装する場合はペア全体を再標本化し、専用seed・回数・分位点補間を固定する。時間予算による結果変動を、このbootstrapだけで自動的に扱えるとは考えない。

### 4.3 変更前後の差は同じペアで計算する

before/afterをpair_idで結び、各ペアについて `delta_i = score_after_i - score_before_i` を作る。推定対象は同じ固定母集合での平均改善量。差の範囲は[-1,1]なので第4.2節のhの2倍を半幅とし、区間を[-1,1]へ切り詰める。beforeのCIとafterのCIの端を引き算する方法は使わない。

母集合・抽出ケース集合・役割・A/Bそれぞれのseed・相手B・探索予算・計測定義・対戦条件が一致し、両報告の全ペアが適格であることを先に確認する。一致しない場合は厳密比較不可と理由を返す。元の得点・抽出manifest・評価条件が保存されていれば、解析方法や信頼水準だけを変える場合は再解析できる。ただし最終判定条件は事前固定し、判定の再解析履歴を残す。

比較結果には、点推定、95%区間、ユニーク序盤数、ペア数、先後別成績、異常数、予算検証の状態を添える。

### 4.4 採用判定との接続

CIを出す処理と、AIを採用する処理は分ける。自動コミットや自動採用は行わない。将来の採用レポートでは、対象コード・資産に対応した全仕様テスト成功、異常0、完全な序盤ペア、最終評価用データの適切な管理、予算確認を先に要求する。別途deployment評価の完走と時間上限遵守も確認するが、固定上限での成績のCIを時間予算下の強さの証明へ転用しない。

主要な判定を事前に一つ選ぶ。直接対戦なら勝ち点率55%以上かつCI下限50%超を初期の候補条件とする。同じ固定相手への改善量を主要な主張とするなら、平均差のCI下限0超を確認する。複数の区間・相手・候補を同時に正式な根拠へ使う場合は、有意水準の配分等を事前に定め、個々の95%区間を同時95%保証とは説明しない。CIがnullなら判断不能、有効なCIで基準未達なら条件未達と区別する。

少数スモーク、異常を除いた部分集計、探索予算未確認の比較、多数候補から偶然よい結果だけを選ぶ方法では昇格しない。母集合、候補と設定、抽出数、抽出seed決定手順、主要指標、信頼水準、判定条件を事前に固定する。合格まで対局を逐次追加せず、追加評価には別途事前計画が必要とする。

`purpose=held_out` だけで未使用性は証明できない。候補・設定の凍結記録、学習・調整との分離、最終結果を確認した時点、実施者の利用履歴を残す。before/after比較でも両版を最終結果を見る前に凍結し、beforeの最終成績を見てafterを調整しない。既に調整に使った集合を名前だけ変えて最終評価用としない。これらの運用履歴はハーネスだけでは完全に自動証明できない。

### 4.5 完了条件とテスト

- 人工的な勝敗fixtureで、1勝1敗=0.5、1勝1分=0.75等を正確に検証する。
- 正常な全ペアで、ペア平均と従来の勝ち点率が一致する。
- 既知のN・n・alphaで境界式を検算し、n=N/2付近の分岐と全数評価を確認する。
- 全勝・全引き分け・小標本でも、n<Nなら範囲境界に従う区間となる。
- 欠損、重複、異常局、予算不適格、非決定的モードで正式区間を拒否する。
- 前後の順序が異なってもIDで正しく対応し、不一致を拒否する。
- 変更前後のCI差ではなく、対応するペア得点差と範囲[-1,1]で区間を計算する。
- 解析のみの変更で再対戦せず再解析でき、履歴と判定条件の変更を区別する。

## 5. 失敗処理、JSONとCLIの互換性

### 5.1 状態を別々に持つ

| 判定軸 | 状態 | 意味 |
| --- | --- | --- |
| `game_status` | `complete` / `invalid` / `incomplete` | 独立判定による合法な終局、不正な対局、未完了 |
| `protocol_status` | `verified` / `failed` / `not_checked` | 応答形式、期限、同期、終局確認、quit等の検査 |
| `budget_status` | `verified` / `exempt` / `unknown` / `failed` | 予算確認、宣言済み適用除外、不明、違反・不一致 |
| `pair_status` | `qualified` / `unqualified` / `incomplete` | 二局と条件が揃い、正式評価資格を満たすか |
| `statistics_status` | `available` / `descriptive_only` / `unavailable` | 正式推定、参考値のみ、必要データ不足 |
| `decision_status` | `criteria_met` / `criteria_not_met` / `undetermined` / `not_requested` | 判定条件充足、未達、判断不能、対象外 |

適格なペアは二局ともgame=complete、protocol=verified、budget=verifiedまたは事前許可されたexemptで、識別・役割・設定の照合を満たすものとする。正式統計には、さらに全予定ペアの適格性、固定得点の前提と一様抽出の確認が必要。smoke/descriptive/deploymentでは完全な対局でも原則descriptive_onlyとする。

### 5.2 各種失敗時の扱い

| 事象 | 記録・判定 |
| --- | --- |
| 不正着手、不正なパス、盤面不一致 | game=invalid。正式な得点を付けない |
| 終局前のタイムアウト、異常終了 | game=incomplete、protocol=failed。自動的な負けや引き分けにしない |
| 余計なstdout、終局確認・quitの失敗 | protocol=failed。既に独立確認した終局結果は参考記録として保持するが、ペアは不適格 |
| trace欠落・重複・要求との不一致、要求設定の無視 | budget=unknownまたはfailed。missing/unsupportedと矛盾・違反をreasonで区別 |
| 探索上限超過、予定外のモデル・代替処理 | budget=failed。合法な終局結果でも正式な採用試験に使わない |
| ハーネス例外、保存失敗、環境障害 | infrastructure失敗として記録し、AIの敗北へ変換しない |
| 不正な設定・母集合・抽出manifest、未対応の条件 | 起動前に入力エラーで拒否する |

エラーにはphase、対象、要求連番、reason、直前の確認盤面を付ける。合法な終局結果と、その後の終了処理失敗を上書きし合わないようにする。継続可能な場合は予定された残りケースも記録し、継続不能なら未実行ケースを明示する。予算だけの失敗なら参考対局の記録を続けられる。

既存summaryの勝率・勝ち点率は、従来どおりプロトコル検査も含む正常完了局を分母とし、失敗を敗北へ変換しない。予算不適格を含む場合はsummary全体を参考値と明示し、正式な母集合推定と区別する。終了処理失敗後に残る終局結果は個別の参考記録に置き、正常完了数へ足さない。

予定局数・開始局数・正常完了数・失敗数・未実行数を保存する。失敗率の分母は開始局数と明示し、実行カバレッジも併記する。予定された一ペアでも不適格なら正式CIはnullとし、成功ペアだけの部分集計には件数と除外理由を付ける。

失敗ケースを成功するまで置き換えず、全試行を保持する。修正後の正式評価は別run_idで予定全体を再実行する。障害調査の部分再実行は可能だが、元の失敗を消して正式評価へ合成しない。

### 5.3 JSONの互換性

初版の評価JSONはschema_version=2であり、第8節の修正後はschema_version=3とする。現在の対象・環境・条件・games・summaryは残し、母集合と抽出manifest、各ID、開始局面、要求/実効/観測予算、判定状態とreason、統計の項目を追加する。ペア統計は別の `statistics` 項目に置き、method・推定対象・N・n・信頼水準・適用条件・解析fingerprintを保存する。タイムアウトや保存途中のデータも、成功報告と識別できるようにする。

v1 JSONは引き続き読み込めるようにする。ただし不足する予算や序盤を推測で埋めない。v1同士の旧方式の集計比較は残し、「予算未確認・ペアCIなし」を明示する。v1とv2の厳密な比較は互換扱いせず、v2で評価を取り直すよう理由を返す。

比較可否を一つのboolで過剰に保証しないよう、従来の `comparable` に加え、`budget_comparable`、`pair_statistics_available`、それぞれの理由を返す。対戦処理fingerprintが違う報告は厳密比較から除外する。解析fingerprintのみの差は明示的な同一方式への再解析で扱い、再対戦を必須にしない。

### 5.4 終了コードと実験成功

終了コード0は要求された評価プロファイルの処理・検証が正常完了、1は実行・検証・比較条件の失敗、2は入力設定の不正とする。smokeやdescriptiveで予算がunknownでも、当該プロファイルが検証を要求しなければ0で参考レポートを返せる。confirmatoryや `--require-budget-verification` では未確認・違反を1とする。

実験成功と採用判断は分ける。有効な実験で採用基準を満たさなければ、終了コード0のままcriteria_not_metとなる。smokeにCIがないことは失敗ではない。採用判断に必要なテスト・運用記録がない場合はundeterminedとし、対戦を実行しただけで全仕様テスト成功と報告しない。

CLIの引数は現行実装済み。confirmatory例は、両設定が同じ計数定義・上限を持ち、AIが決定的に動くことが前提。beforeも凍結済み候補を使い、afterと同じ母集合・抽出seed・games・評価seed・固定相手・予算で取得する。deployment例は実用評価の経路確認であり、それだけで時間予算下の優越性を統計的に証明しない。

## 6. 実装順序と最初の依頼範囲

1. ID・正規化・評価manifest・判定状態を共通契約として定義し、固定序盤母集合の生成・検証・抽出、同期、v2 JSONへ接続する。従来テストを保全し、1ケース×2局のスモークと10ケース×2局を確認する。
2. 探索予算の設定・計測範囲・記録・照合を、まず予算対応のテスト専用AIで実装する。決定的上限と時間予算、全genmove要求と通常思考時間を分けて検査し、異常系を各状態へ接続する。実際の探索基準AIへの接続は後のAI開発段階で行う。
3. 保存済みv2 JSONから、適格性検査・有限母集合の区間・対応するペア差・解析fingerprint・比較理由を実装する。人工データ、欠損・予算違反・全勝・全数評価・v1互換で検証する。
4. 決定的fixtureによるconfirmatoryと、時間予算fixtureによるdeploymentの経路を統合検証する。実AIが予算に対応するまでは参考評価に留め、本格的な採用試験を実行済みと扱わない。

初期の100ms、母集合1,000ケース、抽出200ペアという値は設定として保存する提案である。完了条件は数値だけでなく、履歴まで含む同条件で再実行・比較でき、欠損や未確認を成功扱いせず、推定対象と実用評価の限界を説明できること。

統合の受入れでは、(1) case/pair IDが序盤・予算・統計の全経路で対応する、(2) 合法終局とプロトコル・予算失敗が独立に保存される、(3) 一つの不適格ペアでも正式CIが止まる、(4) 全勝や小標本を都合よく除外しない、(5) 解析だけの変更で再対戦を要求しない、(6) 採用基準未達と実験失敗が別に報告される、(7) 従来CLI・stdout・GUIの互換性が保たれることを確認する。

## 8. 整合性精査で見つかった6項目の修正計画

作成日: 2026-10-09。状態: 修正実装前の具体案。今回の変更はこの計画書だけであり、以下の関数、形式、検査、テストが実装・実行済みであるとは扱わない。第7節は初版実装の記録として残す。修正後の版、既定値、比較・統計の資格について第1〜6節と解釈が分かれる場合は、この第8節を優先する。

### 8.1 六つの修正に共通する契約

- 処理順序を「実行条件の確定 → 証拠の収集 → 内容の検証 → 正式統計の適格性 → 区間計算 → 採用判断」に固定する。後段は前段の失敗・不明を成功へ変更しない。評価と保存JSONの比較・再解析は同じ検証関数を使う。
- 新規の `harness/contracts.py` に、型と必須項目、数値正規化、ID再計算、予定ケース・ペア・役割・seed・ログの照合を集約する。`harness/analysis.py` に適格性判定・再解析・統計的基準の判定を集約し、`harness/statistics.py` は検証済み得点に対する計算を担当する。別々の条件式をevaluateとcompareへコピーしない。
- 修正後の新規評価・解析報告は `schema_version=3` とし、`report_kind` で evaluation / analysis / comparison を区別する。予算設定とtraceは `format_version=2`、数値正規化は version=2 とする。序盤母集合format_version=1、case/pairのID定義とseed導出方式は現行のversion=1を維持する。
- 旧v1/v2報告は既存資産として残し、読み取れる既知の項目による記述的比較を維持する。欠けた証拠を推測で補わず、`budget_comparable=false`、正式CIなし、旧形式による未検証項目を理由として返す。比較範囲をlegacy_descriptiveと明示し、v3の検証済み条件照合と同じ保証を付けない。旧形式を修正版の正式評価へ昇格させるにはv3で再評価する。この移行時の再評価と、v3同士で解析方法だけを変える再解析を混同しない。
- 元のrawログ、要求設定、実効設定、取得時の判定と解析結果は上書きしない。再検証・再解析は入力報告のSHA-256と元の判定を参照する新しい結果として保存する。hashは内容の照合手段であり、発行者や記録の真正性を暗号的に証明するものではない。

| 評価プロファイル | 許可する予算policy | 実行・比較で必要な予算検証 | 正式CI | 採用への接続 |
| --- | --- | --- | --- | --- |
| smoke | descriptive / equal-time / equal-work / baseline-asymmetric | 明示的な要求がある場合 | 付けない | 対象外 |
| descriptive | 上記4種 | 明示的な要求がある場合 | 付けない | 対象外 |
| confirmatory | equal-work / baseline-asymmetric | 必須 | 全資格を満たす場合だけ | 別途品質・運用証拠が必要 |
| deployment | equal-time | 必須 | 初版では付けない | 期限・安定性の証拠のみ |

smokeでequal-timeを使うことは時間予算の経路検証であり、第3.4節の用途をこの表で具体化する。policyを選んだだけで予算をverifiedとせず、profileを選んだだけで固定得点の前提を証明したとも扱わない。決定性はコード・資産・設定hashに結び付いた事前の検査記録と宣言を要求するが、有限回の再実行だけで全局面の決定性を証明したとは説明しない。

### 8.2 修正1：比較時にも正式統計の適用条件を検査する

対象: `harness/evaluate.py`、新規 `harness/analysis.py`、`harness/statistics.py`、`tests/test_harness.py`。

`assess_statistical_eligibility(validated_report)` を唯一の適格性判定とし、判定値と理由一覧を返す。条件は、修正版報告の内容検証、confirmatory、許可された固定探索上限policy、双方の決定性の検査記録、検証済み母集合と非復元抽出、予定全ケースの完全な先後交換、各局の合法終局・プロトコル検証・予算検証である。Bのnoneは修正3で許可された適用除外だけを受け入れる。

`evaluate` が単独の区間を出す場合も、`compare_reports` が前後差の区間を出す場合も、この判定を通す。比較ではbeforeとafterの双方が適格で、修正2の条件照合も成立した場合だけ `paired_difference` を呼ぶ。統計モジュールへ未検証のJSONを直接渡す経路を作らない。

smoke/descriptive/deploymentの正常データは `statistics_status=descriptive_only`、CIはnull、統計的採用基準はnot_requestedとする。資格を求めたconfirmatoryでデータ・予算・固定得点の前提が不足した場合はunavailableと理由を返す。診断用の得点差は記述的参考値として表示できるが、正式CIの欄へ入れない。

有効なCIの基準未達と実験失敗を区別する。品質・最終評価用データの運用証拠が不足した採用判断はundeterminedとし、数値基準を満たすだけでcriteria_metにしない。候補の自動採用・コミットは行わない。

受け入れテスト: deploymentかつtime・deterministic=false、予算verifiedのsmoke、descriptiveをそれぞれ自分自身と比較しても正式CIが出ない。confirmatoryの正常ペアはCIが出る。欠落一局・欠落一ペア・予算不適格・決定性未確認のいずれでも全体の正式CIが止まり、成功ペアだけの区間を出さない。

### 8.3 修正2：実験条件を実データから照合し、予算検証要求を比較にも適用する

### 8.4 修正3：予算traceを型・意味・要求対応の三段階で検証する

対象: `harness/search_budget.py`、`harness/protocol.py`、新規 `harness/contracts.py`、`tests/fixtures/budget_player.py`、`tests/test_harness.py`。

設定の読み込みではJSONの型、対応する版、kind別の必須項目と不要項目を確認する。既知の旧設定v1は明示的な変換で要求設定v2へ移行できるが、欠けた計測定義・確認記録を推測で補わない。元ファイルと変換版・正規化設定を保存する。bool、NaN、Infinity、非正値を拒否する。nodes/depthの上限は整数に正規化し、100と100.0は同じ値・hash、100.5は不正とする。time入力のlimit_msは十進数として整数nsに正確に換算し、同じ時間は同じ意味上のhashとする。nsより細かく換算不能な入力を丸めて受け入れない。trace中のノード数・深さ・経過nsは非負の整数を要求する。

`none` は上限を検証するkindではない。Bに対するbaseline-asymmetricの事前宣言、対象コード・資産hash、理由と確認記録が揃った場合だけexemptとする。その他のnoneはtraceがあってもunknown。対象hashの不一致が起動前に判明した場合は入力エラー2とし、実行中の実効設定やモデルの不一致はbudget=failedとする。equal-workのnodesと、baseline-asymmetricの候補nodesには同じ必須の計数定義IDを要求する。

trace v2の先頭はobject型のheaderとし、run/pair/leg/player、要求設定hash、対象hash、実効設定、時計と計測範囲の定義、初期モデル情報を検証する。genmoveの各objectは全要求の連番、phase、色、着手前盤面hash、応答、計測値、停止理由を持つ。初期モデルロードと要求内のロード時間を別に記録し、各要求で使ったモデルID、フォールバックの有無・理由を照合する。モデルなしは明示的なnullとし、未記録をモデルなしと推測しない。

phaseはハーネスが決めたnormal_move / pass_probe / terminal_probeと照合する。通常着手・パス・終局確認すべてをPlayerの要求ログで照合し、モデルロード・trace書き込み・通信はsearch時間と応答RTTを混同しない。通常思考の平均・最大と、全genmove要求の平均・最大を別々に保存する。

深さは `0 <= completed_depth <= max_depth_started` を検査し、depth予算ならさらに `max_depth_started <= limit_depth` を要求する。片方だけの深さ記録は不正とする。time/nodesでも記録された深さの内部矛盾は受け入れない。通常コマンド1秒・genmove10秒の外部期限監視は独立に維持する。confirmatoryで外部期限を理由に探索量を変えたフォールバックは正式評価に使わない。

trace欠落はunknown、object以外のイベント・構文不正・必須項目不足・重複・対応不一致・設定無視・上限超過・予定外モデル/フォールバックはfailedとし、理由、イベント位置、要求連番を残す。未知のtrace版はunknownとして対応不足を示す。型不正のnullや配列を `.get` へ渡さない。検証を安全な境界で行い、既知の不正データは結果として返す。予期しないハーネス例外はinfrastructure失敗とし、AIの敗北へ変換せず部分記録を保存する。

予算失敗は既に確認した合法終局や得点を消さず、game/protocol/budgetを独立に残す。可能な範囲で予定残りケースを続ける。none・自己申告trace・hashだけでAI内部の正しさ全般を保証せず、コード確認と対象hashに対応した計測テストも必要とする。

受け入れテスト: none未承認、正しい適用除外、対象hash不一致、深さ2/完了999、各上限の超過、null/配列/文字列、欠落・重複、実効設定無視、予定外モデル・フォールバック、全phaseをfixtureで検査する。一つの壊れたtraceでバッチ全体の結果が失われないこと、予算失敗と合法終局が共存することも確認する。

### 8.5 修正4：traceを対局ごとに分離し、検証可能な証拠を残す

対象: `harness/evaluate.py`、`harness/protocol.py`、`harness/search_budget.py`、新規 `harness/contracts.py`、fixtureとハーネステスト。

出力JSONの隣に `runs/<run_id>/` を排他的に作り、その下の `<pair_id>/leg-<0|1>/<A|B>.jsonl` を各プロセスのtrace先とする。パスはlegループ内で決め、別legや再実行で同じファイルを使わない。意味上のpair IDにrun ID・絶対パスを加えず、ファイルの一意性と実験条件の一致を分ける。

要求設定、母集合全体、抽出manifest、raw trace、要求phase付きコマンドログ、決定性・適用除外の確認記録を保存する。対象・モデル資産は既存asset記録でhashを固定し、証拠を参照する。解析に必要なraw traceと母集合は保存済みJSONを後で読む場合にも必要であり、一時フォルダ終了時に削除しない。

報告にはrunディレクトリからの相対パス、ファイルSHA-256、形式版、存在状態、実効設定・観測値・失敗理由を保存する。relative pathと保存先は実験IDや比較条件のhashへ含めない。証拠がない場合は明示的なmissingとし、noneの許可済み適用除外ではtrace不要であることを別状態として残す。

保存JSONを読む側は、参照した証拠の存在・hash・版・内容を検査し、その結果で資格を再判定する。ファイルが欠けていても以前のverifiedをそのまま採用しない。元の取得時判定は履歴として保持し、現在の検証結果を別に返す。raw traceで記録する項目とsummaryへ転記する項目を固定し、失敗時も実効値を捨てない。

開始前に保存先の既存ファイル衝突を拒否する。予定ケース・局数を先に記録し、各leg終了時にcheckpointを残す。終了時にfinal reportを保存し、途中停止はpartialと未実行ケースを明示する。開始後の保存失敗はinfrastructure失敗1とし、保存可能なcheckpointとstderrに理由を残す。既存結果や他runの証拠を上書きしない。

受け入れテスト: traceを'w'で開くfixtureと'a'で開くfixtureの両方で先後2局がverifiedになる。別runのパスが重複しない。終了後にraw traceを再読込でき、実効設定・モデル・phaseが残る。保存ディレクトリ移動だけでは比較条件が変わらない。証拠の欠落・改変、部分停止、保存衝突で正式CIと終了コードが予定どおりになる。

### 8.6 修正5：対戦条件と解析条件のID・比較・履歴を分離する

対象: `harness/evaluate.py`、新規 `harness/analysis.py`、`harness/statistics.py`、新規 `harness/contracts.py`、`tests/test_harness.py`。

`evaluation_fingerprint` は対局・同期・外部計測・raw記録の検証・ルール・ID/seed導出に影響するコードと契約版を、責務別の明示リストから作る。全harnessファイルのglobで作らない。`analysis.py` と `statistics.py` は `analysis_fingerprint` にだけ含める。区間方法、信頼水準、推定対象、主要指標・判定基準を正規化した `analysis_spec` として分離し、対戦CLIからも計算・適格性・基準判定の実装をanalysisへ移す。

`experiment_id` は実際の母集合・抽出ケース集合・予定局数、seed、A/B実体・計算に使う設定、予算と計測定義、対戦fingerprintと必須環境から作る。confidence、CI方法、採用の閾値、過去の解析結果、実行順だけの違い、保存先や絶対パスを含めない。検証を要求したCLIフラグは取得要求の履歴として保存し、計算条件から分ける。フラグの必須判定は修正2で維持する。

再解析は入力報告を再検証してから、明示した共通analysis_specで実行する。元報告のconfidenceが95%と90%でも、対戦条件が同じで必要な証拠が揃えば、比較時に指定した同一水準で再解析できる。過去のCIの端を引き算せず、検証済みの対応ペア得点差から再計算する。

`analysis_id` は入力報告のhash、解析fingerprint、analysis_specから作る。結果に元のrun/experiment/analysis ID、入力hash、今回の方法・水準・理由を残す。解析だけの変更を理由に再対戦せず、新しい結果ファイルへ保存する。解析変更でseed・予算・予定ケース数・失敗記録を書き換えることは許さない。

運用上の採用計画は事前凍結する。変更後の解析は再解析履歴と探索的であることを明記し、過去の正式な採用判定を上書きしない。区間を別水準で計算できることと、結果を見て採用基準を変更してよいことは別とする。

受け入れテスト: confidenceだけの差、statistics.pyだけの差、analysis_specだけの差で対戦IDは変わらず、解析IDは変わる。異なる元の信頼水準でも指定した共通水準で比較できる。B・予算・計測定義・同期/ルール/seed処理の変更は引き続き対戦条件不一致となる。原JSONと既存解析を上書きせず、数値の独立検算・前後差・全数評価も保つ。

### 8.7 修正6：省略されたgamesと解決後の予定局数を区別する

対象: `harness/evaluate.py`、新規 `harness/contracts.py`、`tests/test_harness.py`。実装完了後に `ハーネス.md` と `docs/reports/ハーネス検証記録.md` を更新する。

argparseとPython APIのgames既定値をNoneとし、`resolve_game_count` で次の順序で決める。`games_explicit`、要求値、解決値、解決理由を別に保存する。

| 条件 | --games省略 | 明示指定 |
| --- | --- | --- |
| 初期盤面、smoke/descriptive/deployment | 既存どおり2局 | 2以上の偶数 |
| 固定序盤、smoke/descriptive/deployment | 母集合Nの2倍、全Nケース | 2以上の偶数、games/2 <= N |
| confirmatory | 起動前に入力エラー2 | 固定序盤と明示selection-seedも必須、2以上の偶数、games/2 <= N |

省略値は隠れた2局指定としない。smokeでも固定序盤の省略値は2Nであり、短い確認は `--games 2` を明示する。profile名だけで予定数を自動短縮しない。解決したN・n・局数を開始前に表示・保存する。母集合超過・奇数・非正値・bool等は起動前に拒否し、同じ序盤の再利用や成功ケースへの置換で埋めない。

予定ペア数nと局数2nを正式統計とcoverage検査の唯一の予定値にする。開始した試行数、合法終局かつprotocol verifiedの正常完了数、失敗試行数、未実行数を別に保存し、開始数=正常完了数+失敗数、予定数=開始数+未実行数を検査する。開始は当該legのプロセス起動試行を始めた時点と定義する。budgetだけの失敗は別軸なので正常完了の参考得点を維持できるが、正式ペア資格は失う。

受け入れテスト: 固定母集合4件でgames省略なら8局、明示2なら1ペア、明示10なら入力エラー。初期盤面の省略は2局。confirmatoryのgamesまたはselection-seed省略ではプロセスを作らない。途中停止でcoverageが一致し、一ペアでも欠ければ正式CIが出ない。

| --- | --- | --- |
| 正式CIは適格性判定の後だけ | 1・2・3・4・6 | profile、予算、証拠、予定全ケースを同じ検証済み入力で検査する |

終了コードは次で統一する。正常な参考集計、deploymentのCIなし、有効な正式CIで基準未達は0。必須予算未確認、正式統計を要求したのに不適格、保存報告の内容照合不一致、開始後のinfrastructure失敗は1。JSON構文・型・対応版・入力設定の不正、指定母集合や抽出設定の不正、開始前の保存先衝突は2。旧v1/v2の読み込み自体は対応済み入力とし、通常の参考処理は未検証理由付き0にできるが、正式処理又は必須予算検証を求めた場合の資格不足は1とする。保存済み報告のhash・seed等の意味上の不整合は比較結果の理由として1を返し、raw traceの不正は当該budgetの失敗として保持する。

### 10.2 推奨する共通入口と責務

**第一推奨は、新しいモジュールを増やさず、contractsの既存報告検査を「検証済みの値を返す入口」に拡張すること。** エラー配列だけでなく、検査から得たN・ケース集合・局別状態・得点をanalysisへ渡す。raw報告の値を検査後に再び直接読んで統計へ渡す経路をなくす。

以下の名前は具体的な実装案である。

| 変更対象 | 具体的な変更と責務 |
|---|---|
| `contracts.py» | `inspect_evaluation(report, evidence_root=None)»を追加し、既存の型/ID/棋譜/集計検査を再利用する。private helperで母集合・manifest・coverage・局/commandsを検査し、search_budgetの専門検査へ接続。検証結果と導出値を返す。`validate_report -> list[str]»は既存利用者向けwrapperとして保つが、空配列を正式資格の代用にしない |
| `openings.py» | 母集合・Entry・抽出algorithmの定義元を維持する。必要な厳密型検査を加え、全manifestの再計算・照合に利用する。新しいID式や抽出方式を追加しない |
| `search_budget.py» | `validate_trace_events(events, normalized_config, verified_command_context, expected_identity, …)»を同ファイルの内部実装として分離する案。ファイル版validate_traceも同じ内容検査を使う。未知版/欠損/型不正/予算違反を判定結果として返す。noneの未承認fall-throughを閉じる |
| `protocol.py» | 応答形式の検査をprocessを起動しない純粋helperとして取り出し、Playerの検査と保存commandsの検査で共用する。quitの応答0行も明示する。通信・期限・停止処理はPlayerのまま |
| `referee.py» | ルール判定の責務を維持。入力盤面/座標の型と形は呼び出し境界で確認してから利用する。本体AIをimportしない |
| `analysis.py» | 公開estimate/statistical_eligibility/pairedは毎回共通入口を通る。内部の資格判定は共通検証結果から行う。paired自身にもbefore/after相互条件照合を適用し、compare_reportsを経ない迂回を防ぐ |
| `statistics.py» | 検証済みNと得点配列/ペアだけを計算へ渡す。報告JSONやartifactの読み込みは担当しない。n=Nの算術を禁止するのでなく、報告生成側が全数の資格を保証する |
| `evaluate.py» | 新規取得と保存報告比較で同じ検証入口を使う。summary/旧statusは監査対象・履歴として保持し、現在の検証結果から正式資格を判断する。CLIの必須予算・正式統計要求も同じ判定結果へ接続 |
| `tests/test_harness.py» | 既存の正常fixture試験を拡張し、10.8の再発・統合・互換試験を追加する。新規テストファイルの大量追加は不要 |

検証結果は小さな辞書、必要ならcontracts内の少数のTypedDictで表す。クラス階層、plugin registry、専用サービスは導入しない。概念上、次を返す。

```text
InspectionResult
  validation_contract_version, validator_fingerprint, source_report_sha256
  status: verified / failed / unknown
  reasons: code, location, case_id, pair_id, leg, player, sequence
  population: status, population_hash, verified_N, case_ids
  selection: status, planned_n, selected_case_ids
  coverage: status, expected_pair_legs, observed_pair_legs
  gameplay/protocol: status, per_leg_results
  trace/budget: status, per_leg_per_player_results
  derived: qualified_pair_scores, validated_counts, coverage_kind
```

この結果は**当該呼出で原資料から導出するもの**で、JSONに保存したInspectionResultやverifiedフラグを次の解析がそのまま信用する設計にしない。positiveな保存statusは証拠ではない。原報告は変更せず、必要な正規化・新しい局別状態は派生viewとして扱う。N・得点・summaryの矛盾を派生値でこっそり修復して成功に変えない。

入力report自体も呼出開始時にsnapshot化し、そのhashと同じ内容から検査する。途中で呼出元の可変dictやファイルが変更されても、検査した値と数式に渡す値を別snapshotにしない。検証結果の共有は1回の解析内部だけに限定する。

### 10.3 母集合・抽出・全数の検証手順

1. **archiveを特定する。** 報告に記録された母集合artifactを読んで、記録済みファイルSHA-256を照合する。ファイルbytesは一度の読込snapshotとしてhashとparseの双方に使う。存在しない場合に同じ名前の他ファイルを探したり、報告のNを代用したりしない。
2. **内容を検証する。** openings.validate_populationでformat/rules/identity版、初期盤面からの合法履歴・手番、case/orbit ID、重複、population_hashを再確認する。Nは`len(validated_population.entries)»から得て、archive自身のpopulation_sizeとも一致させる。正式評価には厳密な正のintを要求し、bool・float・空母集合を受け入れない。
3. **全aliasを照合する。** 少なくとも`report.population.size/hash/purpose/placements»、`conditions.opening_population_size/hash»、`selection_manifest.population_size/hash»をarchiveの値へ照合する。selected_case_idsの報告aliasもmanifestへ照合する。必須alias欠落はunknown、型不正・既知値の不一致はfailed。報告側のNは統計の入力元にしない。
4. **予定標本を検証する。** nはmanifest.sample_sizeで宣言された予定値を扱い、選択ID数・一意性・planned_games/2・conditions.games/2へ照合する。`1 <= n <= N»、planned_games=2n。抽出algorithm/format、selection seed、全manifestとselection_hashを再生成して照合する。失敗局を除いた数を新しい予定nとしない。

   現行algorithmはPython random.sampleへ依存するため、記録されたruntime/Python版とalgorithm定義を再現できる範囲を明示する。現在のPythonで結果が違っただけで元の標本が不正だったと決めつけない。再現に対応できない版はunknownとして止め、algorithm名を同じにして別の抽出を採用しない。
5. **予定と実績を照合する。** 各caseについてrole seed・pair IDを再計算し、予定(pair_id,leg)集合を構築する。実績は各caseちょうど1ペア、leg0/1各1局、先後交換、A/B seed・開始履歴・盤面・手番が一致。重複・欠落・予定外・片leg・不正局・未開始を検出する。dictで上書きした後の件数やsetだけで重複を隠さない。
6. **統計へ渡す値を確定する。** trace/ゲーム/通信/予算検証まで済んだ全予定ペアから得点を作り、n_valid=n_plannedを要求する。Nは上記verified_Nのみを使う。集合・件数・各ペアの適格性のいずれかが未確認なら、全数区間も標本区間も出さない。

全数と標本の区別は次で固定する。

| 区分 | 必要条件 | 正式な区間 |
|---|---|---|
| census_verified | archiveがverified、selected集合=archive全case集合、n_planned=n_valid=N、全2N局と全要求が適格、固定得点の正式前提を満たす | その有限母集合の平均/対応差について一点区間。未観測局面や非決定的再実行の不確かさを0と主張しない |
| sample_verified | 同じ検証を通り、選択集合が母集合の一様非復元標本、n_valid=n_planned<N | 既存の有限母集合bound。得点がすべて同じでもn<Nなら全数区間にしない |
| incomplete / unverifiable / invalid | 欠損・重複・片leg・不適格局、archive/alias/抽出未確認のいずれか | CIなし。成功した一部だけを標本として再定義しない |
| full_coverage_descriptive | 全caseを対局していてもtime/deploymentや非決定的得点など正式前提外 | 記述集計のみ。n=Nという数値だけで正式censusへ進めない |

母集合の同一性はNだけでなくpopulation_hashとvalidated case集合で扱う。N件の異なる集合を同一母集合と扱わない。初期盤面だけのモードは母集合無しとして区別し、N=1を補って正式全数区間にしない。初期盤面の複数repeatは既存のrepeat_index/seed式から予定pairを構築し、正常な2局・4局以上の記述評価を維持する。

### 10.4 保存traceの形式検査と意味検査

ここで検証するtraceは、**ゲーム棋譜、各playerの通信ログ、AIが書いた予算JSONLの対応全体**である。予算JSONL単独に全盤面遷移や全コマンドが記録されていると仮定しない。

#### 10.4.1 形式・原資料の検査

- 正式対象の各局はplayersがA/B両方そろい、commandsが配列、各recordがobjectであることを要求する。成功応答・失敗record、board、位置、seconds、phase、exit codeの型・許容値を確認する。未知キーを読むことで必須項目不足を埋めない。
- 必須raw traceはartifactの存在・bytes SHA-256・対応形式版を確認してから、同じbytesをparseする。hash一致だけでverifiedにしない。hash記録なし/ファイル欠落/未知版/読込不能はunknown、hash矛盾/既知版の壊れたJSON/不正型/必須項目違反はfailedとする。
- headerと全genmoveの件数・連番・欠落・重複を確認する。原記録のsecondsや内部nsは有限/非負、整数カウンタはboolを除くint。再検証処理にかかった時間を過去のコマンドRTTとして使わない。
- 保存原本を上書きせず、取得時status、現在の再検証status、理由を別に返す。違反を見つけても合法終局の参考勝敗を消さず、正式資格を止める。

#### 10.4.2 盤面・コマンド・着手の再生

1. 検証済みcaseの履歴を初期盤面から再生し、forced openingのboard/to_moveを得る。既存_replay_gameを拡張/再利用し、AI本体を起動して棋譜を作り直す方法は使わない。
2. global movesの各手について手番、担当role、座標の合法性、8方向反転、記録された各盤面をrefereeで照合する。passは当該色に合法手なし、相手に合法手あり。両色合法手なしなら終局で、通常着手/通常passを追加しない。
3. A/Bそれぞれのcommandsもローカル盤面を再生する。forced playは両者、通常genmoveは担当者自身を更新し、相手のplayが同じ着手を反映する。askは盤面を変えず合法性応答、showboardはその時点の盤面、resultは同じ時点の終局/勝敗へ照合する。保存したshowboard文字列を無検証の「正解盤面」としない。
4. globalの1手と担当genmove・相手playを対応付け、隠れた余分なgenmove/playや欠けた相手同期を拒否する。commands内にglobal棋譜と無関係な別対局を混ぜない。通常着手・pass・終局probeのphaseは再生した盤面から算出し、保存phaseへ照合する。
5. 終局後の各playerのgenmove probeはNGかつ盤面不変、quitは応答0行・正常exitとして確認する。名前・stdout形式と実時間期限はprotocolの共通helper/記録値で確認し、エラー・timeout・異常exitを成功へ変えない。
6. 終局盤面、B/W/D結果、role winner、A得点、全予定局に対するsummaryと検証結果を照合する。保存score/result/summaryが矛盾したらfailedで、値の書換えによる「修復」はしない。

通常途中で通信失敗したログは、記録済みの接頭部分まで再生できても完走証拠にならない。棋譜完了、通信完了、予算検証は別軸で保持する。

#### 10.4.3 予算JSONLと実験条件の照合

- 10.4.2で確認した各要求のcommand、sequence、色、要求前盤面hash、実応答、算出phaseへgenmove eventを照合する。trace headerはrun_id・再計算pair_id・leg・A/B role・取得時target hash・正規化要求config hash・effective_configへ照合する。期待targetは保存実験の対象で、現在のAIファイルをhashして過去の対象を置き換えない。
- case_idとrole seedは親報告から再計算し、case→pair→headerの対応を検証する。**現行trace v2にcase_id/seedそのものはない。** v2は再計算pair IDによる宣言seedへの間接対応として記録し、AI内部が実際にseedを使用した証明とは扱わない。将来版で直接フィールドを追加するならその版では照合を必須化し、古いv2へ存在しない項目を推測して補わない。
- 全roleのkind・上限・node計数ID・policyを再確認し、内部elapsed/nodes/depth、completed<=started<=上限、モデルload/fallbackの許容条件を同じvalidatorで検査する。取得時と再解析時で「超過」「未知」「除外」の規則を別にしない。
- clock/scopeは任意の非空文字列ではなく、対応する計測定義として照合する。現行v2で利用しているperf_counter_ns/search_onlyを、validation contractが対応する定義として明記する。要求に明示された計測/モデル設定は必ず照合し、未対応scopeや非nullモデルの対応資産を確認できない場合はunknown。既知の期待設定との矛盾はfailed。モデル無しは明示nullであり、欠落から推測しない。
- noneは上限検証のkindではない。baseline-asymmetricのBで、現行契約の宣言・理由・取得対象hash等を確認した場合だけbudget=exempt/trace=not_requiredとする。**AのtraceやBのprotocolログまで免除しない。** 未承認noneはrawがあってもunknown。必要trace集合が空だからall([])でverified/exemptとする経路を作らない。
- 取得時の明白な通信エラー、違反、failedな実測値は履歴の事実として残す。原statusがunknown/failedだったことを新しいboolで自動昇格させない。既知hashの証拠が回復した場合も明示的な全再検証と新しい報告が必要で、hash未記録の新しい証拠の登録・旧失敗の更正は今回の自動処理範囲外とする。

#### 10.4.4 時間予算と非決定性

timeモードでは同じcase・seed・設定でもOSスケジューリングや探索終了点によって異なる合法棋譜を得る可能性がある。保存対局の再生では、その**同じ対局内**のmoves・commands・JSONLの一致が必要だが、別run・別AI・現在再起動したAIとの棋譜完全一致は要求しない。固定序盤の履歴・case・role seedの対応は維持する。

time/deploymentの合法な異なる棋譜はどちらも品質検証へ通せる。ただし現在の正式区間は固定探索予算の固定得点に対する有限母集合推定であり、time/deploymentへ移植しない。全Nケース完走や予算verifiedだけでは正式CIを付けず、記述的勝敗・時間・違反数を報告する。

### 10.5 二つの検証の接続と状態判定

検証の順序は「入力形式/原資料snapshot → 母集合・予定集合 → 局/commands再生 → 必須raw/予算照合 → coverage/得点照合 → 正式資格 → 数式 → 数値基準」。母集合を先に検証するのは、後続traceの期待case・board・pair・seedをその結果から得るためである。N検証だけ先に通して数式を実行する中間経路を残さない。

単独評価の正式条件は概念上、次のANDで固定する。

```text
population_verified
AND selection_verified
AND exact_planned_pair_coverage
AND all_games_legally_terminal
AND both_players_protocol_verified
AND every_required_trace_semantically_verified
AND role_budget_verified_or_explicitly_allowed_B_exempt
AND confirmatory_with_supported_fixed_work_policy
AND recorded_determinism_assumptions_and_evidence_eligible
```

comparisonは**両報告がこのANDを満たすことに加え**、母集合hash・N・選択case/pair・role seed・固定B・役割予算・計測定義・runtime・取得fingerprintの相互一致を要求する。analysis.pairedの直接呼出にも同じ比較契約を適用する。候補Aのコード/アルゴリズム変更は既存規則の範囲で許可し、A/Bのbudgetやscope変更を候補改善として隠して許可しない。

| 母集合・選択 | 必須trace/予算 | ゲーム/通信/予定coverage | 正式profile・固定得点前提 | 結果 |
|---|---|---|---|---|
| verified | verified（必要なら許可済みBだけexempt） | 全件verified | 適格 | 正式区間可。全case一致の時だけcensus |
| verified | unknown | 全件verified | 適格 | unavailable、CI=null、理由を返す |
| unknown | verified | 全件verified | 適格 | unavailable、CI=null、Nを推測しない |
| いずれかfailed | 任意 | 任意 | 任意 | unavailable。成功分だけを使わない |
| verified | verified | 欠損/未開始/片leg/不正/通信失敗 | 適格 | unavailable。予定nを縮めない |
| verified | verified | 全件verified | time/deployment等 | descriptive_only、正式数値基準not_requested |
| 母集合無しの初期盤面 | unknownまたは任意 | 記述評価として検査可能 | 非confirmatory | 正常な参考集計は維持。正式な序盤CIは付けない |

検証状態はverified / failed / unknownを用いる。unknownはmissing・unsupported・証拠不足、failedは既知契約との矛盾や違反。複数理由は全部保存し、集約はfailed優先、その次unknown、全必須要件の成功時だけverifiedとする。budgetのexemptは許可条件を確認した除外であってtrace verifiedではない。statistics unavailable、条件比較不可、採用undeterminedは別に返す。

表のunavailableは**正式統計を要求する入口**の判定である。非confirmatoryでは正式数値基準はnot_requestedのまま参考表示を可能にし、品質のfailed/unknownを別項目に必ず残す。optional budgetの欠損がある通常descriptiveと、予算が必須のdeploymentを同じ成功条件にしない。trace=not_requiredは許可済みBの局所項目だけで、全体traceの検査成功を意味しない。専門validate_traceのverifiedも「渡された要求集合との一致」であり、全対局完走・予定coverage・統計適格性まで証明する値ではない。

必須予算/正式統計を要求した実行・比較で、上記の資格が不足したら終了コード1。正しい正式区間で基準未達は0。任意予算の通常descriptiveは未検証理由を添えて参考集計を維持し、未検証を成功証明へ変えない。入力JSON/型/未対応入力の不正は既存の2、保存資料の内容不一致・開始後失敗は診断報告付き1へ接続する。最終採用の品質/運用証拠はこの2検証だけで満たされないため、現在のdecision=undeterminedを勝手にmetへ変えない。

### 10.6 保存済みデータ・ID・再解析との整合性

- 母集合format v1、case/pair/seed定義v1、予算/trace v2、評価JSON v3を維持する案を優先する。今回の母集合/trace意味検査は既存原資料で可能であり、全過去報告を強制的に別schemaへ変換する必要はない。
- 新しい検証の契約版（案: validation_contract_version=1）とコードfingerprintは再検証結果/新しい解析報告に保存する。これは取得時evaluation_fingerprintとは別の履歴で、旧報告のexperiment IDや取得fingerprintを現行検証コードで上書きしない。
- 保存報告の取得fingerprintを「現在のvalidatorコードと同じか」で判定しない。対応する収集形式/ルール/ID定義を検証できれば、旧v3を新しい検証器で再解析できる。before/afterの取得条件の相互一致は従来どおり検査し、異なる取得方式を同条件へ自動昇格しない。
- 新しいanalysis IDは入力報告hash、現在の検証契約/fingerprint、解析fingerprint、明示的なanalysis_specから算出する。古いanalysis_idを取得条件の証拠として使わず、旧解析と現在の結果を両方参照する。公表experiment IDと更新前の局所変数を取り違える現状A08も再解析の出力側で防ぐ。
- 同じ保存対局について、元のconfidenceが異なっていても明示した共通analysis_specで再計算する。引数省略時は保存analysis_specを使い、存在しないconditions.confidenceを読んで黙って0.95へ戻さない。別水準への再解析と事前の採用基準変更を同一視しない。
- 原評価JSON、raw、取得判定、既存解析は不変。新しい解析JSONを別名で出す。evidence_root引数はファイルを探す基準で、実験条件/IDへ含めず、別の場所の同じbytes/hashを検証できる。移動だけで再対局を強制しない。

| 保存形式/状態 | 再利用規則 |
|---|---|
| v3・母集合/manifest/commands/rawが完全、対応版、意味検査に成功 | 正式前提も満たせば再対局せず再解析可。元報告のCI・verifiedを再利用するのではなく再算出する |
| v3・原資料欠落/未知scope/未知raw版 | 参考情報を表示し、unknownと必要証拠を返す。正式CIなし |
| v3・N/履歴/trace/設定/結果の矛盾 | failed。正しいNへ勝手に置換したり失敗局を削除したりしない |
| v1/v2評価報告 | 従来の記述読み込みを保持し、legacy_unverifiedとして扱う。検証の空エラー配列だけでは正式資格を得ない。形式だけ書き換えてv3へ昇格しない |
| trace v2でcase/seed直接項目なし | 再計算pairと親条件による間接対応を検証する。内部seed使用そのものの証明とはしない |
| nonconfirmatory/timeの正常報告 | 合法性・通信・予算の品質と記述集計を再確認する。別run棋譜一致や正式CIを要求しない |

互換性維持は「以前の誤った区間まで再現する」ことではない。正常に完全な根拠を持つ報告の読み込みと再解析を維持し、誤ってavailableだった報告は資格不足として止める。

#### 独立プロセスによる対戦評価

スモーク評価の例:

```powershell
python -m harness.evaluate --a reversi_player/reversi.py --b reversi_player/reversi.py --games 2 --seed 20261009 --output evaluation_results/smoke.json
```

本格的な比較には、固定した相手と十分な対戦数を指定する。以下の `baselines/reversi.py` は、比較対象として別途保存した過去版へのパスに置き換える。

```powershell
python -m harness.evaluate --a reversi_player/reversi.py --b baselines/reversi.py --games 100 --seed 20261009 --output evaluation_results/candidate.json
```

`--games` は2以上の偶数。2局ごとにA/Bの黒白を交換し、同じペアではプレイヤーごとのシードを保つ。毎局、A/Bを別プロセスで起動する。着手側の `genmove` は自身の盤面を更新するため、相手だけに `play` を送る。各着手・パスの後、双方の `showboard` と独立判定の盤面を照合し、両者の `result` も確認する。パスは `genmove` の `NG` で検査し、仕様にないpassコマンドは追加しない。

標準出力の余計な行、応答形式の違反、盤面不一致、結果不一致、不正着手、タイムアウト、異常終了を記録し、その対局を失敗として扱って次局へ進む。失敗をどちらかの勝利に変換しない。勝率は勝利数÷正常完了局数、勝ち点率は（勝利数＋引き分け数÷2）÷正常完了局数。失敗数と原因を必ず併せて見る。正常完了局がなければ率はJSONのnull。

##### 固定序盤と予算設定

候補AIに依存しない固定序盤母集合を作成し、hashと合法性を検証する。`--exclude-openings` は複数指定でき、既存集合との対称重複を除外する。出力先は既存ファイルを上書きしない。

```powershell
python -m harness.openings generate --count 1000 --placements 8 --seed 20261009 --purpose development --output benchmark_sets/development-v1.json
python -m harness.openings validate benchmark_sets/development-v1.json
```

序盤指定時の `--games` は先後交換ペアのため偶数で、2局ごとに1ケースを非復元抽出する。結果には母集合hash、抽出seed、選択case IDが残る。

予算設定JSONの例（A/Bそれぞれに指定）:

```json
{
  "format_version": 1,
  "budget": {"kind": "nodes", "limit_nodes": 100000},
  "search": {"deterministic": true, "counting_definition_id": "negamax-node-v1"}
}
```

ハーネスは子プロセスへ `REVERSI_EVAL_CONFIG` と `REVERSI_EVAL_TRACE` を渡す。AI自身が設定を受理し、各 `genmove` の有効設定・探索時間・ノード/深さ・応答・盤面hashをJSONL traceへ出さなければ、予算はverifiedにならない。`none` 予算は対象プログラムのSHA-256に結びついた明示的な適用除外が必要。現在の `reversi.py` はこのtraceに未対応のため、厳密な予算検証はテストfixtureで確認した範囲に限られる。

評価プロファイルは `smoke` / `descriptive` / `confirmatory` / `deployment`。confirmatoryは固定序盤、明示的な抽出seed、決定性、nodes/depthの候補予算とequal-workまたは宣言済みbaseline-asymmetricを要求する。deploymentは双方の時間予算とequal-timeを要求する。strict profileではプロトコルと予算の未検証・失敗を終了コード1とする。

```powershell
python -m harness.evaluate --a candidate/reversi.py --b baseline/reversi.py --openings benchmark_sets/development-v1.json --games 20 --selection-seed 20261010 --seed 31 --a-config candidate/eval-work.json --b-config baseline/eval-work.json --evaluation-profile confirmatory --budget-policy equal-work --output evaluation_results/candidate.json
python -m harness.evaluate --compare evaluation_results/before.json evaluation_results/candidate.json --confidence 0.95 --output evaluation_results/comparison.json
```

統計は全予定ペアが完全かつ適格な場合だけ、固定有限母集合に対するHoeffding–Serfling区間を返す。比較時はcaseごとのbefore/afterペア得点差を推定する。対象は保存済み母集合に限り、未知の局面分布への一般化や非決定的AIの時間予算下の優越性をこの区間で主張しない。

終了コードは要求成功0、対局/必須検証/比較条件不成立または開始後の保存障害1、入力不正・未対応root schema・開始前の既存出力指定2。数値基準未達でも実行と保存が正常なら0。保存先は排他的に作成し、raceでできた他者の出力も上書きしない。

##### 拡張実装後の運用

評価JSONはschema v4、予算設定はformat v2、traceはformat v3で保存する。`--games`を省略すると初期盤面では2局、固定序盤では母集合N件すべてを使う2N局になる。短い固定序盤の確認では `--games 2` を明示する。confirmatoryでは `--games`、`--openings`、`--selection-seed` が必須で、開始前に同じ局面・seed・設定で各AIを2回起動する決定性probeを行う。このprobeは有限の再現性確認であり、全局面の決定性を証明しない。

raw traceと母集合は出力JSONの隣の `runs/<run_id>/` に保存し、JSON内には相対パスとSHA-256を記録する。`run-state.json` は局ごとに原子的に更新し、途中停止時は進行中・中断・未開始局数を残す。評価JSONと証跡ディレクトリの両方を保管する。予算検証を要求した比較では、旧schema v1/v2/v3の報告は現在の実測区間証拠が不足するため成功扱いしない。比較JSONはschema v4の別ファイルに保存し、元の評価JSONを変更しない。confidenceは解析条件なので、異なるconfidenceで取得した同一対戦結果も `--compare ... --confidence ...` で共通条件へ再解析できる。

現行 `reversi.py` は予算traceを出力しないため、実AIの予算状態はunknownとなる。fixtureでのtrace検証成功と、実AIの内部予算適合は区別する。

#### 時間計測とプロセスの終了

`harness/protocol.py` がstdoutとstderrを別スレッドで読み、キューを通して応答期限を管理する。子プロセスには `-u` を付けず、本体自身のflushが機能することも確認する。

起動時間はPopenの直前から最初の `name` 応答まで。これはPython・import・盤面初期化と最初のnameの処理を含む起動の指標であり、純粋なOSの起動時間ではない。準備完了の専用コマンドが仕様にないため、この初回応答だけは別の上限（既定5秒、`--startup-timeout` で変更可能）で待つ。以後の `name` を含む通常コマンドは1秒、`genmove` は10秒、`quit` の正常終了は1秒で待つ。

コマンド応答時間は送信の直前から必要な全行を受信して形式を確認するまでの実測値。`genmove` の平均・最大には合法手のない問い合わせも含む。通信とOSのスケジューリングを含む時間であり、AI内部だけのCPU時間ではない。起動のnameは通常コマンドの平均には含めない。失敗コマンドの待ち時間と終了処理は区別する。

期限超過・異常時は停止処理を行う。Windowsでは自身が起動したPIDに対して `taskkill /T /F` を使い、必要ならkillへフォールバックしてwaitする。POSIXでは独立したプロセスグループを終了する。正常終了時にも余分なstdoutがなかったことを確認し、パイプを閉じる。

#### 保存と再評価・比較

JSONには設定、Python/OS、A/B本体とハーネスのSHA-256、起動時間、全コマンドと応答時間、棋譜、各着手の盤面、最終盤面、勝敗、エラー、stderr末尾を保存する。標準出力に集計結果も表示する。詳細JSONは `evaluation_results/` に保存し、Gitでは既定で無視する。採用判断に使う結果は必要に応じて別途保管する。

現在のAIの乱数は外部の `harness/seeded_player.py` でPythonのrandomとPYTHONHASHSEEDを固定する。本体は書き換えない。同じPython、同じコード・シード・相手で評価を再実行すれば現在の棋譜と勝敗を再現できる。計測時間は実行ごとに変動する。将来numpy、GPU、別の乱数源等を使う場合は、それらの再現性を追加で確保する。

モデルや読み込む別モジュールなどが追加された場合は `--a-asset PATH` / `--b-asset PATH` を繰り返し指定し、資産のハッシュも保存する。ハーネスはimport依存関係や外部設定を自動的にすべて列挙するものではない。

```powershell
python -m harness.evaluate --compare evaluation_results/before.json evaluation_results/after.json --output evaluation_results/comparison.json
```

比較ではAを候補、Bを固定相手として扱う。対戦数・シード・時間上限・実行環境・相手のコード/資産・ハーネスが一致し、両評価に失敗局がないことを確認する。Aの勝率、勝ち点率、平均・最大応答時間の差（after−before）を表示する。候補Aのコードが違うことは許容する。同条件でも少数局の差だけで強さの改善を断定せず、本格評価では対戦数・複数シード・複数の固定相手を増やす。

#### AI改善時の作業順序

1. Git状態と `python -m pytest -q` を確認して開始時点の失敗を記録する。
2. 比較する過去版と、その依存モジュール・モデルを別ディレクトリに保持する。固定相手のコードを変えない。
3. 同じ相手・対戦数・シードで変更前の評価JSONを保存する。
4. AIを変更し、関連テストと全体の仕様検証を通す。失敗を調査し、期待値だけを変更して通さない。
5. 同じ条件で変更後の評価を保存・比較する。失敗局、先後の偏り、制限時間を確認する。
6. 測定結果と未検証事項を報告し、採用を判断する。コミット・pushは明示的な依頼がある場合に行う。

#### 1. 第一推奨と現在地

第一推奨は **固定した探索型の比較相手を作る → 軽量なn-tuple価値モデルを自己対戦TD学習で育てる → 学習済みモデルに探索を組み合わせる** という順序である。探索はまず比較対象としてαβ法を整備し、学習後には同じ価値モデルを使うαβ法とMCTSを同じ条件で比較する。学習ループの中に重い探索を最初から入れない。

ここで「価値モデル」は局面から最終的な勝敗の見込みを出す学習済みモデル。「n-tuple」は盤面の数マスの石配置を表引きして値を合計するモデル。「TD学習」は後の局面の予測と終局の勝敗から、前の局面の予測を修正する強化学習である。巨大なニューラルネットがなくても、自己対戦で価値モデルを改善する研究課題を構成できる。

既存計画の方策・価値ネットワーク＋自己対戦探索は将来の拡張候補として残す。今回はGPU学習環境と使える学習時間が未確認のため、CPUで実験を始めやすい方式を先に提案する。GPUがないと断定しているわけではない。提出期限、CPU/GPU、学習に使える時間を確認したら実験量を調整する。

現在の `reversi_player/reversi.py` は、学習済みモデルをまだ使わず、合法手からランダムに選ぶ。前回確認は73テスト成功で、20局のランダム版同士の評価も完走している。これは強さの比較基準が完成したことや、勝率55%の側が強いことを意味しない。現在のコードは保全できており、ここから評価対象を作れる状態である。

##### 決定的な探索AIの評価に必要な拡張

現在のハーネスは全局が同じ初期盤面から始まる。乱数シードを変えても、乱数を使わない探索AI同士なら同じ棋譜が繰り返される。100局完走しても、独立した100個の対局条件とはみなせない。

このため、統計的な採用判定の前に **固定序盤セット** を追加する。初期盤面から合法な4手または8手を独立判定で生成・検証し、棋譜とSHA-256を保存する。同じ序盤をA黒/B白、B黒/A白の2局で使用する。序盤は両プロセスへplayで同期してから評価を開始する。初期盤面からの通常対局の結果も別に残し、強制序盤付き評価と混ぜて報告しない。

重複した序盤・同じ盤面と手番になる序盤は除く。初期配置に対する単なる回転等が独立した問題を増やすとは考えず、対称な重複も整理する。学習・調整に使うセットと最終判定セットを分け、最終セットを見ながら重みや設定を調整しない。

必要なユニーク局面数を4手の序盤で満たせない場合は8手等へ進み、重複対局で標本数を水増ししない。

その他、以下をJSONから集計できるようにする。まだ実装済みの機能として扱わない。

- 合法手があるgenmoveと、パス・終局のNG問い合わせを分けた時間集計。平均に加えp95、最大、最初のgenmoveの時間を出す。
- 初手genmove、起動、モデル読み込みの時間、モデルの欠落・破損時の動作。
- 対局結果だけでなく、完了深さ、展開ノード数、打ち切り理由、使用したモデル・設定。通常stdoutへ混ぜずstderrまたは開発用ログで記録する。
- 序盤の先後交換ペア単位の勝ち点、信頼区間、同じペアでの変更前後の差。

現在の `--compare` が確認する時間設定はプロトコルの応答上限であり、AI内部の探索予算は含まれない。`comparable: true` だけで両AIが同じ思考時間を使ったと判断せず、比較条件へ内部の時間・ノード予算も追加する。

学習のための大量自己対戦は、毎手HTTPや別プロセスを往復する方式で行わない。既存Boardを学習コードから再利用し、信頼できる独立判定で一部の棋譜を監査する。最終評価には外部プロセスのハーネスを使う。`harness/referee.py` をAI側のルールエンジンへ流用して、判定の独立性を失わせない。

段階1は評価基準としての探索プログラムであり、強化学習モデルが完成した段階とは呼ばない。段階3で自己対戦と報酬からモデルを更新し、段階4で学習と探索の寄与を分けて示す。

##### 段階1: 探索と手作業の評価

1. 合法手を置いた後の局面を評価する1手読みを作る。角、合法手数（mobility）、空きマスに隣接する石（frontier）、未取得の角に隣接する危険なマスを特徴にする。序中盤の石数だけを大きく評価しない。角を取得した後まで隣接マスを一律に悪いと扱わない。
2. 係数は仮設定であることを記録し、最初は少数の正規化した特徴で始める。論文の数値を未確認で転記したものとして扱わない。終盤の確定勝敗を非終局の評価より優先する。
3. Negamax形式のαβ法を実装し、まず固定深さ1→3で検証する。深さは盤面に石を置く回数で数えると決め、パスでは深さを減らさず手番を交代する。両色に合法手がなければ終了する。値の符号は手番との関係をテストする。
4. 反復深化で完了した深さの手を保持する。先に合法な代替手を確保し、期限で止まったら最後に完了した探索結果を返す。探索途中の一部の根の手だけで最良手を決めない。
5. 置換表を入れる場合は盤面だけでなく手番・探索深さ・値の境界種別を正しく管理する。最初からProbCutなどの統計的枝刈りを入れない。

時間予算はまず通常0.1秒/手を試し、必要なら1秒/手へ拡張する。内部の安全上限は最大8秒を初期案とし、課題上限まで余裕を残す。これは実測で調整する設計値であり、処理時間の保証ではない。比較実験は同じ時間予算の結果を主指標とし、固定深さ・固定ノード数の実験も学習効果の切り分けに使う。

##### 段階2・3: n-tuple価値モデルとTD学習

最初の候補は体系的に配置した直線状2-tuplesと3-tuples。長さごとのLUTには3^n通りの空白・黒・白の配置を入れる。8種類の回転・反転で対応する重みを共有し、同じ重みが複数回参照されるときは更新の参照回数も一致させる。モデル容量と一手当たりの参照数をmanifestに記録する。

Jaśkowski論文の小型モデルと同じパラメータ数・強度の再現を約束するものではない。短いtupleで頭打ちになったら、4-tuples、角や辺の長いパターン、時期別モデルを一つずつ比較する。Scheiermann/Konen論文の大きなモデルは後の比較候補であり、最初の実装にその複雑さを持ち込まない。

状態は **盤面＋手番** とする。パスでは盤面を変えず手番が変わるので、手番を捨てない。初版は黒から見た価値V(s)を一貫して扱い、手番別のLUTを用意する。黒は価値の最大化、白は最小化で手を選ぶ。白番なのに黒の予測値を最大化する誤りをテストする。

値の例は Vθ(s)=tanh(fθ(s))。終局の目標zは黒勝ち+1、白勝ち−1、引き分け0。途中の石数増減を報酬にせず、主目的を勝敗に合わせる。非終局の遷移s→s'では目標をVθ(s')、終局への遷移では目標をzとし、TD誤差δ=目標−Vθ(s)で重みを更新する。ブートストラップの目標側へは勾配を流さない。この黒視点の設計では、手番交代のたびにTD目標を無条件に負にしない。探索のNegamax表現への変換は探索側で明示する。

初期実験値の提案:

- TD(0)、割引率γ=1。初期学習率は0.001を中心に試し、発火する特徴数・重複参照で更新幅が過大にならないよう正規化する。必要なら0.0001と0.01を比較する。論文の学習率をそのまま最適値とみなさない。
- 学習中のみε-greedy（確率εでランダムな合法手）。ε=0.1から開始し、例えば累計2万局までに0.02へ下げる案を検証する。評価ではこの探索的ランダム着手を止め、同点手の選び方とシードを記録する。
- 最初に1000局の試行で速度、終局、数値の発散、ファイル容量を調べる。その後5000局単位で保存し、1万局→5万局を初期の実験範囲とする。到達強度や所要時間を保証する対局数ではない。
- 最初は同じ学習モデルの自己対戦。改善を確認したら、過去の採用モデルも対戦相手に混ぜ、相手と比率を記録する。最新の自分との勝率だけを改善指標にしない。
- まずtuple配置、次に学習率など、一度に一要素を比較する。選んだ設定は少なくとも3つの学習シードで再学習して、特定の初期値だけで成功していないか調べる。全組合せの大規模探索は最初に行わない。

checkpointには、重み、tuple配置、対称性処理、手番・色・報酬の定義、学習局数、学習率、ε、乱数状態、学習コード/データのハッシュを保存する。対戦時は固定checkpointを読み、評価対局の途中で学習しない。推論時は学習用ライブラリを不要にする小さな形式を優先する。

モデルの欠落・破損時には、提出用の対戦動作として検証済み探索版へ戻す案とする。使ったモデルとフォールバック理由をstderr等に記録し、学習モデルの採用試験ではフォールバック0回を必須とする。読み込み失敗を隠したまま、探索版の勝率を学習モデルの成果として報告しない。

追加すべきテストは、終端ラベル、パスを含む状態遷移、TD更新の方向、有限差分による勾配、重複LUT参照、8対称性、色交換と勝敗符号の対応、save/loadの一致、学習中と評価中の乱数の分離。色交換を行う場合は石だけでなく手番と目標符号も交換する。

##### 段階4: 学習済みモデルを使う探索

同じ重みを使う1手評価を基準に、まず既存のαβ探索へ価値モデルを差し替える。次に、対戦時だけMCTSを使う方式を比較する。MCTSの事前確率は、合法手を置いた後の価値を手番の視点に直してsoftmaxで作る案とし、最初から別の方策ネットワークを学習しない。終局ではモデルの推測値より確定勝敗を使う。

MCTSは100→1000回の試行から時間を測り、10秒の上限内で増やす。論文の探索回数を、そのままPython版でも実行できると仮定しない。同じ局面セット・モデル・時間予算でαβ法より強いかを判定し、強くなければαβ版を採用する。

TD(λ)、TCL、終局からの追加更新等はTD(0)が動いてから一つずつ検証する。さらに資源が確保でき、軽量方式に明確な限界が見えた場合に、方策・価値ネットワーク＋学習中MCTSへ進む。AlphaZero型の導入自体を成功条件にしない。

##### 段階5: 終盤完全読みと速度

残り空きマス8以下から、時間予算内で終局まで読み切る候補を試す。読み切れない局面では元の探索へ戻す。全局面の8空き以下が一定時間で解けるとは仮定せず、パスを含む遅い局面も測る。十分な余裕がある場合だけ10、12へ拡張する。

bitboardや高速化はノード当たりの合法手判定・反転・評価の計測から必要箇所を決める。追加エンジンは固定盤面、既存Board、独立refereeとの比較で確認し、独立refereeを候補に合わせて変更しない。

#### 5. 評価設計と採用規則

##### 固定する対戦相手

1. `random_v1`: 現在のランダム版。初期の正常性・弱すぎるモデルの検出用。
2. `search_v1`: 段階1で固定した手作業評価＋αβ版。学習モデルの主要な比較基準。
3. `champion_vN`: 前回採用した学習版。新checkpointが以前の成果を失っていないかの検査用。

ランダムに勝つだけでは採用しない。対戦相手はコード・依存モジュール・モデル・設定を丸ごと固定する。候補と過去版が同じ最新モジュールをimportしてしまわないよう、各ディレクトリから独立して起動する。必要なら将来Edax等の外部相手を追加するが、現ハーネスのPythonコマンド形式にはアダプターが必要であり、接続済みとは扱わない。

##### 対局数と統計

以下はこのプロジェクトの初期運用案であり、論文が指定する合格基準ではない。

- スモーク: 2局。通信、盤面同期、終了を確認する。
- 開発中: 20局。明らかな退化や速度違反を早く検出する。強さを確定しない。
- 調整用: 固定探索版・旧採用版へ各100局。最終判定に使わない序盤とシードを使い、有望な候補を絞る。
- 最終判定: 主要相手へ400局（200個の序盤×先後2局、生成用シードも2群に分ける）、固定探索版へ200局、ランダム版へ100局を初期案とする。相手が重複する場合は同じ結果を二重に数えない。

勝率に加え、引き分けを0.5点にした勝ち点率を主指標とする。先後交換の2局を1ペアとして、序盤ペア単位のブートストラップで95%信頼区間を出す案とする。変更前後の比較も同じペアの差を使う。独立に用意した序盤が少ないと区間推定も頼れないので、棋譜の重複数・ユニーク局面数・先後別成績を添える。この区間は固定した相手・序盤分布についての結果であり、未知の全相手への保証ではない。

採用には、全仕様テスト成功、全対局の異常0、時間上限遵守を必須とする。そのうえで主要相手への勝ち点率55%以上かつ下側95%信頼限界が50%超を初期の昇格条件にする。条件を満たさなければ保留し、最終セットを見て調整を続けず、追加の未使用セットで再判定する。複数相手への評価で明確に退化した場合も採用を保留する。最終判定する候補を事前に一つへ絞り、多数候補の中から偶然よかったものを選ばない。

学習方式の効果を説明するため、最低限「ランダム」「手作業評価1手」「手作業評価＋αβ」「未学習n-tuple」「学習n-tuple1手」「学習n-tuple＋探索」の比較を残す。探索方式を固定した比較と、時間予算を固定した比較を分け、単に計算時間を増やした効果を学習の効果と混同しない。

##### 計算時間を先に見積もる

現在の数ミリ秒のランダム版の結果から、探索版・学習版の速度を見積もらない。20局の試行から1局の実時間を測り、本格評価に必要な時間を計算する。例として双方が平均0.1秒/着手なら、100局×約60着手×0.1秒は約600秒（10分）。平均1秒なら約100分になる。起動・パス・検証の費用はさらに加わる。測定結果に合わせて局数と実験頻度を決める。

GUIは要求ごとに本体を起動するので、学習済みモデルを常駐させた評価だけで済ませない。モデルロードと最初のgenmoveを含むHTTP応答も確認する。前回のHTTP確認では静的資産、初期盤面、一手のAI応答は成功したが、実ブラウザでの操作確認は別に残る。

#### 6. 配布棋譜の扱い

`102400-games.pkl` は現段階の強化方針に必須ではない。利用するときは原本を変更せず、出所・信頼性・棋譜の合法性・パス・石数差ラベル・重複を確認する。対局単位で学習/検証/最終判定を分け、対称変換等の重複も同じ分割側へ置く。

価値モデルの教師あり初期化として利用する案はあるが、棋譜の品質が不明なうちは「強い教師」とみなさない。配布棋譜のみの学習と、モデルが自分で指して得た報酬による自己対戦強化学習の効果を分けて測る。学習用棋譜が、独立した相手による強さの評価を置き換えることはない。

#### 7. 次の実装依頼の範囲

最初に実装するのは **ランダム版の独立保存と、時間管理付きの1手評価・αβ探索による固定比較相手**。併せて固定序盤の評価設計を実装し、候補と固定相手の資産を漏れなく記録する。

既存Boardと外部コマンドの責務を保ち、`_genmove()` の手選択を新しいモジュールへ委譲する最小限の変更にする。モデル学習や高度な高速化は、この比較相手の正常性と速度が確認できてから着手する。

実装時は、開始時のpytest → 関連する固定局面・探索テスト → 全pytest → 2局スモーク → 固定条件の評価 → JSON比較の順で確認する。今回作成したのはこの方針文書であり、記載の新機能や学習・強さの結果を実装済みと報告しない。
