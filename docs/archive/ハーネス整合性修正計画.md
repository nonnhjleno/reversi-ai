| analysis.py | assess_evaluation / assess_comparison、正式資格と必要条件、解析spec、正式結果の組立て | 全公開入口が使う単独/対応差資格、要求成功と数値基準の分離 |

contractsはprotocol/search_budgetの純粋helperを呼ぶ。両者からcontractsへの逆importは禁止する。ClockContractの実体はprotocolが所有し、contractsの仕様表は参照するだけ。contractsからstatisticsへの得点化依存は外し、検証済みgameとcoverageをanalysisから数式へ渡す。seed/case/母集合の既存定義は維持する。

### 3.2 毎呼出の結果型

次の名前は提案DTOで、重いクラス階層ではなく小さな辞書/TypedDictと実行時型検査を想定する。

```text
DecodedInput
  input_status: valid / invalid / unsupported
  source_schema, requested_profile: known value or null
  normalized_conditions, analysis_spec, required_roles, requirements
  source_snapshot, source_report_sha256, issues

Inspection
  validation_contract_version=2, validator_fingerprint
  source_report_sha256, artifact_hashes, capability_profile
  source_consistency, population, selection, coverage
  execution, gameplay, protocol, budget_by_role/game/report, timing, metrics
  acquisition_claims, current_validation, hold_reasons
  validated_games, verified_N, planned_n, expected_pair_legs
  derived_measurements, canonical_summary, reference_summary, issues

Assessment
  input_status, quality_status, formal_eligibility, formal_reasons
  reference_available, metrics_certified, request_success
  comparison_match_status (comparison only)

```

Inspectionは必ず新しいsource/bytes snapshotから生成する。保存されたInspection、eligible bool、summary、status、caller提供の計算結果を資格として受け付けない。一呼出のcacheはbytesと内部検証結果の共有に限り、別の呼出へpositive flagを持ち越さない。

DecodedInputのinvalid/unsupportedには利用可能なnormalized viewを保証しない。consumerはinput_statusを先に分岐し、raw snapshotへ.getを使って代用品を作らない。source_report_sha256は原reportのcanonical JSON hash、artifact hashは原bytesのSHA-256という既存の違いを維持する。file入力の場合は原JSON file bytesのhashも別フィールドで付けられるが、二つを混同しない。

root JSONのNaN/Infや非JSON値は入力層でinvalidにする。canonical化不能な入力のsource_report_sha256はnullと理由を返し、偽のhashを作らない。file bytesのhashが取得できる場合はそれを出典にできる。既知rootから参照されるraw内の不正JSON/非有限値はartifact検証failedであり、入力rootのunsupportedとは異なる。失敗結果には不正floatをそのまま埋めず、安全なcode/path/型表現を使う。

## 4. Q1・Q4: 状態と必要role集合の修正

### 4.1 集約規則

必要roleは既知の対戦契約から常にA/Bを作り、players.keys()から決めない。起動前にA/Bのslotを用意し、起動状態と予算証拠の有無を別に記録する。

| 層 | 値・規則 |
|---|---|
| roleのbudget | verified / exempt / unknown / failed |
| exempt条件 | B、baseline-asymmetric、理由、元本体hash一致をすべて確認した場合だけ。欠損role・空集合・A・未許可noneはexemptでない |
| gameのbudget | failedがあればfailed。必要roleの欠損/unknownはunknown。A verified + B verifiedまたは許可済みexemptならverified |
| reportのbudget | 同じ規則で全予定gameを集約。欠落gameはunknown、既知違反はfailed、必要全gameがverifiedならverified |
| execution/protocol | 起動/通信失敗はfailed。予算証拠不足unknownとは別。正常終局だけでprotocolをverifiedにしない |

現行policyではgame/report全体をexemptにする正当な経路はない。Bの除外はroleに残し、game/reportはverifiedとして「同予算」とは主張しない。起動0件はbudget unknown、execution/protocol failedとなる。元v3の空集合exemptは既存バグとして受理しない。

### 4.2 原状態と現在の状態

まず保存されたplayer→game→reportのacquisition状態を同じ集約関数で照合する。source内の矛盾はsource_consistency=failedであり、rawが有効でも修復して正式へ通さない。現在の再検証結果は別の軸で計算し、元JSONを変更しない。

必要な取得軸の原failed、または原unknownを新しいpositive flagで自動昇格しない。証拠が回復しても既知hash・明示的全再検証・別の更正報告が必要で、今回の自動更正機能には含めない。hold理由を共通Assessmentへ渡す。元の「保存済みCI」は過去の主張として残し、今回のCI資格を与えない。

取得直後も共通集約を使って正規の状態を保存し、再解析時だけ厳しくする設計にしない。原取得失敗のvalidな報告と、状態が矛盾したinvalidな報告を区別する。

## 5. Q2: 実測区間による時間契約

本節はschema4/trace3に実装された要求内包含の設計履歴。生存期間・全command間の順序は保証しない。T1では本節を保持したままSP/PR/CE/IR/終了と全要求を接続する。新しい正式必要集合・版移行・未知scopeの扱いは時系列修正計画第5・6・9節を正本とする。

### 5.1 新規取得の記録

提案する強化契約は評価schema=4、trace format=3、measurement_contract=`local_cpython313_perf_ns_enclosed_v1`。budget config v2とcase/pair/seed versionは変更しない。

現在のfloat秒差だけから新しいnsの実測開始/終了を作らない。Playerとtrace producerが実際の計測点でtime.perf_counter_nsを呼ぶ。

| 記録 | 必須の実測点・派生値 |
|---|---|
| startup | spawn_before_ns→最初nameのvalidation_end_ns。起動別期限。初期model loadはこの範囲に対応 |
| host command | exchange_start_ns、send_start_ns、response_read_end_ns、validation_end_ns。成功時はこの順序。external_response_ns=validation_end-exchange_start、wire_envelope_ns=response_read_end-send_start |
| host quit | send_start_ns→正常process終了観測exit_observed_ns。reader join/abortの回収時間は含めない |
| child genmove | command_received_ns、search_start_ns、search_end_ns、response_ready_ns。response_readyは応答が決まりstdout送信/trace書込みへ進む前の点 |
| search | search_elapsed_ns=search_end-search_start。合法手判定・候補列挙・選択・盤面更新を含む既存fixtureのscopeを固定。trace書込・通信は含めない |
| model load | modelありならstartupまたは当該commandの実測区間とload start/end/elapsedを記録。search_onlyではloadとsearchを別の非重複区間にする。modelなしは明示not_required、elapsed=0、端点null |

command_idはrun/pair/leg/role/全command_indexを結ぶ。genmove sequenceは通常/pass/terminal probeをすべて数える別の連番。childはname/play等を含めた全要求のindexを数え、hostの要求列と照合する。clock_domain_idは親が同一取得内の時計domainを結ぶcontext値で、case/pair IDや実験条件へ混ぜない。

headerは親子runtime・ClockContract・元contextと結ぶ。initial model loadの端点はstartupへ、lazy loadは当該commandへ結ぶ。fallback・未知scope・GPU完了未同期・別clockによる値は既知契約で推測して受理しない。

### 5.2 包含関係

当面の対応domainは、同一hostで同一CPython 3.13 interpreterから起動する親子、perf_counter_ns、monotonic=true、adjustable=false、同じclock実装/単位/measurement契約に限定する。domain・runtime・版が確認できない場合はtiming unknownとし、正式へ通さない。

Python 3.13のperf_counterは全processで同じ時計を使い、perf_counter_nsはfloat精度損失を避ける整数nsである。get_clock_infoで実装・単調性・resolution等を取得できる。[Python公式time資料](https://docs.python.org/3.13/library/time.html#time.perf_counter_ns)。これはUTC時刻・真の連続時間の完全精度・trace発行者の真正性を保証する説明ではない。

**提案の検証式**（同一domain確認後、同じ保存要求内だけ）:

```text
host.exchange_start <= host.send_start
host.send_start <= child.command_received
child.command_received <= child.search_start <= child.search_end <= child.response_ready
child.response_ready <= host.response_read_end <= host.validation_end
search_elapsed = child.search_end - child.search_start
external_response = host.validation_end - host.exchange_start
0 <= search_elapsed <= wire_envelope <= external_response <= command_limit_ns
```

絶対UTCの比較はしない。上記は同一取得の共通counterでの順序であり、別run・別machineの端点を比較しない。整数型はboolを除外する。timestampの符号そのものは規約にしないが順序と差は必要。時計resolutionは診断情報で、一律10ms等の猶予や未知clockを認める口実にしない。対応domainでは加算猶予0で確認する。deadlineの秒設定は起動前に有限正数・整数nsへ厳密変換する。

response_read_endだけが期限内でも形式検査終了が遅れたら失敗。secondsは新規取得でcanonical external_response_ns/1e9の表示用に統一し、move.seconds等のaliasも同じ派生値を使う。quit/startupはそれぞれの定義から派生し、回収時間を混ぜない。失敗要求は成功envelopeを捏造せず、実測failure点とerrorを診断記録にする。

同じdomainだと宣言しながら元contextのclock_domain_idが不一致、対応済みdescriptorの値が矛盾、端点/elapsedの不整合ならfailed。domain証拠が欠損またはclock/runtime契約そのものが未対応ならunknown。この二つを「未知時計」という一つの理由へ潰さない。

この契約の親子区間比較は、互換時計と正しく計測するproducerという前提に依存する。自己申告を全部偽造する行為への認証機構ではない。

### 5.3 probeと旧データ

_verify_determinismは各attemptの実際のPlayer.commands/startup/exitとclock contextも保存する。現在のinspectが仮のshowboard/genmoveを組み立てる方法では時間envelopeを証明できない。新しいprobeは実要求とcase/role seedへrawを結び、同じ時間validatorを使う。Bの通常予算除外はprobe証拠の免除ではない。

protocol検証のpurposeはgamesの位置ならgame、determinism evidenceの位置ならprobeと内部で決め、rawの自己宣言で切り替えない。gameは合法終局・両終局probe・quitを要求する。probeは検証済みcaseへのforced play、予定する単発genmove1件、更新盤面・応答、quitを検証し、対局終局を要求しない。_command_contextsと新しい_observe_probeは純粋な要求/時計/盤面helperを共用するが、完了条件を同一にしない。probe用を選んで通常gameの終局検証を省く入口は作らない。

schema3/trace2のsecondsやsearch_elapsedは参考測定として保持するが、欠けた端点/domainをseconds*1e9や現在の時計情報で補わない。記録上の大きな時間差は診断に示し、強化区間契約への適合はunknownにする。既知のraw/盤面/予算矛盾は別軸でfailed。強化正式資格はunknownを拒否するため、旧正常報告の過去CIも今回の証明として再利用しない。真正な同時取得の区間証拠が存在しない旧報告は、参考再解析または新契約での再取得が必要。

これは旧データを壊す変更ではなく、追加の保証に必要な証拠がないことを明示する意図的な資格移行である。旧データを無条件に現在の正式availableへ保つことと、実測区間の強化保証は両立しない。互換性方針は第9節で固定する。

## 6. Q3: 測定値とsummaryの正本

derived_measurementsのjoin keyはrun/pair/leg/role/command_id/genmove sequence。1成功genmoveにつき要求された測定が1件、重複・欠落・余分イベントは拒否する。source側player.budget_trace.measurements、game.budget.measurements、summaryはcacheであり、正式入力の正本でない。

contracts.reduce_observationsで新しい検証結果からcanonical_summaryを一度作る。evaluate.summarizeはこのreducerへのfacadeとし、保存game.budgetを正式測定として直接集計しない。sourceの全aliasとcanonical値を照合する。負数・NaN/Inf・boolカウント・数と平均/最大の矛盾はfailed。source値を直して成功にしない。

| 集計 | 対象・分母・扱い |
|---|---|
| wins/losses/draws・win_rate/point_rate | 合法終局かつ通信verifiedの局。予算不合格でも参考勝敗へ残す。失敗を敗北にしない |
| 全genmove外部RTT | 成功した要求の外部envelope。通常/pass/terminalを含む対象を固定。失敗要求は別の診断時間 |
| internal search all / normal | fresh rawから時間/対応を検証した測定。全phaseとnormalのみを別に集計 |
| internal数値の正本 | sample_count、sum_ns、max_ns。mean秒=sum_ns/count/1e9、max秒=max_ns/1e9。空のcount=0ならmean/maxはnull |
| B exemptで内部測定未要求 | internal metric status=not_required、count=0、mean/max=null。未知の時間を「0秒」と証明しない |
| 途中/未検証 | 参考観測を残してseries statusをunknown/failed/incomplete相当理由付きにする。正常測定の一部で全シリーズverifiedを主張しない |

正式対象では必要な内部シリーズが全予定測定を満たす。欠損測定を除外して平均を速くしたり、nを減らしてCIを作らない。参考prefixの表示と正式資格は別である。旧報告の不完全なcacheはhistorical_reportedとして残し、verified集計へ昇格させない。

取得時のsummary→inspection→summaryという循環を作らない。内部_observe_leg/core reducerはsummaryに依存せず原要求・盤面・rawから観測を作る。collectorはそこから最終報告のcacheを作り、その後public inspectがcacheを含む全整合性を確認する。checkpointの暫定summaryはreference_onlyであり、正式資格を与えない。

## 7. Q5と公開入口: 一つのAssessment

### 7.1 型・版を先に決める

decode_inputはroot object、schema型/対応版、report kind、conditionsの型、既知profile、games容器、解析引数の型を先に確認する。未検証snapshotはraw監査資料でありconsumerへ辞書保証付きviewとして渡さない。

- conditions=[]等のroot入力不正: input_status=invalid、統一reason code/path、統計unavailable。公開APIは構造化結果、CLIは2。AttributeErrorを漏らさない。
- schema=99等の未対応入力: input_status=unsupported、requested_profile=null、統計unavailable(reason=unsupported_schema)。profileを推測してnot_requestedにしない。
- 対応版と合法なsmoke/descriptive/deploymentであるとdecodeできた場合だけ、formal=not_requestedにする。
- decode後に読むartifactの欠損・未知trace/clockは品質unknown、既知内容矛盾はfailed。root入力不正とは別の検証結果で、必須要求なら終了1。
- 内部検証器の予期しない例外も明示internal_errorとして正式を停止し、単なるunknownや成功へ丸めない。

unknown/failedという通常の構造化検証判定は結果JSONの保存経路へ進み、必須要求なら保存後に終了1にする。結果を作れない検証器内部障害や保存I/O例外はoperation失敗経路へ進む。両者ともCIなしだが、入力2や「診断結果そのものを作れない失敗」と混同しない。

### 7.2 全公開経路

| 入口 | 修正後の経路・意味 |
|---|---|
| inspect_evaluation | decode→source snapshot/bytes→検証。正式資格を単独の保存boolで主張しない |
| validate_report | inspectを呼ぶ互換list[str] wrapper。空配列は正式資格の証明でない |
| statistical_eligibility / estimate / reanalysis_report | 毎回fresh inspect→同じassess_evaluation。保存statusを独自に読み直さない |
| paired | 両sourceをfresh inspect→同じassess_comparison→数式 |
| evaluate.compare_reports | analysis側共通compareへのfacade。現在の保存statusによる独自拒否/許可を削除 |
| analysis.comparison_report | sourceから共通compareを再実行する公開wrapper。callerのresultは資格に使わず、互換引数は再計算値と厳密照合して不一致を拒否。内部の結果組立てはprivate化 |
| evaluate / 両CLI | 取得済み正規報告または読込sourceを同じAssessmentへ。request_success/exitの共通規則を使用 |
| statisticsのpublic数式API | arithmetic_only、formal_eligibility=not_assessedを明示。eligible=Trueの既定値を資格として使う設計を廃止する。直接計算結果を正式報告builderへ渡せない |

公開報告builderはsource/解析条件しか正式根拠として受け取らない。保存Inspection、caller eligible=True、caller製CI、caller resultでformal/status/schema/lineageを上書きすることを拒否する。private helperは同じ呼出内の新しいcontextだけに使用し、publicな「検証省略」flagを作らない。数式の利用は残すが、同じstatus=availableだけで正式結果と誤解できる表現を移行する。

単独formal_eligibilityと対応差formal_pair_eligibilityは別。後者は両側適格性に加え元取得条件・固定B/資産・母集合/予定case・role seed・予算/時計・runtime/fingerprint一致が必要。同じsourceと同じrequest/specならどの正式入口も同じpredicateとreasonを使う。`comparable`という参考比較可否と`pair_statistics_available`を同義にしない。

確認済みN、予定n、全case/leg、全必要測定だけを数式へ渡す。全数幅0は実母集合全網羅・全適格性・固定得点前提が揃う場合に限る。time/deploymentは合法な別棋譜を許容し、同一保存局内だけ照合してCIをnot_requestedにする。

### 7.3 正式資格の必須集合（全公開入口共通）

入力valid、kind=evaluation、schema4、source整合verified、母集合/抽出/全予定coverage verified、全必要gameの合法終局/両通信verified、原必須状態のholdなしが共通の前提である。

| frozen profile/policy | A normal trace/内部区間/series | B normal trace/内部区間/series | 両host要求/startup/quit | probe |
|---|---|---|---|---|
| confirmatory equal-work | trace3・verified | trace3・verified | verified | A/Bとも実commandsとtrace3を検証 |
| confirmatory baseline-asymmetric | trace3・verified | 許可済みB budget exemptならnot_required。計測未要求を0秒と主張しない | Bもverifiedが必要 | B除外でもprobe証拠は必要 |
| deployment equal-time / budget必須 | 両time roleはtrace3・verified | 両time roleはtrace3・verified。許可済み非time B除外をequal-timeへ持ち込まない | verified | 正式固定得点probeを要求せずCIなし |
| smoke/descriptive・予算任意 | 任意項目のunknownを表示、正式なし | 同左。noneを勝手にexemptにしない | 正常参考集計にはhost通信証拠が必要 | 正式なし |

必要role/必要測定は既知契約から決め、sourceがA trace不要やB不存在と宣言しても弱めない。明示的な追加計測要求は要求集合を増やすだけ。一般require-budgetはそのpolicyの許可済みB除外を扱うが、deploymentはequal-time限定なので両time役割を免除できない。

正式対応差にはさらに両reportの上記資格と相互取得条件一致が必要。数学的な固定得点仮定は第13節の条件付き解釈を伴い、全ケース決定性の実証済みflagを捏造しない。

### 7.4 公開出力の境界

低水準の正常数式結果はcalculation_status=computed、result_scope=arithmetic_only、formal_eligibility=not_assessedとし、正式のstatus=availableを発行しない。不正ペア/算術条件は未計算または従来unavailableとして拒否する。旧eligible引数を残す互換wrapperを設けても資格として解釈しない。正式availableへの変換は共通Assessmentが検証済み入力から成功計算を得た場合だけ。

保存したcomparison/analysis JSONやcheckpointをevaluationと偽ってpublic builderへ渡せないようkindとsource linkを検査する。checkpointのreport_state=completeだけではevaluation資格を与えない。旧comparison_reportのresult互換引数は、検証済み再計算との完全一致確認にしか使わず、予約fieldの上書きを禁止する。

## 8. Q6: エラーphaseと保存

contractsに小さな共通ArtifactWriteErrorとwrite_report_exclusiveを置く。evaluate.EvidenceWriteErrorは互換aliasとして保持する。analysisからevaluateへwriterをimportして循環を作らない。

| 失敗 | 共通分類 / CLI |
|---|---|
| CLI/root JSON/型/版/解析引数不正、実行前に出力既存と判明 | InputError / 2 |
| preflight終了後の準備mkdir・原証跡保存・checkpoint・最終/比較/再解析JSON書込み失敗 | ArtifactWriteError(phase, path, operation_id, cause) / 1 |
| 正常decode後の必須artifact欠損/不整合、必須予算/正式統計不可、対局失敗 | Validation/RunFailure / 1 |
| 検証/計算/要求保存が成功、数値基準は未達 | success / 0 |
| 任意予算の参考要求で、正常な対局/参考集計に必要な軸のみ成功、予算はunknownまたは既知の非適格 | reference success / 0、品質と非正式を明記。必須flag/profileを弱める経路ではない |

予算不適格でも参考勝敗は保存できるが、source内の改変矛盾を通常の参考成功として隠さない。reanalysis/compare/evaluateの成功規則は入口名ではなくRequestSpecの必要軸で決める。任意の予算状態とroot入力/source整合性の失敗を混同しない。

preflightは入力検査。operation_startedはその終了直後・最初のartifact操作前に設定する。Popen前の準備I/O失敗も1。根本分類を保持し、例外が起きた行だけで2へ変えない。公開Python APIはtyped失敗/構造化判定を返し、SystemExitはCLIだけで使う。

writerは全serialize・open・write・flush/fsyncを捕捉する。最終JSONは新規exclusive作成を維持し、実行後に同名ファイルが現れるraceも上書きせず1。checkpointは所有するrun領域だけを既存の一時書込/replaceで更新する。finalをreplaceで無条件上書きしない。最終ファイルの原子的公開までを今回の保証にはしない。途中ファイルはpartialとして診断し、無条件削除・完成扱いをしない。

保存失敗時はprocessをfinallyで回収し、既存の有効checkpoint/原traceを保つ。checkpointへoperation_state=failed、failure_phase、出力path、原因を書ける場合は追記する。checkpoint自体も失敗したら最初の原因を残した構造化stderrを必ず試し、二次失敗も明記する。report_state=completeは取得/解析終了であり最終JSON保存成功ではない。両軸を別に表示する。

保存成功と統計資格を混ぜない。完全な原証跡が後で明示再解析できることと、元の保存依頼が成功だったことは別。partial JSON/欠損証跡は正式へ通さず、元失敗を新しい成功履歴へ書き換えない。hard kill/停電で診断を必ず残せるとは保証しない。

| 対象 | 方針 |

## 12. 実装順序と段階的な安全策

1. **D0 凍結と赤い回帰**: source/証跡hash・基準結果を保全し、R01/R04/R06/R11/R13/R16とR18/R19を先に追加。既存失敗と新規失敗を区別する。
2. **D1 入力・必要集合・判定核**: decode、role集合、共通集約、原状態hold、Assessment/RequestSpecを実装。入口から保存状態の独自判定を外す。移行中に新契約formalを許可しない。
3. **D2 観測契約とproducer**: schema4/trace3、Player ns、clock、command index、probe commands、fixtureを同時に実装。seed adapterを取得manifestへ登録する。新旧parserを混ぜて旧証拠を補わない。
4. **D3 検証とreducer**: 区間・raw・source alias・summaryの検証、partial/referenceとcertifiedの区別。取得とreplayで同じpure coreを使う。
5. **D4 全正式入口閉鎖**: 数式scope/builder/compare/reanalysis/CLIを共通Assessmentへ接続し、全R18/R19 matrixを通す。ここで初めてschema4正式資格を有効化する。
6. **D5 保存・失敗phase**: 全writer/catch/cleanup/exitを統一してR16/R17を確認。入力2・開始後1・数値未達0を区別する。
7. **D6 総合と資料**: 関連pytest→全体→独立smoke→小数fixture取得/保存/再解析/compare、旧bundle互換、AST依存循環を確認。A/B/C・契約・利用手順・記録をコードと同時に更新。明示依頼なしにcommit/pushしない。

D2～D5が未完なら強化formal gateは閉じたまま。赤いテストを期待値の緩和で消さず、途中の限定的な成功を正式完成と呼ばない。モデルで矛盾が出たら本書を修正し、モデルと同じrevisionへ合わせる。
