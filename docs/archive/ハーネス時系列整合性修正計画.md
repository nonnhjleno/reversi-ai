## 4. 推奨する修正方針と時計の前提

新measurement_contract名を`local_cpython313_perf_ns_lifecycle_v2`とする。これは現在と同じ対応環境に限定した**将来の登録名**であり、他OS/時計の対応拡張を含めない。

同一取得runを実行する親で比較scopeの`clock_domain_id`を一度作り、子にも渡す。schema4のPlayerごとのUUIDとは意味が変わるため版を分ける。新しい`process_session_id`が各Popen試行を識別する。domain token一致だけで検証済みにせず、親子descriptor、親の同一local起動経路・run、sessionへの結合、対応契約をすべて要求する。PIDは診断補助であり再利用されるのでidentityの正本にしない。

保存済みの時計記述を、再解析マシンの現在の時計へ書き換えない。検証器が対応する**元の取得契約**で判定する。別runや別host間の絶対端点差は算出しない。比較評価は独立に検証した経過時間・得点を使う。

`Popen`戻りは初期化完了のbarrierではない。SP=spawn直前、PR=Popen戻り、CE=子の最初の計測hookとしたとき、SP≤PRとSP≤CEは要求するが、**PR≤CEもCE≤PRも必須にしない**。MicrosoftのCreateProcess資料も初期化待ちではないことを明記する。[CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)

時間単位は整数nsだが1ns精度は保証しない。Python公式の同一process間時計・単調時計・整数nsの説明を根拠に、対応済みlocal時計だけを比較する。resolutionは診断であって許容逆転幅ではない。同時刻を許す`<=`を使い、逆転を大きなepsilonで救済しない。[Python 3.13 time](https://docs.python.org/3.13/library/time.html#time.perf_counter_ns)

**精度に関する設計監査での補正:** Microsoftは異なるthreadで採ったQPC値の±1tick近傍を順序曖昧としている。同一threadの順序検査と親子の検査を一律の数値比較にしない。[QPCの時刻比較](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

- 同一計測threadのイベント: 整数`<=`を厳密に検査し、同値/0経過も許す。今回の親showboard/quit/要求間逆転はこの検査でfailedとなり、救済しない。
- 異なるthread/processの辺: 対応domainに加え、起動時にQueryPerformanceFrequencyから得た正の整数`qpc_frequency_hz`をdescriptorへ保存し、親子/元runtimeで一致を確認する。`U=ceil(1_000_000_000/frequency)+1`nsを、1tickと整数ns変換差の保守的上界とする。後点−前点が`>U`なら数値順序verified、`<-U`ならfailed、`[-U,U]`なら`unknown: clock_order_ambiguous`。Uは利用者が緩める猶予ではなく、曖昧な値を**正式へ通さない**ための判定境界である。
- この上界はQPC→整数ns変換の丸め幅も前提とする。今回[CPython 3.13.5のpytime.c](https://raw.githubusercontent.com/python/cpython/v3.13.5/Python/pytime.c)のpy_get_win_perf_counterと_PyTimeFraction_Mulを照合し、非負tick・overflowなしの整数商による変換から誤差差分1ns未満と判断した。実装時は対象runtimeもこの登録前提を満たすことを確認し、未確認の版/変換はunknownのままにする。周波数欠損/未対応もunknown、不正型や既知値の不一致はfailed。
- 親の計測はcollectorの単一thread、子の計測はproducerの単一threadに固定し、`measurement_thread_id`をlifecycle/headerへ記録する。thread IDはclock descriptorの同一性項目に混ぜない。threadを跨ぐ計測に拡張する場合はイベントごとの所属を必要とし、同一threadと推測しない。
- 曖昧な親子辺がある場合、単純な`search_ns <= wire_ns`の僅差違反だけを追加の確定矛盾にしない。各同一thread区間の端点差・alias・期限は厳密に検査し、親子包含の派生不等式は辺の検証後に適用する。時刻の丸め直し・補正・並べ替えは行わない。

この補正は現行のゼロ猶予の親子比較を強化設計で置き換えるものである。正常動作でも証明に足りない小差は正式保留になり得るが、物理的矛盾と誤判定しない。遅延を挿入して通す、epsilonを拡大してverifiedへする、別時計をこのUで比較する設計ではない。

## 5. 追加・変更するデータ契約

以下は追加フィールド案。dictと既存JSONLを拡張し、新しい抽象クラス/保存ファイルは原則増やさない。新フィールドも一呼出内の同一bytesからhashと意味を検証する。

### 5.1 親のProcessEvidence

games[].players[label]およびdeterminism.attempts[]に同じ`lifecycle`構造を持たせる。

| 項目 | 生成元・規約・保存 |
|---|---|
| run_id / pair_id / leg / player / purpose | collectorの期待context。purposeは検証側が格納位置からgame/probeを決め、自己宣言と照合 |
| process_session_id | 親がPopen試行前に採番するUUID。失敗試行でも残す。同一run内で重複不可 |
| process_generation | 同一論理slot `(run,purpose,pair,leg,player)` の試行番号、非負整数。現行方式は常に0。将来再試行しても新sessionが必要 |
| pid | Popen.pidを戻り後に記録。子のgetpidと照合可能だが時刻・session証拠の代わりではない |
| clock_domain_id / host_clock / measurement_thread_id | runで共有する比較scope token、QPC周波数を含む親descriptor、親計測threadのID。子header/全host commandsと所属を照合する |
| spawn_before_ns / popen_return_ns | Popen呼出直前 / 戻り直後に親が実測。失敗時はreturnを補わずspawn_failure_nsと原因 |
| startup_end_ns | 従来どおり初回nameのHE1。readyやモデル完了時刻への意味変更は禁止 |
| exit_observed_ns / exit_code / termination_kind | 親がwait/pollで初めて終了を確認した直後。normal_quit / unexpected_exit / killed / spawn_failed等。既存quit aliasと一致 |
| abort_requested_ns / cleanup_end_ns | 実行された場合だけ実測。kill要請と終了確認、pipe回収を区別し、探索/quit応答へ足さない |

現行のplayer.spawn/startup、name.spawn、quit.exit aliasは移行時も照合する。重複値を黙ってcanonical値へ修復しない。各commandのidentityにsession/generationを追加し、新command_idは`[run,purpose,pair,leg,player,session,generation,index]`のcanonical JSON。indexはsession内0から欠番・重複なし。genmove sequenceは別に維持する。

**再起動を新機能として実装しない**。同じleg/probeを途中再起動で継続して正式成功にすることは禁止する。将来の再試行は別契約が必要。それまで同一slotの複数generationは失敗/参考履歴として保存し、正式coverageを成功分だけに縮めない。

### 5.2 子のtrace4

- config header: 現行config/target/model/contextにsession/generation/purpose/case_id/role_seed/pid、child descriptor、`child_entry_ns`（CE）、`protocol_ready_ns`（IR）を追加する。case/seedは既存の派生規則と照合するだけで、乱数利用の証明ではない。
- CEは対象producerで最初に計測した点。OSプロセスの正確な生成時刻でもPython起動開始でもない。IRは盤面・入力処理系を準備して最初のstdin取得に進める点。「全モデルの準備完了」と同義にしない。
- init計測scopeはCE〜IRに含まれる対象の初期化。対象がモデルをimport時に読むならCE hookをその前に置く必要がある。計測より前に起きたloadを0秒・CE時刻で補わない。seed adapterは現状起動時計を記録しないので、無変更のadapterを証拠生成済みと扱わない。
- name/ask/play/showboard/resultにも`type=command`のCC（stdin行取得直後）/CR（結果決定後・出力前）/command_index/command_id/実コマンドを保存する。host応答は既存の形式検査・盤面再生が正本。genmoveは既存`type=genmove`に同じenvelopeと探索計測を載せ、二重にcommandイベントを出さない。
- quitもcommandイベントを出すがCCのみ、通常応答を捏造しない。最後に`type=process_exit_ready`のCS（quit処理終了後、trace close/return前）と最後のcommand_idを記録する。CSは終了準備点でありOS死亡時刻ではない。
- JSONLのイベント順はconfig→全command/genmove→quit→exit_ready。ヘッダ以降をすべてgenmoveとする現行`events[1:]`処理は型別dispatchへ変更する。余剰・二重・未知イベントを黙って読み飛ばさない。未知拡張はunknown、既知版の重複/順序違反はfailed。
- stdoutプロトコルは不変。trace作成・flushはsearch外だが外部応答時間に入る。計測コストが増えるため、旧取得fingerprintと同じ性能条件とは扱わない。

### 5.3 model loadと適用除外

モデルなしは従来の明示not_required。startup loadは**CE≤load_start≤load_end≤IR**に包含し、必要なら最初のgenmoveよりずっと前でもよい。初回nameのHSより前/後のどちらもあり得る。command内loadはCC〜CRに包含し、当該searchで使うモデルはload_end≤SSを要求する。初期化時間をsearch_elapsedへ加算しない。

headerで初期loadを証明できないlazy初期化、name後の自律的background load、GPU非同期などは現行でも十分な契約がない。T1ではそれらの計測方式を新規実装せず、**未対応scope=unknown**として保存する。物理的に不可能と断定しない。一方、「このsearchが使用したモデルのload完了」がSE後と明示される既知依存矛盾はfailed。対応拡張には別途scope定義・同期証拠・テストが必要。

**予算B除外とライフサイクルは別軸**。新強化正式評価では全A/B・必須probeのhost/child lifecycleと全command envelopeを要求する。許可済みbaseline-asymmetricのB通常genmoveは内部SS/SE/counterだけnot_requiredにできるが、trace4のCC/CRと起動/終了証拠は必要（この場合type=command）。Bのprobeには従来どおり内部計測も必要。producer非対応でも通常の外部対局は可能、強化正式資格だけunknownで保留する。exemptをtiming.verifiedへ直接写す現行処理は廃止する。

## 6. 時系列の不変条件と状態

### 6.1 必須の部分順序（新契約）

比較可能な同一domainとidentityを確認した後にだけ親子端点を比較する。親のみ/子のみの既知矛盾は独立して収集し、他軸unknownがあっても消さない。

| ID | 不変条件 | 所有者・根拠 |
|---|---|---|
| T-ID | run/slot/session/generation/commandが親・raw・予定contextで一致。sessionはrun全体で一意 | contractsの原資料対応、protocol.command_id |
| T-CLK | 対応clock契約と同一run domain、元の親子descriptor/QPC周波数一致。同一threadは厳密、異threadの1tick近傍はunknown | protocol.clock_statusと順序helper。第4節の分類。UUIDだけは証明でない |
| T-SP | SP≤PR≤HE0[0]。全host要求のHE0≥PR。startup_end=HE1[name] | protocolの逐次Popen→name実装。旧4は存在するSP下限のみ検査 |
| T-INIT | SP≤CE≤IR≤CC[name]。IRとHS[name]、CEとPRの相対順は**要求しない** | 子入力準備後にstdin取得、親はその前にpipeへ送信可能 |
| T-CMD | 通常全要求: HE0≤HS≤CC≤CR≤HR≤HE1。genmoveはCC≤SS≤SE≤CRも要求 | 既存要求内包含を全コマンドへ拡張 |
| T-SERIAL | 全隣接要求で前HE1≤次HE0。最後がquit、quit後に要求なし。子前CR≤次CC | 同一Playerは常に同期。quitの終点だけEOを使う |
| T-EXIT | 正常quit: HE0q≤HSq≤CCq≤CS≤EO。全子イベント≤CS、全通常host終点≤HE0q≤EO | CSは死亡前、EOは死亡後観測。shutdown後の入力処理は禁止 |
| T-LOAD | startupはCE〜IR、commandはCC〜CRに包含。当該モデル利用ならload_end≤SS。差は実測差 | search_budget。未知scopeと既知依存逆転を区別 |
| T-DIFF | search=SE−SS、wire=HR−HS、external=HE1−HE0。各同一threadの差・整数型bool除外・非負・既存期限/alias一致。親子包含の派生比較はT-CLKも要求 | protocolとsearch_budget。丸めた秒から端点を作らない |
| T-CAUSE | 実際に同期しているA/Bの因果辺も親時計で確認 | contractsがcollectorの呼出順テンプレートから再構築 |
| T-GATE | 全必須temporal軸verifiedかつ既存母集合/trace/予算/coverage等も成立しなければ正式不可 | contracts観測→analysis共通判定。失敗legを削らない |

T-CAUSEの対象は、game内のA初回name完了→B spawn、初期/着手後check_stateのA/B順、actor genmove完了→peer play開始（passではplayなし）、各同期確認の完了→次着手、最終検査→A quit→B quitである。_command_contextsの期待列にこれらの辺を保持し、記録時刻で順番を並べ替えて正当化しない。probeは別テンプレートで非終局完了を許す。別leg/probeを並列化する契約はないが、T1では互いの独立sessionを任意に全順序化せず、必須のデータ依存辺だけを検査する。

表の`<=`は因果的に保証すべき関係。異threadの観測値からそれをverified/failed/unknownへ写す際は第4節の規則を使う。T-SP/SERIAL/CAUSEは同一親thread、T-INITのSP→CEやT-CMDのHS→CC/CR→HR、T-EXITのCS→EOは異threadとなる。

異常終了ではEOより後の**子側で実行されたイベント**は不可能だが、親がpipeに既にある出力を読むことはあり得る。正常完走T-EXITをそのまま異常ログへ強制しない。timeout後のkill・遅れた終了観測・reader回収は失敗診断として許し、正常quit成功を合成しない。poll/waitで初めて確認した終了点を保持し、abortの後の観測で過去の上限を広げない。

### 6.2 状態の直積

`execution`（not_started / running / complete / failed）と`verification`（verified / unknown / failed）と`publication`（saved / failed）は別軸。completeは合法終局/正常quitの実行主張であって時間検証済みを意味しない。statistical statusと最終採用decisionも別である。

- **failed**: 対応済み時計で確定できる順序矛盾（第4節）、明示されたID混在、既知版の不正型/重複、差不一致、期限違反。reasonにはpath・slot・command ID・左右の点/値・不変条件IDを記録する。
- **unknown**: 欠損した新証拠、未対応時計/trace/scope、時計精度上の順序曖昧、未取得の子終了点、別検査のためまだ検証していない区間。空集合をverifiedにしない。
- **verified**: 要求された全集合について検査完了した場合のみ。既知矛盾があればfailedを優先し、unknown理由も残す。
- **not_required**: requirementsで事前に決める内部counterなどだけ。lifecycle全体や未起動roleに使用しない。

時間検証は`timing={status,host_lifecycle,child_lifecycle,command_intervals,causal_order,reasons}`へ集約。game/probeで同じ関数を使う。budgetがexempt/verifiedでも時間のunknown/failedは残す。原状態・cache・summaryとの矛盾はsource_consistencyへも出し、新しい検証で保存値を黙って訂正しない。

## 9. 既存schemaとの互換性

- 新取得evaluation=5、raw trace=4、validation=3、analysis/comparison出力=5を予定。budget config=2、population/case/pair/seed規則は維持する。条件のmeasurement契約と取得fingerprintは新規になる。session/domainの実際のUUIDは実験条件やanalysis specへ混ぜない。
- 旧1〜4は読み取り・過去結果の表示・可能な参考再解析を維持する。旧4にあるSP/要求/quitを使う矛盾検査は先に実施するが、PR/CE/IR/CSの欠損を補えないので、検査が通っても強化lifecycleはunknown。旧4が全てfailedという意味ではない。
- 新旧とも確認できた矛盾はfailed、不足はunknown。未対応root版は入力unsupported、読める旧rootの不足traceは品質unknownであり入力不正とは異なる。
- 原JSON/trace/hash/過去CI/失敗履歴を更新しない。再解析は新しいファイルに元取得版・source hash・現検証版・状態/理由を記録する。出力schema5だけで元source4が新取得能力を得ることはない。
- 正常な外部対局、GUI、課題stdout形式は維持する。ただし旧正式資格の無条件維持と新しい起動証拠の必須化は両立しない。新強化正式評価には再取得が必要であり、その費用とB/実AIproducer対応を移行条件として明記する。
- 異なる版/取得条件のbefore-afterを「同条件」として比較しない。保存場所の移動はhashと原identityが同じなら引き続き許す。時刻を移動先runtimeで再生成しない。
