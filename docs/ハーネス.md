# リバーシ検証・評価ハーネス

## 開発用の短時間フィードバック（A/C実装契約）

既定の`python -B tools/quality.py`はFull専用で、従来10工程に本番strict登録の必須typing_scopeを追加する。Quick成功をFull成功として報告しない。

```text
python -B -m tools.feedback --base origin/main
python -B -m tools.feedback --profile quick --base origin/main
python -B -m tools.feedback --profile standard-ai --base origin/main
python -B -m tools.feedback --profile quick --measure-profile
python -B -m tools.feedback --profile standard-ai --measure-profile
python -B -m tools.feedback --verify evaluation_results/feedback-<run>
```

### 全Phase共通の新規テスト方針

各開発Phaseで新たに作成したテストは、Phase終了時のレビューまではFullのみで実行する。Quick／Standardへの追加は、テストの検証目的と実行時間を確認した後に判断する。Fullは全pytestを実行するため、新規テストをFullから除外しない。

現行の自動選択は変更されたファイルや登録済みnodeidを基準にするため、既存のQuick／Standard対象ファイルへ新しいテストを追加すると、レビュー前でも短時間プロファイルに含まれる場合がある。Phase終了前の新規テストは別ファイルに追加し、Phase終了時に必要なものだけQuick／Standardへ登録する。Phase 2をこの運用の初回試行とし、終了時に所要時間と分類作業の負担を確認する。

既定profileはauto。base→HEAD、HEAD→index、index→作業ツリー、未追跡の和集合で分類する。既存ai_engine.py/test_ai_engine.pyの変更だけならQuick、その他の既知AI・盤面・入出力テストの変更はStandard_AI。共有基盤/設定/docs/未知/追加/削除/rename/競合/Git不明はFullへ戻す。明示quickも未知変更のFullを迂回しない。`--measure-profile`には明示quickまたはstandard-aiが必要で、独立計測専用（差分の安全認定ではない）。補助feedback.jsonは常にFull未合格を保持し、fallbackしたFullの合否は別quality.jsonを参照する。routing.jsonには層別変更と要求・推奨・解決profileを残す。

QuickはAI/盤面/入出力、軽量な契約/型境界と補助runner回帰。Standard_AIは加えてschema5保存CLI・正常正式入口・対局同期・終了/通信失敗・期限を実行する。全異常trace改変や重いmypy自己テストはFullに残る。全collectionから予定したnodeidと実行journal/JUnitを照合し、未選択とskipを区別する。skip・空・欠損は補助PASSにしない。

出力はUUID別のevaluation_results/feedback-*。元journalを変えず参照bytesを同run内へ保管するので、元pytest一時領域消失後も再照合できる。明示削除まで残すがバックアップは別途必要。再検証の欠損/改変は失敗として報告する。本番scopeはharness/reversi_player/tools、web.pyだけをstrict例外とし、旧reversi_01.pyと棋譜閲覧data.pyは利用者確認済みの保管/参考用途である。

CIはmain push・PR合成merge・merge_group・手動実行でFullを実行し、feature push単独の重複を除く。PRがないfeatureはローカルfeedbackか手動Fullで検証する。PRのdocs/未知変更やdraftでFullを省略しない。quality jobはFull専用で、ローカルQuick成功を必須チェックへ流用しない。pytest診断とrun配下のquality/evidence/JUnit/journal/logsをartifactへ7日保管する（mypy-cacheは除く）。run外の一時原証拠の全コピーや恒久保存は保証しない。mainのPR必須・strict quality必須のサーバー設定と実CI確認は[C実施記録](reports/20261020_quality_ci_implementation.md)を参照する。YAMLだけでは保護設定の適用を保証しない。

更新日: 2026-10-13。現行はevaluation/analysis/comparison schema5、trace4、validation3。ここには**現在の操作手順と結果の読み方**を置く。過去の実行件数・修正経緯・旧版の手順は履歴資料へ分離する。

## 2. 準備・テスト・GUI

プロジェクトのルートで実行する。本体・GUI・ハーネスはPython標準ライブラリを使い、テスト・品質検証は `requirements-dev.txt` の開発依存を使う。確認済み環境の詳細と実行件数はreportsを参照する。正式な親子時計照合の対応契約はlocal CPython3.13/Windows/QPCに限定され、他環境で起動できることと正式資格は別である。

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m pytest -q -m smoke
```

全体テストと独立smokeをそれぞれ1コマンドで実行できる。通常のpytestに大量のAI性能評価は含めない。失敗時はtest名、入力・期待値・実際値とtracebackを読み、必要なら `python -m pytest -vv tests/test_harness.py -k テスト名の一部` で絞る。実行件数は拡張で変わるため固定の合格件数にはしない。

### 開発用の統合品質ゲート

直接インストールしたCPython3.13.5 / Windowsで、ルートから以下を実行する。

```powershell
python -c "import sys; print(sys.version); print(sys.prefix == sys.base_prefix)"
python -m pip install --user -r requirements-dev.txt
python -B tools/quality.py
$LASTEXITCODE
```

最初の確認は3.13.5とTrueが必要。WindowsのvenvランチャーはPopen PIDと実AIのPIDが異なるため正式fixture回帰に未対応であり、venvを有効化したまま実行しない。対応しない環境やtool版は、検査不能として終了1になる。CIは同じコマンドをWindows/3.13.5で実行する設定で、remote実行の確認とローカル成功は区別する。

gateは環境・モデル照合、pip check、Ruff lint/format、strict mypy、全pytest（性質試験とgate故障試験を含む）、独立smokeを直列実行する。全必須成功と保存成功だけが終了0。不在・nonzero・timeout・未実行・モデルずれ・保存失敗は終了1。既存失敗を対象外にして成功扱いする機能はない。
毎回新しい`evaluation_results/quality-UUID/`へcommandログとquality.jsonを保存する。全pytestとsmokeは別ディレクトリへ標準JUnit XML・段階別events.jsonlを自動保存し、evidence.json/evidence.mdも生成する。旧9検査に必須evidence検査を加え、終了0でもXML/記録の欠損・破損・対応不一致・保存不能はgate失敗。各終了値・実行時間・環境版・対象source hash・モデル不一致理由を読む。既存評価結果を上書きしない。quality.jsonは評価schema5ではなく、passedも正式AI評価資格・強さの証明ではない。

lintはharness/reversi_player/tests/tools、formatは独立ルール/seed adapter/新しい品質コード・試験からの段階導入。未整形の動的ハーネス・本体・GUI・既存大規模テストを同設定に列挙する。strictは従来の13moduleにreversi_player.ai_engine（Phase 1A）、harness.__init__・tools.__init__・tools.feedback（品質監査A）を加えた17対象とする。正規リストはpyproject.tomlのtool.mypy.filesで、必須typing_scopeが本番inventoryとの一致を検査する。reversi_player/web.pyは2026-10-16方針により意図的なstrict対象外（Phase 3は非PASS）とし、他の本番コードへ例外を広げない。型は原証拠の検証や正式資格を代替しない。openingsの履歴positionはobjectとして扱い、形状・値域・合法性を既存の実行時検査で確認する。生成metadataとprotocolの旧時計metadata/自由拡張lifecycle、search_budgetのsearch metadata/途中測定値も未検証のobjectとして扱う。protocolは承認済みのpipe境界検査とsys.platform分岐を導入し、終了時刻の静的ビューだけにcastを限定する。search_budgetも承認済みの既存述語の型ガード化と局所再束縛を行い、castは6か所の既存演算/型関係だけに限定する。contractsは通常形状と未検証objectを分け、原report/trace全体のcastを使わず、既存33＋Phase 9の反復/座標/保存path境界4の37か所の局所ビューを回帰で固定する。analysisは数値/既存method/認証済み分岐のscalar等10か所、statisticsは既存属性操作2か所だけのビューとし、未検証field/IDをobjectで共有する。原算術辞書をコピーせず、既存の得点演算の動的境界も拡大しない。理由・command列の読み取り専用注釈は直接依存と共有し、原データや検証順は変えない。採時順・期限定義・不正値の再検証は維持する。教員配布のweb.pyは変更/拡張を原則予定しないためstrict化を実施しないが、既存LintとGUI関連テストは維持する。将来の機能追加/大規模修正時はstrict化を再検討する。formatの対象拡大は今回行わない。設定はpyproject.toml、導入根拠・検証証拠・未確認事項は[QUALITY_PROGRESS.md](QUALITY_PROGRESS.md)。 Phase 9でevaluateも常設対象へ追加し、局所ビューは8か所へ限定。取得途中のNone・部分親証拠・原artifactの未知値を保持し、必須の取得検査結果型を弱めない。既存update/反復/添字と数値基準の局所ビューだけで接続し、全report/traceをcastしない。検証結果は進捗Phase 9を参照する。

**strict範囲の変更ルール（2026-10-16）**: 対象の追加・除外は理由、対象パス、用途、影響範囲、承認根拠と検証を記録する。web.pyだけの例外は、Lint/GUIテストの免除やGUIフォルダ全体の免除ではない。Phase 3は「意図的な対象外」でありPASSではない。方針の正本とPhase 10の最小設計は[QUALITY_PROGRESS.md](QUALITY_PROGRESS.md)の現行strict方針を参照する。

A導入時の現行状態: 必須typing_scopeは実装済み。本番3ルートの全.pyと明示strictを照合し、未知Python配置・stub・未承認の除外/抑制を拒否する。strictは既存14＋initializer2＋feedbackの17対象。web.pyのLint/GUIテストは維持し、strict例外は同ファイルだけ。旧reversi_01.pyと102400-games/data.pyは利用者確認済みの保管/参考用途で、実利用時は再分類する。本番を依存/生成物等へ偽装配置する意味まで自動判定する認証機構ではない。

mypyはexplicit_package_basesで本体をreversi_player.reversiとして解決する。実行時のimport構造は変えず、型チェック用の__init__.pyは追加しない。本体のPos.__eq__は既存の非bool/duck typing/属性例外を保つ限定的な動的境界であり、他の関数へAnyを拡大する変更は回帰で検出する。strict成功はその動的比較まで完全な静的保証を得たことを意味しない。

証拠は次のように読む。evidence.mdは全テスト結果と重要チェックの期待/観測、evidence.jsonはmanifest（Git commit/dirty・ソース/モデル/仕様hash・環境・実argv）とstep/test ID、phase、診断、原参照を保持する。全体とsmokeの同じtest IDもexecution IDが異なる。一般テストの内部期待値/実測は未収集と明記し、成功重要テストだけ明示登録を必須にする。負例の想定拒否はテスト成功、skipはpassedと別、setup/teardown失敗はerror、中断はinterrupted。

```powershell
python -B -c "from pathlib import Path; from tools.evidence import verify_publication; print(verify_publication(Path('evaluation_results/quality-対象UUID')))"
```

`[]`は保存証拠・quality完成marker・参照bytesに検出した不一致がないこと（正式AI資格ではない）。quality.jsonのpassedと収集状態も読む。JSONのquality_report_sha256と最後に保存したquality.jsonが一致しない、または参照先が消えた場合は部分証拠/再確認不能。原trace/checkpointはコピー・修復せず参照するため、pytest一時領域の証拠は後日消失し得る。実argvのJUnit先は既存owned領域なのでそのまま再利用せず、再検証は`python -B tools/quality.py`で新領域を作る。個別再現argvはJSONにあるが、全assert/localや全Hypothesis成功例は収集しない。秘密metadataは拒否するが、原ログの全匿名化・停電/強制停止の完全保存は保証しない。CI artifactの範囲と保持制限は本書冒頭のC契約を参照する。

## 3. 独立プロセスの参考対戦

既存結果と重ならない名前を使う。以下は現在のランダム版同士の動作確認であり、正式な優越性評価ではない。

```powershell
$run = Get-Date -Format 'yyyyMMdd-HHmmss-ffff'
python -m harness.evaluate --a reversi_player/reversi.py --b reversi_player/reversi.py --games 2 --seed 20261009 --evaluation-profile smoke --output "evaluation_results/smoke-$run.json"
```

`--games` は2以上の偶数。2局で1ペアとしてA/Bの黒白を交換し、同じ役割のseedを保持する。毎局A/Bを別プロセスで起動する。着手側のgenmoveが自身の盤面を更新するため相手だけにplayを送り、双方のshowboardと独立盤面を照合する。合法手なしはgenmoveのNGで検査し、仕様にないpassコマンドは送らない。終局では双方のresultも照合する。

不正手、余剰stdout、形式・盤面・結果の矛盾、timeout、異常終了は失敗局として保存し、相手の勝利に変換しない。勝率は勝利数÷正常完了局数、勝ち点率は（勝利数＋引き分け数÷2）÷正常完了局数。分母0はnull。失敗・未検証状態を伴う率だけで採用しない。

## 4. 固定序盤・設定・評価プロファイル

候補に依存しない母集合を生成し、合法性・重複・hashを検証する。下記コマンドは必要な場合の例であり、整理作業の一環として実行するものではない。

```powershell
$set = Get-Date -Format 'yyyyMMdd-HHmmss-ffff'
python -m harness.openings generate --count 1000 --placements 8 --seed 20261009 --purpose development --output "benchmark_sets/development-$set.json"
python -m harness.openings validate "benchmark_sets/development-$set.json"
```

`--purpose held_out` は最終判定用の区別。`--exclude-openings PATH` を繰り返して他集合との対称重複を除外できるが、未閲覧・学習非混入を自動保証するものではない。生成seed、抽出selection seed、AIのmaster seedは別の意味を持つ。

固定序盤では2局ごとに1ケースを非復元抽出し、両AIへ同じ序盤をplayで適用する。Nは保存母集合の検証済みentries数から得る。`--games` 省略時は初期盤面で2局、固定序盤で全N件の2N局。短い確認では必ず `--games 2` を明示する。

探索予算設定JSONの例（新しいAI側が受領・計測を実装する必要がある）。

```json
{
  "format_version": 2,
  "budget": {"kind": "nodes", "limit_nodes": 100000},
  "search": {"deterministic": true, "counting_definition_id": "negamax-node-v1"}
}
```

`--a-config PATH` / `--b-config PATH` で各役割へ設定する。format1も入力互換として扱い、保存はformat2へ正規化する。timeのformat2は正整数 `limit_ns` を使い、内部探索時間と全応答時間を別にする。counting_definition_idは計数の定義を特定する名前であり、名前を書くだけで実装の真正性は証明できない。

ハーネスは設定・trace先・contextを環境変数で渡す。producerには有効設定、全要求、子lifecycle、genmoveの探索・盤面・応答などのtrace4記録が必要。単にJSONLや設定が存在するだけではverifiedにならない。

| profile | 用途・主な条件 |
|---|---|
| smoke / descriptive | 動作確認・参考対局。実AIの内部証拠unknownと参考勝敗を区別 |
| confirmatory | 固定有限母集合での正式固定得点評価。明示games/openings/selection seed、固定nodes/depth、決定性、必要証拠を要求 |
| deployment | 双方time予算・equal-timeでの実行品質確認。固定得点の正式CIとは別 |

policyはdescriptive / equal-work / equal-time / baseline-asymmetric。confirmatoryはequal-workまたは宣言済みB noneのbaseline-asymmetricを使う。Bの許可済み内部予算除外はB子lifecycle・両host・決定性probeを免除しない。confirmatory開始前の2回probeは有限の再現性確認であり、全局面の決定性の証明ではない。

次は**未作成の候補・baseline・設定パスを置き換えて使う書式例**であり、現在の実AIへそのまま指定して正式合格する手順ではない。

```powershell
python -m harness.evaluate --a candidate/reversi.py --b baseline/reversi.py --openings benchmark_sets/development.json --games 20 --selection-seed 20261010 --seed 31 --a-config candidate/eval-work.json --b-config baseline/eval-work.json --evaluation-profile confirmatory --budget-policy equal-work --output evaluation_results/candidate-new.json
```

## 5. 時間計測・終了

起動指標はPopen直前から初回nameの形式確認完了までで、OS起動だけでなくimport・初期化・初回nameを含む。初回nameはstartup期限（既定5秒）。その後は通常コマンド1秒、genmove10秒、quitの正常終了1秒を既定とし、各timeoutオプションで変更できる。

外部応答はHE1−HE0、wireはHR−HS、内部探索はSE−SS。親子の整数ns端点・時計domain・run/session/generation/commandを照合する。Popen戻りより早い子開始や、name送信後に初期化完了することは正常にあり得る。モデル読込・trace書込・盤面更新・OS待ちをsearch_onlyへ混ぜない。詳細は[時計契約](harness_contracts.md#temporal-invariants)を参照する。

平均・最大の全genmove応答にはパス・終局問い合わせも含む。内部全genmoveとnormal_moveの集計は別で、traceなしの実AIでは内部値はnull/unknown。計測時間は各実行で変動する。

protocolはstdout/stderrを別スレッドで読み、必要行と期限を管理する。子に `-u` を付けず、本体のflushも検証する。異常時はWindowsで自身のPIDのprocess treeをtaskkillし、必要ならkill・waitへ移る。POSIXは独立process groupを終了する。正常quit証拠をtimeout/killから補造しない。

## 6. 保存・再解析・比較

評価JSONには条件・runtime・本体/明示資産/取得コードhash、全要求、棋譜・盤面・勝敗・診断・測定を保存する。raw trace・母集合・checkpointは隣の `runs/<run_id>/` に保存する。**JSONだけでなく証跡ディレクトリも保管する。** 出力は排他新規作成で、既存結果を上書きしない。途中checkpointのcompleteと最終保存成功は別である。

モデル・engine・設定は `--a-asset PATH` / `--b-asset PATH` へ繰り返し明示登録する。全importは自動登録しない。固定Bは依存を含め独立保存し、hashだけで復元できると思わない。

```powershell
python -m harness.analysis --report evaluation_results/before.json --output evaluation_results/before-reanalysis-new.json
python -m harness.evaluate --compare evaluation_results/before.json evaluation_results/after.json --confidence 0.95 --output evaluation_results/comparison-new.json
```

解析はAIを再起動せず原reportと原証跡をfresh検証する。confidence省略は保存analysis_specを使い、変更は `--confidence 0.90` 等。移動した原証跡にはanalysisの `--evidence-root PATH` を使う。別母集合や新しい棋譜への差替えではない。現行検証器・source hash・解析ID・理由を別JSONへ保存する。

比較は候補Aの変更を許すが、固定B/資産、ケース・seed、予算・計測・runtime・取得fingerprint等の共通条件を照合する。独立に正常でも条件不一致なら対応差を正式に計算できない。

正式区間は固定有限序盤母集合の先後平均得点またはbefore/after対応差に対するHoeffding–Serfling bound。全予定ケース・両leg・品質・決定性等が適格な全数だけcensusを返す。time/deploymentの合法棋譜差は不正にしないが、この固定得点CIは出さない。数式のcomputedと正式available、数値基準と採用decisionは別である。

保存済みverifiedやhash一致だけで原証拠の意味検証を省略しない。公開inspect/assess/estimate/paired/compare/reanalysis/builderは共通検証経路を使い、不正cache/summaryを黙って修復しない。旧schema1〜4は可能な参考利用を維持するが、新出力5へ包むだけで正式昇格しない。旧秒から不足端点を生成しない。

| 終了コード | 意味 |
|---|---|
| 0 | 要求と保存が成功。正常参考評価の0は正式資格・自動採用ではない |
| 1 | 開始後の保存障害、対局/必須品質/正式・比較要求の不成立 |
| 2 | 入力不正、未対応root schema、開始前の既存出力指定 |

数値基準未達でも要求が正常なら0。失敗はphase/path/causeとreasonsを読み、別出力名で再実行する。旧schema1/2は予算設定の欠落を許すが、存在する不正設定は共通decode_inputで拒否し、両CLIで開始前に2を返す。正常な旧参考入力とraw証拠不足を不正型と混同しない。詳細は[旧形式の入力契約](harness_contracts.md#legacy-optional-budget)と最新reportsを参照する。

## 7. AI改善時の作業順序と限界

1. Git状態と全pytestを確認し、既存の失敗と新しい失敗を分ける。
2. ランダム版・探索版などの固定相手を依存ごと保存し、未実装のAI分離案を確認する。
3. 母集合・抽出・seed・予算・資産・採用基準を先に固定して変更前を保存する。
4. AI変更後は関連テスト・全pytest・2局smokeを通す。期待値だけを変えて仕様違反を隠さない。
5. 同じ条件で変更後を取得し、原証跡から再解析・比較する。quality/statistics/adoptionを分ける。
6. 測定と未検証事項を報告する。コミット・pushは明示依頼がある場合だけ行う。

Python random/PYTHONHASHSEEDはseed adapterで固定するが、numpy/GPU/独立Generator等は別契約が必要。実AItrace4、内部counterの真実性、全ケース決定性、未知時計/GPU、GUIブラウザ、停電時の完全性は既存fixtureの成功から保証しない。

空行・EOF・未知コマンド・引数不足・非整数座標への応答は課題仕様に未定義の部分がある。本体には例外終了・無応答経路があり、独自仕様で合格扱いせず別途確認する。整理前の操作説明と実行履歴は[拡張計画のarchive](archive/ハーネス拡張計画.md#snapshot-harness-operations)に保持する。
